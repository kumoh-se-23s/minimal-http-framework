# RFC 9110 — HTTP 의미론 (한국어 번역, 발췌)

> 이 문서는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110)의 비공식 한국어 번역이다. 원문과 차이가 있으면 원문이 우선한다.
> 서버 구현에 필요한 장만 번역했다: 3장, 5장, 6장, 7.1–7.2절, 8.1–8.6절, 9장, 10장, 15장. 나머지 장은 원문을 참고하라.
> 요구 수준 키워드(MUST, SHOULD, MAY 등)는 번역문 뒤에 괄호로 원어를 함께 적었다. ABNF 문법과 예시는 원문 그대로 두었다.
> HTTP/1.1 메시지 형식은 같은 폴더의 [RFC 9112 번역](rfc9112-ko.md)을 참고하라.

## 초록

HTTP(Hypertext Transfer Protocol)는 분산·협업형 하이퍼텍스트 정보 시스템을 위한 무상태(stateless) 애플리케이션 계층 프로토콜이다. 이 문서는 HTTP의 전체 아키텍처를 설명하고, 공통 용어를 정하고, 모든 버전이 공유하는 프로토콜의 측면을 정의한다. 이 정의에는 핵심 프로토콜 요소, 확장 메커니즘, 그리고 "http"와 "https" URI(Uniform Resource Identifier) 스킴이 포함된다.

이 문서는 RFC 3864를 갱신하며, RFC 2818, 7231, 7232, 7233, 7235, 7538, 7615, 7694와 RFC 7230의 일부를 대체한다.

## 3. 용어와 핵심 개념

HTTP는 월드 와이드 웹(WWW) 아키텍처를 위해 만들어졌고, 전 세계 하이퍼텍스트 시스템의 확장성 요구를 뒷받침하도록 시간이 흐르며 발전해 왔다. 그 아키텍처의 상당 부분이 HTTP를 정의하는 데 쓰는 용어에 반영되어 있다.

### 3.1. 리소스

HTTP 요청의 대상을 "리소스(resource)"라고 한다. HTTP는 리소스의 성격을 제한하지 않고, 리소스와 상호작용하는 데 쓸 수 있는 인터페이스만 정의한다. 대부분의 리소스는 4장에 설명된 URI(Uniform Resource Identifier)로 식별된다.

HTTP의 설계 목표 하나는 리소스 식별과 요청 의미론을 분리하는 것이다. 요청 의미론을 요청 메서드(9장)와 요청을 수식하는 몇몇 헤더 필드에 맡김으로써 이것이 가능해진다. 리소스는 요청 메서드의 의미론과 맞지 않는 방식으로 요청을 다룰 수 없다. 예를 들어 리소스의 URI가 안전하지 않은 의미를 암시하더라도, 클라이언트는 안전한 메서드로 보낸 요청을 처리할 때 리소스가 안전하지 않은 동작을 피할 것이라고 기대할 수 있다(9.2.1절 참고).

HTTP는 대상 리소스(7.1절)와 리소스 간의 관계를 나타내기 위해 URI 표준[URI]에 의존한다.

### 3.2. 표현

"표현(representation)"은 주어진 리소스의 과거, 현재, 또는 원하는 상태를 반영하기 위한 정보로, 프로토콜로 쉽게 전달할 수 있는 형식으로 되어 있다. 표현은 표현 메타데이터 집합과, 길이 제한이 없을 수도 있는 표현 데이터 스트림으로 이루어진다(8장).

HTTP는 리소스 자체를 전송하는 대신 전송할 수 있는 리소스 상태의 표현을 기준으로 통신을 정의함으로써, 균일한 인터페이스 뒤에 "정보를 숨길" 수 있게 한다. 덕분에 URI로 식별되는 리소스는 "라구나 비치의 현재 날씨" 같은 시간에 따라 변하는 함수를 포함해 무엇이든 될 수 있으며, 메시지가 생성되는 시점에 그 리소스를 나타내는 정보를 제공할 수 있다[REST].

균일한 인터페이스는 창문과 비슷하다. 창문 너머의 독립적인 행위자에게 메시지를 전달하는 방식으로만 어떤 대상을 관찰하고 조작할 수 있다. 통신에서 그 대상의 현재 상태나 원하는 상태를 표현할("대신할") 공유된 추상화가 필요하다. 표현이 하이퍼텍스트이면, 리소스 상태의 표현과 함께 수신자의 이후 상호작용을 안내하는 처리 지침도 제공할 수 있다.

대상 리소스에는 각각 리소스의 현재 상태를 반영하기 위한 여러 표현이 제공되거나, 그런 표현을 생성할 능력이 있을 수 있다. 보통 콘텐츠 협상(12장)에 기반한 알고리즘으로 그중 주어진 요청에 가장 적합한 표현 하나를 선택한다. 이 "선택된 표현(selected representation)"은 조건부 요청(13장)을 평가하고, GET(9.3.1절)에 대한 200(OK), 206(Partial Content), 304(Not Modified) 응답의 콘텐츠를 구성하는 데 쓸 데이터와 메타데이터를 제공한다.

### 3.3. 연결, 클라이언트, 서버

HTTP는 신뢰할 수 있는 전송 계층 또는 세션 계층 "연결" 위에서 동작하는 클라이언트/서버 프로토콜이다.

HTTP "클라이언트"는 하나 이상의 HTTP 요청을 보내기 위해 서버와 연결을 수립하는 프로그램이다. HTTP "서버"는 HTTP 응답을 보내서 HTTP 요청을 처리하기 위해 연결을 받아들이는 프로그램이다.

클라이언트와 서버라는 용어는 특정 연결에서 그 프로그램이 맡는 역할만 가리킨다. 같은 프로그램이 어떤 연결에서는 클라이언트로, 다른 연결에서는 서버로 동작할 수 있다.

HTTP는 무상태 프로토콜로 정의된다. 각 요청 메시지의 의미는 따로 떼어서 이해할 수 있고, 연결과 그 위의 메시지들 사이의 관계가 메시지 해석에 영향을 주지 않는다는 뜻이다. 예를 들어 CONNECT 요청(9.3.6절)이나 Upgrade 헤더 필드(7.8절)가 있는 요청은 연결의 첫 메시지뿐 아니라 언제든 올 수 있다. 많은 구현이 프록시 연결을 재사용하거나 여러 서버에 요청을 동적으로 부하 분산하기 위해 HTTP의 무상태 설계에 의존한다.

그래서 서버는 연결이 보호되어 있고 특정 에이전트 전용이 아닌 한, 같은 연결의 두 요청이 같은 사용자 에이전트에서 왔다고 가정해서는 안 된다(MUST NOT). 일부 비표준 HTTP 확장(예: [RFC4559])이 이 요구 사항을 어겨서 보안 및 상호운용성 문제를 일으킨 것으로 알려져 있다.

### 3.4. 메시지

HTTP는 연결을 통해 "메시지"를 주고받는 무상태 요청/응답 프로토콜이다. "송신자"와 "수신자"라는 용어는 각각 주어진 메시지를 보내거나 받는 모든 구현을 가리킨다.

클라이언트는 메서드(9장)와 요청 대상(7.1절)을 담은 "요청" 메시지 형태로 서버에 요청을 보낸다. 요청에는 요청 수식자, 클라이언트 정보, 표현 메타데이터를 위한 헤더 필드(6.3절), 메서드에 따라 처리될 콘텐츠(6.4절), 콘텐츠를 보내는 동안 수집한 정보를 전달하는 트레일러 필드(6.5절)도 들어 있을 수 있다.

서버는 하나 이상의 "응답" 메시지를 보내서 클라이언트의 요청에 응답하며, 각 응답에는 상태 코드(15장)가 들어 있다. 응답에는 서버 정보, 리소스 메타데이터, 표현 메타데이터를 위한 헤더 필드, 상태 코드에 따라 해석될 콘텐츠, 콘텐츠를 보내는 동안 수집한 정보를 전달하는 트레일러 필드도 들어 있을 수 있다.

### 3.5. 사용자 에이전트

"사용자 에이전트(user agent)"라는 용어는 요청을 시작하는 다양한 클라이언트 프로그램을 가리킨다.

가장 익숙한 형태의 사용자 에이전트는 범용 웹 브라우저이지만, 이는 전체 구현 중 일부에 불과하다. 그 밖의 흔한 사용자 에이전트로는 스파이더(웹을 돌아다니는 로봇), 명령줄 도구, 전광판, 가전제품, 저울, 전구, 펌웨어 업데이트 스크립트, 모바일 앱, 그리고 다양한 모양과 크기의 통신 기기가 있다.

사용자 에이전트라고 해서 요청 시점에 사람 사용자가 소프트웨어 에이전트와 직접 상호작용하고 있다는 뜻은 아니다. 많은 경우 사용자 에이전트는 백그라운드에서 실행되도록 설치되거나 설정되어, 결과를 나중에 살펴볼 수 있게 저장한다(또는 흥미롭거나 오류가 있는 결과의 일부만 저장한다). 예를 들어 스파이더는 보통 시작 URI를 받고, 웹을 하이퍼텍스트 그래프로 크롤링하면서 특정 동작을 따르도록 설정된다.

많은 사용자 에이전트는 사용자에게 대화형 제안을 하거나 보안·개인정보 문제를 적절히 경고할 수 없거나, 그러지 않기로 한다. 이 명세가 사용자에게 오류를 알리도록 요구하는 몇 안 되는 경우에도, 그 알림이 오류 콘솔이나 로그 파일에서만 확인되어도 괜찮다. 마찬가지로 자동화된 동작을 진행하기 전에 사용자 확인을 받으라는 요구 사항은 사전 설정, 실행 시 옵션, 또는 단순히 안전하지 않은 동작을 피하는 방식으로 충족할 수 있다. 사용자가 이미 선택을 했다면, 확인이 특정 사용자 인터페이스나 정상 처리의 중단을 뜻하지는 않는다.

### 3.6. 오리진 서버

"오리진 서버(origin server)"라는 용어는 주어진 대상 리소스에 대해 권한 있는(authoritative) 응답을 만들어 낼 수 있는 프로그램을 가리킨다.

가장 익숙한 형태의 오리진 서버는 대형 공개 웹사이트이다. 하지만 사용자 에이전트를 브라우저와 동일시하는 것처럼, 모든 오리진 서버가 비슷하다고 오해하기 쉽다. 흔한 오리진 서버에는 홈 오토메이션 장치, 설정 가능한 네트워크 구성 요소, 사무기기, 자율 로봇, 뉴스 피드, 교통 카메라, 실시간 광고 선택기, 주문형 비디오 플랫폼도 포함된다.

대부분의 HTTP 통신은 URI로 식별되는 어떤 리소스의 표현을 가져오는 요청(GET)으로 이루어진다. 가장 단순한 경우, 이는 사용자 에이전트(UA)와 오리진 서버(O) 사이의 양방향 연결(===) 하나로 이루어질 수 있다.

```
         request   >
    UA ======================================= O
                                <   response
```

### 3.7. 중개자

HTTP에서는 연결 체인을 통해 요청을 처리하도록 중개자를 쓸 수 있다. 흔한 HTTP "중개자(intermediary)"는 프록시, 게이트웨이, 터널 세 가지이다. 경우에 따라 중개자 하나가 요청의 성격에 따라 동작을 바꿔서 오리진 서버, 프록시, 게이트웨이, 터널 역할을 할 수도 있다.

```
         >             >             >             >
    UA =========== A =========== B =========== C =========== O
               <             <             <             <
```

위 그림은 사용자 에이전트와 오리진 서버 사이에 있는 중개자 세 개(A, B, C)를 보여 준다. 체인 전체를 지나는 요청이나 응답 메시지는 별개의 연결 네 개를 거친다. 일부 HTTP 통신 옵션은 터널이 아닌 가장 가까운 이웃과의 연결에만, 체인의 양 끝점에만, 또는 체인의 모든 연결에 적용될 수 있다. 그림은 일직선이지만, 각 참여자는 여러 통신을 동시에 하고 있을 수 있다. 예를 들어 B는 A의 요청을 처리하는 동시에 A 말고도 많은 클라이언트로부터 요청을 받거나, C 말고 다른 서버로 요청을 전달하고 있을 수 있다. 마찬가지로 나중의 요청은 부하 분산을 위한 동적 설정에 따라 다른 연결 경로로 보내질 수 있다.

"업스트림(upstream)"과 "다운스트림(downstream)"은 메시지 흐름에 대한 방향 요구 사항을 설명하는 데 쓰인다. 모든 메시지는 업스트림에서 다운스트림으로 흐른다. "인바운드(inbound)"와 "아웃바운드(outbound)"는 요청 경로에 대한 방향 요구 사항을 설명하는 데 쓰인다. 인바운드는 "오리진 서버 쪽으로", 아웃바운드는 "사용자 에이전트 쪽으로"를 뜻한다.

"프록시(proxy)"는 보통 로컬 설정 규칙에 따라 클라이언트가 선택하는 메시지 전달 에이전트로, 특정 종류의 절대 URI에 대한 요청을 받아 HTTP 인터페이스를 통한 변환으로 그 요청을 처리하려고 한다. "http" URI에 대한 프록시 요청처럼 변환이 아주 적은 경우도 있고, 완전히 다른 애플리케이션 계층 프로토콜과 상호 변환해야 하는 요청도 있다. 프록시는 보안 서비스, 주석 서비스, 공유 캐시를 위해 조직의 HTTP 요청을 공통 중개자로 모으는 데 자주 쓰인다. 일부 프록시는 7.7절에 설명된 대로, 전달하는 동안 선택된 메시지나 콘텐츠에 변환을 적용하도록 설계되어 있다.

"게이트웨이(gateway, '리버스 프록시'라고도 한다)"는 아웃바운드 연결에 대해서는 오리진 서버처럼 동작하지만, 받은 요청을 변환해서 다른 서버(들)로 인바운드 전달하는 중개자이다. 게이트웨이는 레거시이거나 신뢰할 수 없는 정보 서비스를 감싸거나, "가속기" 캐싱으로 서버 성능을 높이거나, HTTP 서비스를 여러 기계에 나누거나 부하 분산하는 데 자주 쓰인다.

오리진 서버에 적용되는 모든 HTTP 요구 사항은 게이트웨이의 아웃바운드 통신에도 적용된다. 게이트웨이는 이 명세의 범위 밖인 HTTP 비공개 확장을 포함해, 원하는 어떤 프로토콜로든 인바운드 서버와 통신한다. 하지만 서드파티 HTTP 서버와 상호운용하려는 HTTP-to-HTTP 게이트웨이는 게이트웨이의 인바운드 연결에서 사용자 에이전트 요구 사항을 따라야 한다.

"터널(tunnel)"은 메시지를 바꾸지 않고 두 연결 사이에서 맹목적으로 중계한다. 터널이 HTTP 요청으로 시작되었더라도, 일단 활성화되면 터널은 HTTP 통신의 당사자로 여겨지지 않는다. 터널은 중계하는 연결의 양 끝이 모두 닫히면 사라진다. 터널은 공유 방화벽 프록시를 통해 기밀 통신을 수립하기 위해 TLS(Transport Layer Security, [TLS13])를 쓸 때처럼, 중개자를 통해 가상 연결을 확장하는 데 쓰인다.

위의 중개자 분류는 HTTP 통신의 참여자로 동작하는 것들만 다룬다. 네트워크 프로토콜 스택의 하위 계층에서 동작하면서, 메시지 송신자 모르게 또는 허락 없이 HTTP 트래픽을 걸러내거나 방향을 바꾸는 중개자도 있다. 네트워크 중개자는 (프로토콜 수준에서) 경로상 공격자(on-path attacker)와 구별할 수 없으며, HTTP 의미론을 실수로 어겨서 보안 결함이나 상호운용성 문제를 일으키는 경우가 많다.

예를 들어 "가로채기 프록시(interception proxy)"[RFC3040](흔히 "투명 프록시"[RFC1919]라고도 한다)는 클라이언트가 선택하지 않는다는 점에서 HTTP 프록시와 다르다. 대신 가로채기 프록시는 나가는 TCP 포트 80 패킷(때로는 다른 흔한 포트의 트래픽도)을 걸러내거나 방향을 바꾼다. 가로채기 프록시는 로컬이 아닌 인터넷 서비스를 쓰기 전에 계정 가입을 강제하는 수단으로 공공 네트워크 접속 지점에서, 그리고 네트워크 사용 정책을 강제하기 위해 기업 방화벽 안에서 흔히 볼 수 있다.

### 3.8. 캐시

"캐시(cache)"는 이전 응답 메시지를 저장하는 로컬 저장소와, 메시지의 저장·조회·삭제를 제어하는 하위 시스템이다. 캐시는 이후의 동등한 요청에 대한 응답 시간과 네트워크 대역폭 소비를 줄이기 위해 캐시 가능한 응답을 저장한다. 어떤 클라이언트나 서버도 캐시를 쓸 수 있지만(MAY), 터널로 동작하는 동안에는 캐시를 쓸 수 없다.

캐시의 효과는 체인의 참여자 중 하나가 그 요청에 적용할 수 있는 캐시된 응답을 가지고 있으면 요청/응답 체인이 짧아진다는 것이다. 다음은 UA나 A가 캐시하지 않은 요청에 대해, B가 (C를 거쳐) O로부터 받은 이전 응답의 캐시 사본을 가지고 있을 때의 체인을 보여 준다.

```
            >             >
       UA =========== A =========== B - - - - - - C - - - - - - O
                  <             <
```

<p align="center">그림 3</p>

캐시가 이후 요청에 응답하는 데 쓰려고 응답 메시지의 사본을 저장하는 것이 허용되면, 그 응답은 "캐시 가능(cacheable)"하다. 응답이 캐시 가능하더라도, 캐시된 응답을 특정 요청에 언제 쓸 수 있는지에 대해 클라이언트나 오리진 서버가 추가 제약을 둘 수 있다. 캐시 동작과 캐시 가능한 응답에 대한 HTTP 요구 사항은 [CACHING]에 정의되어 있다.

월드 와이드 웹과 대규모 조직 내부에는 매우 다양한 캐시 아키텍처와 구성이 배치되어 있다. 대역폭을 아끼고 지연 시간을 줄이기 위한 국가 단위의 프록시 캐시 계층, 인기 사이트의 지역·전 세계 배포를 최적화하기 위해 게이트웨이 캐싱을 쓰는 콘텐츠 전송 네트워크, 캐시 항목을 브로드캐스트하거나 멀티캐스트하는 협업 시스템, 오프라인이나 지연이 큰 환경에서 쓰기 위해 미리 가져온 캐시 항목의 보관소 등이 있다.

## 5. 필드

HTTP는 등록된 키 네임스페이스를 가진, 확장 가능한 이름/값 쌍 형태로 데이터를 제공하기 위해 "필드(field)"를 쓴다. 필드는 메시지의 헤더 섹션과 트레일러 섹션 안에서 보내고 받는다(6장).

### 5.1. 필드 이름

필드 이름은 대응하는 필드 값이 그 이름으로 정의된 의미를 가진다는 것을 나타낸다. 예를 들어 Date 헤더 필드는 6.6.1절에서 그 필드가 나타나는 메시지의 생성 시각을 담는다고 정의되어 있다.

```
  field-name     = token
```

필드 이름은 대소문자를 구분하지 않으며, "Hypertext Transfer Protocol (HTTP) Field Name Registry"에 등록되어야 한다. 16.3.1절을 참고하라.

필드의 해석은 같은 메이저 HTTP 버전의 마이너 버전 사이에서 바뀌지 않는다. 다만 그 필드가 없을 때 수신자의 기본 동작은 바뀔 수 있다. 따로 명시하지 않으면, 필드는 모든 HTTP 버전에 대해 정의된다. 특히 Host와 Connection 필드는 HTTP/1.1 준수를 알리는지와 상관없이 모든 HTTP 구현이 인식해야 한다.

새 필드는 그 의미가 이를 인식하지 못하는 수신자가 안전하게 무시할 수 있도록 정의되어 있다면, 프로토콜 버전을 바꾸지 않고 도입할 수 있다. 16.3절을 참고하라.

프록시는 인식하지 못한 헤더 필드를 전달해야 한다(MUST). 단, 그 필드 이름이 Connection 헤더 필드(7.6.1절)에 나열되어 있거나, 프록시가 그런 필드를 차단하거나 다르게 변환하도록 특별히 설정된 경우는 예외이다. 그 밖의 수신자는 인식하지 못한 헤더 필드와 트레일러 필드를 무시해야 한다(SHOULD). 이 요구 사항을 지키면 이미 배치된 중개자를 갱신하거나 제거하지 않고도 HTTP의 기능을 확장할 수 있다.

### 5.2. 필드 줄과 결합된 필드 값

필드 섹션은 임의 개수의 "필드 줄(field line)"로 이루어진다. 각 필드 줄에는 필드를 식별하는 "필드 이름"(5.1절 참고)과, 그 필드 인스턴스의 데이터를 전달하는 "필드 줄 값(field line value)"이 있다.

필드 이름이 섹션에 한 번만 있으면, 그 필드의 결합된 "필드 값(field value)"은 대응하는 필드 줄 값 하나로 이루어진다. 필드 이름이 섹션 안에서 반복되면, 결합된 필드 값은 그 섹션 안의 대응하는 필드 줄 값들을 순서대로 이어 붙이고 각 필드 줄 값을 쉼표로 구분한 리스트로 이루어진다.

예를 들어 다음 섹션은

```
Example-Field: Foo, Bar
Example-Field: Baz
```

필드 이름이 "Example-Field"인 필드 줄 두 개를 담고 있다. 첫 번째 필드 줄의 필드 줄 값은 "Foo, Bar"이고, 두 번째 필드 줄 값은 "Baz"이다. "Example-Field"의 필드 값은 리스트 "Foo, Bar, Baz"이다.

### 5.3. 필드 순서

수신자는 필드 섹션 안에서 필드 이름이 같은 여러 필드 줄을, 메시지의 의미를 바꾸지 않고 하나의 필드 줄로 결합할 수 있다(MAY). 이어지는 각 필드 줄 값을 쉼표(",")와 선택적 공백(OWS, 5.6.3절에 정의)으로 구분해 첫 필드 줄 값 뒤에 순서대로 붙이면 된다. 일관성을 위해 쉼표 뒤에 SP 하나를 쓴다.

그러므로 이름이 같은 필드 줄을 받은 순서는 필드 값 해석에 중요하다. 프록시는 메시지를 전달할 때 이 필드 줄 값들의 순서를 바꿔서는 안 된다(MUST NOT).

이 말은, 아래에 언급하는 잘 알려진 예외를 제외하면, 송신자는 메시지 안에(헤더든 트레일러든) 이름이 같은 필드 줄을 여러 개 생성하거나, 같은 이름의 필드 줄이 이미 있는데 필드 줄을 덧붙여서는 안 된다는(MUST NOT) 뜻이다. 단, 그 필드의 정의가 여러 필드 줄 값을 쉼표로 구분된 리스트로 다시 결합하는 것을 허용하는 경우(즉, 필드 정의의 대안 중 적어도 하나가 5.6.1절에 정의된 #(values) ABNF 규칙처럼 쉼표로 구분된 리스트를 허용하는 경우)는 예외이다.

> **참고:** 실제로는 "Set-Cookie" 헤더 필드([COOKIE])가 응답 메시지에서 여러 필드 줄에 걸쳐 나타나는 경우가 많고, 리스트 문법을 쓰지 않아서, 이름이 같은 여러 필드 줄에 대한 위 요구 사항을 어긴다. 이 필드는 하나의 필드 값으로 결합할 수 없으므로, 수신자는 필드를 처리할 때 "Set-Cookie"를 특별한 경우로 다뤄야 한다. (자세한 내용은 [Kri2001]의 부록 A.2.3을 참고하라.)

섹션 안에서 이름이 다른 필드 줄을 받은 순서는 중요하지 않다. 하지만 요청의 Host, 응답의 Date처럼 추가 제어 데이터를 담은 헤더 필드를 먼저 보내는 것이 좋은 관행이다. 그래야 구현이 메시지를 처리하지 않을지 최대한 일찍 결정할 수 있다.

서버는 요청 헤더 섹션 전체를 받을 때까지 요청을 대상 리소스에 적용해서는 안 된다(MUST NOT). 나중에 오는 헤더 필드 줄에 조건, 인증 자격 증명, 또는 요청 처리에 영향을 줄 수 있는 의도적으로 오해를 일으키는 중복 헤더 필드가 있을 수 있기 때문이다.

### 5.4. 필드 제한

2장에 설명된 대로, HTTP는 각 필드 줄이나 필드 값의 길이, 또는 헤더나 트레일러 섹션 전체의 길이에 미리 정해진 제한을 두지 않는다. 실제로는 개별 길이에 대한 다양한 임시 제한이 있으며, 특정 필드의 의미에 따라 달라지는 경우가 많다.

처리하고 싶은 것보다 큰 요청 헤더 필드 줄, 필드 값, 또는 필드 집합을 받은 서버는 적절한 4xx(Client Error) 상태 코드로 응답해야 한다(MUST). 이런 헤더 필드를 무시하면 서버가 요청 스머글링 공격([HTTP/1.1] 11.2절)에 더 취약해진다.

클라이언트는 처리하고 싶은 것보다 큰 필드 줄을 받았을 때, 버린 값을 무시해도 메시지 프레이밍이나 응답 의미가 바뀌지 않는 필드라면 그 필드 줄을 버리거나 잘라낼 수 있다(MAY).

### 5.5. 필드 값

HTTP 필드 값은 필드 문법으로 정의된 형식의 문자열로 이루어진다. 각 필드의 문법은 보통 ABNF([RFC5234])로 정의된다.

```
  field-value    = *field-content
  field-content  = field-vchar
                   [ 1*( SP / HTAB / field-vchar ) field-vchar ]
  field-vchar    = VCHAR / obs-text
  obs-text       = %x80-FF
```

필드 값에는 앞뒤 공백이 포함되지 않는다. 특정 HTTP 버전이 메시지에 그런 공백이 나타나는 것을 허용한다면, 필드 파싱 구현은 필드 값을 평가하기 전에 그 공백을 제외해야 한다(MUST).

필드 값은 보통 US-ASCII 문자[USASCII] 범위로 제한된다. 더 넓은 범위의 문자가 필요한 필드는 [RFC8187]에 정의된 것 같은 인코딩을 쓸 수 있다. 역사적으로 HTTP는 ISO-8859-1 문자셋[ISO-8859-1]의 텍스트로 된 필드 내용을 허용했고, 다른 문자셋은 [RFC2047] 인코딩으로만 지원했다. 새로 정의되는 필드의 명세는 값을 보이는 US-ASCII 옥텟(VCHAR), SP, HTAB으로 제한해야 한다(SHOULD). 수신자는 필드 내용에 허용되는 그 밖의 옥텟(즉, obs-text)을 불투명한(opaque) 데이터로 다뤄야 한다(SHOULD).

CR, LF, NUL 문자를 담은 필드 값은 구현마다 그 문자를 파싱하고 해석하는 방식이 달라서 유효하지 않고 위험하다. 필드 값 안에서 CR, LF, NUL을 받은 수신자는 메시지를 거절하거나, 메시지를 더 처리하거나 전달하기 전에 그 문자들을 각각 SP로 바꿔야 한다(MUST). 그 밖의 CTL 문자를 담은 필드 값도 유효하지 않다. 하지만 수신자는 견고성을 위해, 그런 문자가 안전한 맥락(예: 다운스트림 HTTP 파서가 처리하지 않을 애플리케이션 전용 따옴표 문자열 안)에 나타나면 유지할 수 있다(MAY).

필드 값으로 멤버 하나만 예상하는 필드를 "단일 필드(singleton field)"라고 한다.

필드 값으로 여러 멤버를 허용하는 필드를 "리스트 기반 필드(list-based field)"라고 한다. 여러 멤버를 담을 수 있는 필드 값을 정의할 때는 5.6.1절의 리스트 연산자 확장을 공통 표기법으로 쓴다.

쉼표(",")는 멤버 사이의 구분자로 쓰이므로, 멤버 안의 데이터로 쉼표를 허용한다면 주의해서 다뤄야 한다. 이것은 리스트 기반 필드와 단일 필드 모두에 해당한다. 단일 필드가 실수로 여러 멤버와 함께 보내질 수 있고, 그런 오류를 감지하면 상호운용성이 좋아지기 때문이다. HTTP-date나 URI-reference 요소처럼 멤버 안에 쉼표를 담을 것으로 예상되는 필드는, 그 데이터 안의 쉼표를 리스트 구분자와 구별할 수 있도록 그 요소를 구분자로 감싸서 정의해야 한다.

예를 들어 (둘 다 쉼표를 담을 수 있는) 텍스트 날짜와 URI는 다음과 같은 리스트 기반 필드 값으로 안전하게 전달할 수 있다.

```
Example-URIs: "http://example.com/a.html,foo",
              "http://without-a-comma.example.com/"
Example-Dates: "Sat, 04 May 1996", "Wed, 14 Sep 2005"
```

큰따옴표 구분자는 거의 항상 quoted-string 규칙(5.6.4절)과 함께 쓰인다는 점에 유의하라. 큰따옴표 안에서 다른 문법을 쓰면 불필요한 혼란을 일으킬 가능성이 높다.

많은 필드(8.3절에 정의된 Content-Type 등)는 매개변수 값으로 따옴표 없는 형태(token)와 따옴표 있는 형태(quoted-string)를 모두 허용하는 공통 매개변수 문법(5.6.6절)을 쓴다. 공통 문법을 쓰면 수신자가 기존 파서 구성 요소를 재사용할 수 있다. 두 형태를 모두 허용할 때, 매개변수 값의 의미는 토큰으로 받았든 따옴표 문자열로 받았든 같아야 한다.

> **참고:** 필드 값 문법을 정의할 때, 이 명세는 필드 이름을 딴 ABNF 규칙으로 그 필드 값에 허용되는 문법을 정의한다(그 값을 하위 메시지 문법에서 추출하고, 여러 인스턴스를 리스트로 결합한 다음의 문법이다).

### 5.6. 필드 값 정의를 위한 공통 규칙

#### 5.6.1. 리스트 (#rule ABNF 확장)

일부 리스트 기반 필드 값 정의의 가독성을 높이기 위해 [RFC5234]의 ABNF 규칙에 대한 #rule 확장을 쓴다.

쉼표로 구분된 요소 리스트를 정의하기 위해 "*"와 비슷한 "#" 구문을 정의한다. 전체 형태는 "<n>#<m>element"로, 최소 <n>개, 최대 <m>개의 요소를 뜻하며, 각 요소는 쉼표(",") 하나와 선택적 공백(OWS, 5.6.3절에 정의)으로 구분된다.

##### 5.6.1.1. 송신자 요구 사항

리스트 구문을 쓰는 모든 규칙에서 송신자는 빈 리스트 요소를 생성해서는 안 된다(MUST NOT). 다시 말해 송신자는 다음 문법을 만족하는 리스트를 생성해야 한다.

```
  1#element => element *( OWS "," OWS element )
```

그리고

```
  #element => [ 1#element ]
```

그리고 n >= 1, m > 1일 때

```
  <n>#<m>element => element <n-1>*<m-1>( OWS "," OWS element )
```

부록 A에 리스트 구문을 펼친 뒤의 송신자용 ABNF 모음이 있다.

##### 5.6.1.2. 수신자 요구 사항

빈 요소는 요소 개수에 포함되지 않는다. 수신자는 적당한 개수의 빈 리스트 요소를 파싱하고 무시해야 한다(MUST). 값을 병합하는 송신자의 흔한 실수를 처리할 수 있을 만큼은 되어야 하지만, 서비스 거부 수단으로 쓰일 수 있을 만큼 많아서는 안 된다. 다시 말해 수신자는 다음 문법을 만족하는 리스트를 받아들여야 한다(MUST).

```
  #element => [ element ] *( OWS "," OWS [ element ] )
```

빈 리스트 요소가 있을 수 있으므로 RFC 5234 ABNF로는 리스트 요소 개수를 강제할 수 없다. 그래서 모든 경우를 개수가 지정되지 않은 것처럼 대응시킨다.

예를 들어 다음 ABNF 규칙이 주어지면

```
  example-list      = 1#example-list-elmt
  example-list-elmt = token ; see Section 5.6.2
```

다음은 example-list의 유효한 값이다(큰따옴표는 구분을 위해서만 표시했고 값에 포함되지 않는다).

```
  "foo,bar"
  "foo ,bar,"
  "foo , ,bar,charlie"
```

반면 다음 값은 example-list 규칙이 비어 있지 않은 요소를 적어도 하나 요구하므로 유효하지 않다.

```
  ""
  ","
  ",   ,"
```

#### 5.6.2. 토큰

토큰은 공백이나 구분자를 포함하지 않는 짧은 텍스트 식별자이다.

```
  token          = 1*tchar

  tchar          = "!" / "#" / "$" / "%" / "&" / "'" / "*"
                 / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~"
                 / DIGIT / ALPHA
                 ; any VCHAR, except delimiters
```

많은 HTTP 필드 값은 공백이나 특정 구분 문자로 구분되는 공통 문법 구성 요소로 정의된다. 구분자는 토큰에 허용되지 않는 US-ASCII 보이는 문자 집합(DQUOTE와 "(),/:;<=>?@[\]{}")에서 고른다.

#### 5.6.3. 공백

이 명세는 선형 공백 사용을 나타내는 세 가지 규칙을 쓴다. OWS(선택적 공백), RWS(필수 공백), BWS("나쁜" 공백)이다.

OWS 규칙은 0개 이상의 선형 공백 옥텟이 나타날 수 있는 곳에 쓴다. 가독성을 위해 선택적 공백을 쓰는 것이 바람직한 프로토콜 요소에서는 송신자가 선택적 공백을 SP 하나로 생성해야 한다(SHOULD). 그 밖의 경우, 송신자는 메시지를 그 자리에서 필터링하면서 잘못되었거나 원치 않는 프로토콜 요소를 덮어쓸 때 필요한 경우가 아니면 선택적 공백을 생성하지 않아야 한다(SHOULD NOT).

RWS 규칙은 필드 토큰을 구분하기 위해 적어도 하나의 선형 공백 옥텟이 필요할 때 쓴다. 송신자는 RWS를 SP 하나로 생성해야 한다(SHOULD).

OWS와 RWS는 SP 하나와 의미가 같다. OWS나 RWS로 정의된 것으로 알려진 내용은 해석하거나 메시지를 다운스트림으로 전달하기 전에 SP 하나로 바꿀 수 있다(MAY).

BWS 규칙은 역사적인 이유로만 문법이 선택적 공백을 허용하는 곳에 쓴다. 송신자는 메시지에 BWS를 생성해서는 안 된다(MUST NOT). 수신자는 이런 나쁜 공백이 있는지 파싱하고, 프로토콜 요소를 해석하기 전에 제거해야 한다(MUST).

BWS에는 의미가 없다. BWS로 정의된 것으로 알려진 내용은 해석하거나 메시지를 다운스트림으로 전달하기 전에 제거할 수 있다(MAY).

```
  OWS            = *( SP / HTAB )
                 ; optional whitespace
  RWS            = 1*( SP / HTAB )
                 ; required whitespace
  BWS            = OWS
                 ; "bad" whitespace
```

#### 5.6.4. 따옴표 문자열

텍스트 문자열을 큰따옴표로 감싸면 하나의 값으로 파싱된다.

```
  quoted-string  = DQUOTE *( qdtext / quoted-pair ) DQUOTE
  qdtext         = HTAB / SP / %x21 / %x23-5B / %x5D-7E / obs-text
```

백슬래시 옥텟("\")은 quoted-string과 comment 구문 안에서 단일 옥텟 이스케이프 수단으로 쓸 수 있다. quoted-string 값을 처리하는 수신자는 quoted-pair를 백슬래시 뒤의 옥텟으로 바뀐 것처럼 다뤄야 한다(MUST).

```
  quoted-pair    = "\" ( HTAB / SP / VCHAR / obs-text )
```

송신자는 문자열 안의 DQUOTE와 백슬래시 옥텟을 이스케이프해야 하는 경우가 아니면 quoted-string 안에 quoted-pair를 생성하지 않아야 한다(SHOULD NOT). 송신자는 주석 안의 괄호["("와 ")"]와 백슬래시 옥텟을 이스케이프해야 하는 경우가 아니면 comment 안에 quoted-pair를 생성하지 않아야 한다(SHOULD NOT).

#### 5.6.5. 주석

일부 HTTP 필드에는 주석 텍스트를 괄호로 감싸서 주석을 넣을 수 있다. 주석은 필드 값 정의의 일부로 "comment"를 담은 필드에서만 허용된다.

```
  comment        = "(" *( ctext / quoted-pair / comment ) ")"
  ctext          = HTAB / SP / %x21-27 / %x2A-5B / %x5D-7E / obs-text
```

#### 5.6.6. 매개변수

매개변수는 이름/값 쌍의 인스턴스로, 필드 값에서 어떤 항목에 보조 정보를 덧붙이는 공통 문법으로 자주 쓰인다. 각 매개변수는 보통 바로 앞의 세미콜론으로 구분된다.

```
  parameters      = *( OWS ";" OWS [ parameter ] )
  parameter       = parameter-name "=" parameter-value
  parameter-name  = token
  parameter-value = ( token / quoted-string )
```

매개변수 이름은 대소문자를 구분하지 않는다. 매개변수 값은 매개변수 이름의 의미에 따라 대소문자를 구분할 수도, 구분하지 않을 수도 있다. 매개변수와 몇 가지 동등한 형태의 예는 미디어 타입(8.3.1절)과 Accept 헤더 필드(12.5.1절)에서 볼 수 있다.

token 규칙에 맞는 매개변수 값은 토큰으로 보내도 되고 quoted-string 안에 넣어 보내도 된다. 따옴표가 있는 값과 없는 값은 동등하다.

> **참고:** 매개변수는 "=" 문자 주변에 공백("나쁜" 공백도 포함)을 허용하지 않는다.

#### 5.6.7. 날짜/시간 형식

1995년 이전에는 서버가 타임스탬프를 전달할 때 흔히 쓰던 형식이 세 가지 있었다. 오래된 구현과의 호환을 위해 여기서 세 가지를 모두 정의한다. 선호하는 형식은 인터넷 메시지 형식[RFC5322]에서 쓰는 날짜·시간 명세의 고정 길이, 단일 시간대 부분집합이다.

```
  HTTP-date    = IMF-fixdate / obs-date
```

선호하는 형식의 예는 다음과 같다.

```
  Sun, 06 Nov 1994 08:49:37 GMT    ; IMF-fixdate
```

폐기된 두 형식의 예는 다음과 같다.

```
  Sunday, 06-Nov-94 08:49:37 GMT   ; obsolete RFC 850 format
  Sun Nov  6 08:49:37 1994         ; ANSI C's asctime() format
```

HTTP 필드의 타임스탬프 값을 파싱하는 수신자는 세 가지 HTTP-date 형식을 모두 받아들여야 한다(MUST). HTTP-date로 정의된 타임스탬프를 하나 이상 담은 필드를 생성하는 송신자는 그 타임스탬프를 IMF-fixdate 형식으로 생성해야 한다(MUST).

HTTP-date 값은 협정 세계시(UTC)의 한 시점으로 시간을 나타낸다. 처음 두 형식은 UTC라는 이름의 전신인 그리니치 평균시의 세 글자 약어 "GMT"로 UTC를 나타낸다. asctime 형식의 값은 UTC로 가정한다.

"시계(clock)"는 UTC 기준 현재 시각의 합리적인 근삿값을 제공할 수 있는 구현이다. 시계 구현은 UTC와 동기화하기 위해 NTP([RFC5905])나 그와 비슷한 프로토콜을 쓰는 것이 좋다.

선호하는 형식:

```
  IMF-fixdate  = day-name "," SP date1 SP time-of-day SP GMT
  ; fixed length/zone/capitalization subset of the format
  ; see Section 3.3 of [RFC5322]

  day-name     = %s"Mon" / %s"Tue" / %s"Wed"
               / %s"Thu" / %s"Fri" / %s"Sat" / %s"Sun"

  date1        = day SP month SP year
               ; e.g., 02 Jun 1982

  day          = 2DIGIT
  month        = %s"Jan" / %s"Feb" / %s"Mar" / %s"Apr"
               / %s"May" / %s"Jun" / %s"Jul" / %s"Aug"
               / %s"Sep" / %s"Oct" / %s"Nov" / %s"Dec"
  year         = 4DIGIT

  GMT          = %s"GMT"

  time-of-day  = hour ":" minute ":" second
               ; 00:00:00 - 23:59:60 (leap second)

  hour         = 2DIGIT
  minute       = 2DIGIT
  second       = 2DIGIT
```

폐기된 형식:

```
  obs-date     = rfc850-date / asctime-date

  rfc850-date  = day-name-l "," SP date2 SP time-of-day SP GMT
  date2        = day "-" month "-" 2DIGIT
               ; e.g., 02-Jun-82

  day-name-l   = %s"Monday" / %s"Tuesday" / %s"Wednesday"
               / %s"Thursday" / %s"Friday" / %s"Saturday"
               / %s"Sunday"

  asctime-date = day-name SP date3 SP time-of-day SP year
  date3        = month SP ( 2DIGIT / ( SP 1DIGIT ))
               ; e.g., Jun  2
```

HTTP-date는 대소문자를 구분한다. [CACHING] 4.2절은 캐시 수신자에 대해 이를 완화한다는 점에 유의하라.

송신자는 HTTP-date 안에 문법에서 SP로 명시한 것 외의 공백을 추가로 생성해서는 안 된다(MUST NOT). day-name, day, month, year, time-of-day의 의미는 같은 이름의 인터넷 메시지 형식 구문([RFC5322] 3.3절)에 정의된 것과 같다.

두 자리 연도를 쓰는 rfc850-date 형식의 타임스탬프 값을 받은 수신자는, 50년 넘게 미래인 것처럼 보이는 타임스탬프를 끝 두 자리가 같은 가장 최근의 과거 연도로 해석해야 한다(MUST).

타임스탬프 값을 받는 수신자는 필드 정의가 따로 제한하지 않는 한 타임스탬프를 견고하게 파싱하는 것이 좋다. 예를 들어 HTTP가 아닌 출처에서 온 메시지가 가끔 HTTP로 전달되는데, 그 출처는 인터넷 메시지 형식에 정의된 어떤 날짜·시간 명세든 생성할 수 있다.

> **참고:** 타임스탬프 형식에 대한 HTTP 요구 사항은 프로토콜 스트림 안에서 쓸 때만 적용된다. 사용자에게 표시하거나 요청을 로깅하는 등의 용도에서는 이 형식을 쓰지 않아도 된다.

## 6. 메시지 추상화

HTTP의 각 메이저 버전은 메시지를 전달하기 위한 고유한 문법을 정의한다. 이 장은 그 메시지들의 특성, 공통 구조, 의미 전달 능력을 일반화해서 HTTP 메시지의 추상 데이터 타입을 정의한다. 이 추상화는 HTTP 버전과 독립적인 송신자·수신자 요구 사항을 정의하는 데 쓰이며, 덕분에 한 버전의 메시지가 의미를 바꾸지 않고 다른 버전을 거쳐 중계될 수 있다.

"메시지"는 다음으로 이루어진다.

- 메시지를 설명하고 라우팅하기 위한 제어 데이터
- 그 제어 데이터를 확장하고, 송신자, 메시지, 콘텐츠, 컨텍스트에 대한 추가 정보를 전달하기 위한 이름/값 쌍의 헤더 조회 테이블
- 길이 제한이 없을 수도 있는 콘텐츠 스트림
- 콘텐츠를 보내는 동안 얻은 정보를 전달하기 위한 이름/값 쌍의 트레일러 조회 테이블

프레이밍과 제어 데이터가 먼저 전송되고, 그 뒤에 헤더 테이블을 위한 필드를 담은 헤더 섹션이 온다. 메시지에 콘텐츠가 있으면 헤더 섹션 뒤에 콘텐츠가 전송되며, 그 뒤에 트레일러 테이블을 위한 필드를 담을 수 있는 트레일러 섹션이 올 수 있다.

메시지는 스트림으로 처리된다고 예상한다. 즉, 스트림의 목적과 계속 처리할지 여부가 읽는 도중에 드러난다. 그래서 제어 데이터는 수신자가 즉시 알아야 할 것을, 헤더 필드는 콘텐츠를 받기 전에 알아야 할 것을 설명한다. 콘텐츠(있다면)는 아마도 수신자가 메시지 의미를 이행하기 위해 원하거나 필요로 하는 것을 담고 있고, 트레일러 필드는 콘텐츠를 보내기 전에는 알 수 없었던 선택적 메타데이터를 제공한다.

메시지는 "자기 서술적(self-descriptive)"이도록 의도된다. 전송 중에 압축되거나 생략된 부분을 디코딩하거나 재구성한 뒤에는, 수신자가 메시지에 대해 알아야 할 모든 것을 (이전 메시지로 확립된) 송신자의 현재 애플리케이션 상태를 이해하지 않고도 메시지 자체만 보고 알아낼 수 있다. 하지만 클라이언트는 대응하는 응답을 파싱하거나, 해석하거나, 캐시할 때 요청에 대한 정보를 유지해야 한다(MUST). 예를 들어 HEAD 메서드에 대한 응답은 GET에 대한 응답의 앞부분과 똑같아 보이지만, 같은 방식으로 파싱할 수 없다.

이 메시지 추상화는 여러 HTTP 버전에 걸친 일반화이므로, 일부 버전에는 없는 기능도 포함되어 있다는 점에 유의하라. 예를 들어 트레일러는 HTTP/1.1의 청크 전송 코딩에서 콘텐츠 뒤의 트레일러 섹션으로 도입되었다. HTTP/2와 HTTP/3에서는 각 스트림을 끝내는 헤더 블록 안에 동등한 기능이 있다.

### 6.1. 프레이밍과 완전성

메시지 프레이밍은 각 메시지가 어디서 시작하고 끝나는지를 나타내서, 같은 연결의 다른 메시지나 잡음과 구별할 수 있게 한다. HTTP의 각 메이저 버전은 고유한 프레이밍 메커니즘을 정의한다.

HTTP/0.9와 초기 HTTP/1.0 배포에서는 하위 연결을 닫는 것으로 응답을 끝냈다. 하위 호환성을 위해 HTTP/1.1에서도 이 암묵적 프레이밍이 허용된다. 하지만 암묵적 프레이밍은 연결이 일찍 닫혔을 때 불완전한 응답을 구별하지 못할 수 있다. 그래서 거의 모든 최신 구현은 길이로 구분된 메시지 데이터 시퀀스 형태의 명시적 프레이밍을 쓴다.

메시지는 프레이밍이 나타내는 옥텟을 모두 사용할 수 있을 때 "완전하다(complete)"고 본다. 명시적 프레이밍을 쓰지 않을 때, 하위 연결의 종료로 끝난 응답 메시지는 불완전한 응답과 구별되지 않을 수 있지만, 전송 수준 오류가 불완전함을 나타내지 않는 한 완전한 것으로 본다는 점에 유의하라.

### 6.2. 제어 데이터

메시지는 주요 목적을 설명하는 제어 데이터로 시작한다. 요청 메시지의 제어 데이터에는 요청 메서드(9장), 요청 대상(7.1절), 프로토콜 버전(2.5절)이 포함된다. 응답 메시지의 제어 데이터에는 상태 코드(15장), 선택적 사유 구절(reason phrase), 프로토콜 버전이 포함된다.

HTTP/1.1([HTTP/1.1]) 이하에서는 제어 데이터가 메시지의 첫 줄로 전송된다. HTTP/2([HTTP/2])와 HTTP/3([HTTP/3])에서는 제어 데이터가 예약된 이름 접두사(예: ":authority")를 가진 의사 헤더 필드(pseudo-header field)로 전송된다.

모든 HTTP 메시지에는 프로토콜 버전이 있다. 사용하는 버전에 따라 메시지 안에서 명시적으로 식별되거나, 메시지를 받은 연결로부터 추론된다. 수신자는 그 버전 정보로 그 송신자와의 이후 통신에 대한 제약이나 가능성을 판단한다.

중개자가 메시지를 전달하면, 프로토콜 버전은 그 중개자가 쓰는 버전을 반영하도록 갱신된다. 전달된 메시지 안에서 업스트림 프로토콜 정보를 전달하는 데는 Via 헤더 필드(7.6.3절)를 쓴다.

클라이언트는 자신이 준수하는 가장 높은 버전이면서, (알고 있다면) 메이저 버전이 서버가 지원하는 가장 높은 버전보다 높지 않은 버전을 요청 버전으로 보내야 한다(SHOULD). 클라이언트는 자신이 준수하지 않는 버전을 보내서는 안 된다(MUST NOT).

서버가 HTTP 명세를 잘못 구현한 것으로 알려져 있다면, 클라이언트는 더 낮은 요청 버전을 보낼 수 있다(MAY). 다만 적어도 한 번은 정상적인 요청을 시도하고, 응답 상태 코드나 헤더 필드(예: Server)로 서버가 더 높은 요청 버전을 제대로 처리하지 못한다고 판단한 뒤에만 그렇게 해야 한다.

서버는 메이저 버전이 요청에서 받은 것보다 작거나 같으면서 자신이 준수하는 가장 높은 버전을 응답 버전으로 보내야 한다(SHOULD). 서버는 자신이 준수하지 않는 버전을 보내서는 안 된다(MUST NOT). 서버는 어떤 이유로든 클라이언트의 메이저 프로토콜 버전에 대한 서비스를 거절하고 싶다면 505(HTTP Version Not Supported) 응답을 보낼 수 있다.

자신이 구현한 메이저 버전 번호와, 구현한 것보다 높은 마이너 버전 번호를 가진 메시지를 받은 수신자는, 그 메시지를 그 메이저 버전 안에서 자신이 준수하는 가장 높은 마이너 버전인 것처럼 처리해야 한다(SHOULD). 수신자는 더 높은 마이너 버전을 지원한다고 아직 알리지 않은 수신자에게 보내진 더 높은 마이너 버전의 메시지가, 같은 메이저 버전의 어떤 구현이든 안전하게 처리할 수 있을 만큼 하위 호환된다고 가정할 수 있다.

### 6.3. 헤더 필드

콘텐츠보다 먼저 보내거나 받는 필드(5장)를 "헤더 필드(header field)"(구어로는 그냥 "헤더")라고 한다.

메시지의 "헤더 섹션(header section)"은 헤더 필드 줄의 연속으로 이루어진다. 각 헤더 필드는 메시지 의미를 수정하거나 확장하거나, 송신자를 설명하거나, 콘텐츠를 정의하거나, 추가 컨텍스트를 제공할 수 있다.

> **참고:** 이름이 있는 필드를 특별히 "헤더 필드"라고 부를 때는, 그 필드를 헤더 섹션에서만 보낼 수 있다는 뜻이다.

### 6.4. 콘텐츠

HTTP 메시지는 완전한 표현이나 부분 표현을 메시지 "콘텐츠(content)"로 전송하는 경우가 많다. 콘텐츠는 메시지 프레이밍으로 구분되어 헤더 섹션 뒤에 전송되는 옥텟 스트림이다.

이 콘텐츠의 추상적 정의는 메시지 프레이밍에서 추출한 뒤의 데이터를 반영한다. 예를 들어 HTTP/1.1 메시지 본문([HTTP/1.1] 6장)은 청크 전송 코딩으로 인코딩된 데이터 스트림(데이터 청크의 연속, 길이 0인 청크 하나, 트레일러 섹션)으로 이루어질 수 있다. 반면 같은 메시지의 콘텐츠에는 전송 코딩을 디코딩한 뒤의 데이터 스트림만 포함된다. 청크 길이, 청크 프레이밍 문법, 트레일러 필드(6.5절)는 포함되지 않는다.

> **참고:** 일부 필드 이름에는 "Content-" 접두사가 붙어 있다. 이것은 비공식적인 관례이다. 이 필드 중 일부는 위에서 정의한 메시지의 콘텐츠를 가리키지만, 다른 일부는 선택된 표현(3.2절)을 범위로 한다. 구분하려면 각 필드의 정의를 참고하라.

#### 6.4.1. 콘텐츠 의미론

요청에서 콘텐츠의 목적은 메서드 의미론(9장)으로 정의된다.

예를 들어 PUT 요청(9.3.4절)의 콘텐츠에 담긴 표현은 요청이 성공적으로 적용된 뒤 대상 리소스의 원하는 상태를 나타내는 반면, POST 요청(9.3.3절)의 콘텐츠에 담긴 표현은 대상 리소스가 처리할 정보를 나타낸다.

응답에서 콘텐츠의 목적은 요청 메서드, 응답 상태 코드(15장), 그리고 그 콘텐츠를 설명하는 응답 필드로 정의된다. 예를 들어 GET(9.3.1절)에 대한 200(OK) 응답의 콘텐츠는 메시지 생성 날짜(6.6.1절) 시점에 관찰된 대상 리소스의 현재 상태를 나타내는 반면, POST에 대한 응답에서 같은 상태 코드의 콘텐츠는 처리 결과나, 처리를 적용한 뒤 대상 리소스의 새 상태를 나타낼 수 있다.

GET에 대한 206(Partial Content) 응답의 콘텐츠는 15.3.7절에 설명된 대로, 선택된 표현의 한 부분이나 그 표현의 여러 부분을 담은 멀티파트 메시지 본문을 담는다.

오류 상태 코드를 가진 응답 메시지는 보통 오류 상태를 나타내는 콘텐츠를 담아서, 오류 상태와 이를 해결하기 위해 제안하는 단계를 설명한다.

HEAD 요청 메서드(9.3.2절)에 대한 응답에는 콘텐츠가 절대 포함되지 않는다. 관련 응답 헤더 필드는 요청 메서드가 GET(9.3.1절)이었다면 어떤 값을 가졌을지만 나타낸다.

CONNECT 요청 메서드(9.3.6절)에 대한 2xx(Successful) 응답은 콘텐츠를 갖는 대신 연결을 터널 모드로 전환한다.

모든 1xx(Informational), 204(No Content), 304(Not Modified) 응답에는 콘텐츠가 포함되지 않는다.

그 밖의 모든 응답에는 콘텐츠가 포함된다. 다만 그 콘텐츠의 길이는 0일 수 있다.

#### 6.4.2. 콘텐츠 식별

완전한 표현이나 부분 표현을 메시지 콘텐츠로 전송할 때, 송신자가 그 특정 표현에 대응하는 리소스의 식별자를 제공하거나 수신자가 이를 알아내는 것이 바람직한 경우가 많다. 예를 들어 "현재 날씨 보고서" 리소스에 GET 요청을 보내는 클라이언트는 반환된 콘텐츠에 고유한 식별자(예: "20210720T1711 기준 라구나 비치 날씨 보고서")를 원할 수 있다. 이는 시간에 따라 표현이 바뀔 것으로 예상되는 리소스의 콘텐츠를 공유하거나 북마크할 때 유용할 수 있다.

요청 메시지의 경우:

- 요청에 Content-Location 헤더 필드가 있으면, 송신자는 콘텐츠가 Content-Location 필드 값으로 식별되는 리소스의 표현이라고 주장하는 것이다. 하지만 (이 명세가 정의하지 않는) 다른 수단으로 검증할 수 없으면 이런 주장은 신뢰할 수 없다. 그래도 이 정보는 수정 이력 링크에 유용할 수 있다.
- 그렇지 않으면 콘텐츠는 HTTP로 식별되지 않지만, 콘텐츠 자체 안에 더 구체적인 식별자가 제공될 수 있다.

응답 메시지의 경우, 다음 규칙을 일치하는 것이 나올 때까지 순서대로 적용한다.

1. 요청 메서드가 HEAD이거나 응답 상태 코드가 204(No Content) 또는 304(Not Modified)이면, 응답에 콘텐츠가 없다.
2. 요청 메서드가 GET이고 응답 상태 코드가 200(OK)이면, 콘텐츠는 대상 리소스(7.1절)의 표현이다.
3. 요청 메서드가 GET이고 응답 상태 코드가 203(Non-Authoritative Information)이면, 콘텐츠는 중개자가 제공한, 수정되었거나 보강되었을 수 있는 대상 리소스의 표현이다.
4. 요청 메서드가 GET이고 응답 상태 코드가 206(Partial Content)이면, 콘텐츠는 대상 리소스 표현의 하나 이상의 부분이다.
5. 응답에 Content-Location 헤더 필드가 있고 그 필드 값이 대상 URI와 같은 URI에 대한 참조이면, 콘텐츠는 대상 리소스의 표현이다.
6. 응답에 Content-Location 헤더 필드가 있고 그 필드 값이 대상 URI와 다른 URI에 대한 참조이면, 송신자는 콘텐츠가 Content-Location 필드 값으로 식별되는 리소스의 표현이라고 주장하는 것이다. 하지만 (이 명세가 정의하지 않는) 다른 수단으로 검증할 수 없으면 이런 주장은 신뢰할 수 없다.
7. 그렇지 않으면 콘텐츠는 HTTP로 식별되지 않지만, 콘텐츠 자체 안에 더 구체적인 식별자가 제공될 수 있다.

### 6.5. 트레일러 필드

"트레일러 섹션(trailer section)" 안에 있는 필드(5장)를 "트레일러 필드(trailer field)"(구어로는 그냥 "트레일러")라고 한다. 트레일러 필드는 메시지 무결성 검사, 디지털 서명, 전송 지표, 후처리 상태 정보를 제공하는 데 유용할 수 있다.

트레일러 필드는 헤더 섹션이 완료된 시점에 알려진 메시지 의미와 모순되지 않도록, 헤더 섹션의 필드와 따로 처리하고 저장해야 한다. 특정 헤더 필드의 유무는 트레일러를 받기 전에 메시지 전체의 라우팅이나 처리에 대한 선택에 영향을 줄 수 있으며, 그 선택은 나중에 트레일러 필드를 발견했다고 해서 되돌릴 수 없다.

#### 6.5.1. 트레일러 사용 제한

트레일러 섹션은 사용 중인 HTTP 버전이 지원하고 명시적 프레이밍 메커니즘이 이를 가능하게 할 때만 쓸 수 있다. 예를 들어 HTTP/1.1의 청크 전송 코딩은 콘텐츠 뒤에 트레일러 섹션을 보낼 수 있게 한다([HTTP/1.1] 7.1.2절).

메시지 프레이밍, 라우팅, 인증, 요청 수식자, 응답 제어, 콘텐츠 형식을 설명하는 필드처럼, 콘텐츠를 받기 전에 평가해야 하는 많은 필드는 헤더 섹션 밖에서 처리할 수 없다. 송신자는 해당 헤더 필드 이름의 정의가 트레일러로 보내는 것을 허용한다는 것을 알지 못하면 트레일러 필드를 생성해서는 안 된다(MUST NOT).

메시지를 한 프로토콜 버전에서 다른 버전으로 전달하는 중개자는 트레일러 필드를 처리하기 어려울 수 있다. 메시지 전체를 전송 중에 버퍼링할 수 있다면, 일부 중개자는 전달하기 전에 트레일러 필드를 (적절하게) 헤더 섹션에 병합할 수 있다. 하지만 대부분의 경우 트레일러는 그냥 버려진다. 수신자는 해당 헤더 필드 정의를 이해하고, 그 정의가 트레일러 필드 값을 안전하게 병합하는 것을 명시적으로 허용하고 그 방법을 정의하지 않는 한, 트레일러 필드를 헤더 섹션에 병합해서는 안 된다(MUST NOT).

요청의 TE 헤더 필드(10.1.4절)에 키워드 "trailers"가 있으면, 클라이언트가 자신과 모든 다운스트림 클라이언트를 대신해 트레일러 필드를 받아들일 의향이 있다는 뜻이다. 중개자가 보낸 요청이라면, 모든 다운스트림 클라이언트가 전달된 응답의 트레일러 필드를 받아들일 의향이 있다는 뜻이다. "trailers"가 있다고 해서 클라이언트가 응답의 특정 트레일러 필드를 처리한다는 뜻은 아니며, 어떤 클라이언트도 트레일러 섹션을 버리지 않는다는 뜻일 뿐이라는 점에 유의하라.

트레일러 필드는 전송 중에 버려질 가능성이 있으므로, 서버는 사용자 에이전트가 반드시 받아야 한다고 생각하는 트레일러 필드를 생성하지 않아야 한다(SHOULD NOT).

#### 6.5.2. 트레일러 필드 처리

"Trailer" 헤더 필드(6.6.2절)를 보내서 트레일러 섹션에 보내질 가능성이 있는 필드를 알릴 수 있다. 그러면 수신자가 콘텐츠를 처리하기 전에 그 필드를 받을 준비를 할 수 있다. 예를 들어 필드 이름이 콘텐츠를 받는 동안 동적 체크섬을 계산하고, 트레일러 필드 값을 받으면 즉시 확인해야 한다는 것을 나타낸다면 유용할 수 있다.

헤더 필드처럼, 이름이 같은 트레일러 필드는 받은 순서대로 처리된다. 이름이 같은 여러 트레일러 필드 줄은 여러 값을 멤버 리스트로 덧붙인 것과 같은 의미를 가진다. 한 메시지에서 두 번 이상 생성될 수 있는 트레일러 필드는, 각 멤버 값이 받은 필드 줄마다 한 번만 처리되더라도 리스트 기반 필드로 정의해야 한다(MUST).

메시지가 끝나면, 수신자는 받은 트레일러 필드 집합을 헤더 필드와 비슷한(하지만 그와는 별개인) 이름/값 쌍의 데이터 구조로 다룰 수 있다(MAY). 추가 처리 기대 사항이 있다면, 트레일러에 쓰도록 의도된 필드의 필드 명세 안에서 정의할 수 있다.

### 6.6. 메시지 메타데이터

메시지가 언제, 어떻게 생성되었는지처럼 메시지 자체를 설명하는 필드는 요청과 응답 모두에 나타날 수 있다.

#### 6.6.1. Date

"Date" 헤더 필드는 메시지가 생성된 날짜와 시각을 나타내며, [RFC5322] 3.6.1절에 정의된 생성 날짜 필드(orig-date)와 같은 의미를 가진다. 필드 값은 5.6.7절에 정의된 HTTP-date이다.

```
  Date = HTTP-date
```

예시는 다음과 같다.

```
Date: Tue, 15 Nov 1994 08:12:31 GMT
```

Date 헤더 필드를 생성하는 송신자는 필드 값을 메시지 생성 날짜와 시각의 가장 좋은 근삿값으로 생성해야 한다(SHOULD). 이론적으로 날짜는 메시지 콘텐츠를 생성하기 직전의 순간을 나타내야 한다. 실제로는 송신자가 메시지를 생성하는 동안 아무 때나 날짜 값을 생성할 수 있다.

(5.6.7절에 정의된) 시계가 있는 오리진 서버는 모든 2xx(Successful), 3xx(Redirection), 4xx(Client Error) 응답에 Date 헤더 필드를 생성해야 하며(MUST), 1xx(Informational)와 5xx(Server Error) 응답에는 Date 헤더 필드를 생성할 수 있다(MAY).

시계가 없는 오리진 서버는 Date 헤더 필드를 생성해서는 안 된다(MUST NOT).

Date 헤더 필드가 없는 응답 메시지를 받은 시계가 있는 수신자는, 받은 시각을 기록하고, 그 메시지를 캐시하거나 다운스트림으로 전달한다면 메시지의 헤더 섹션에 대응하는 Date 헤더 필드를 덧붙여야 한다(MUST).

Date 헤더 필드 값이 잘못된 응답을 받은 시계가 있는 수신자는 그 값을 응답을 받은 시각으로 바꿀 수 있다(MAY).

사용자 에이전트는 요청에 Date 헤더 필드를 보낼 수 있지만(MAY), 서버에 유용한 정보를 전달한다고 생각하지 않는 한 일반적으로 보내지 않는다. 예를 들어 서버가 사용자 에이전트와 서버 시계의 차이에 따라 사용자의 요청 해석을 조정할 것으로 예상되는 HTTP 맞춤 애플리케이션에서는 Date를 전달할 수 있다.

#### 6.6.2. Trailer

"Trailer" 헤더 필드는 송신자가 그 메시지 안에서 트레일러 필드로 보낼 것으로 예상하는 필드 이름 리스트를 제공한다. 그러면 수신자가 콘텐츠 처리를 시작하기 전에 나타난 메타데이터를 받을 준비를 할 수 있다.

```
  Trailer = #field-name
```

예를 들어 송신자는 콘텐츠를 스트리밍하면서 서명을 계산하고, 최종 서명을 트레일러 필드로 제공한다고 알릴 수 있다. 그러면 수신자는 콘텐츠를 받으면서 같은 검사를 실시간으로 수행할 수 있다.

메시지에 하나 이상의 트레일러 필드를 생성하려는 송신자는, 트레일러에 어떤 필드가 있을 수 있는지 알리기 위해 그 메시지의 헤더 섹션에 Trailer 헤더 필드를 생성해야 한다(SHOULD).

중개자가 전송 중에 트레일러 섹션을 버리면, Trailer 필드는 어떤 메타데이터가 사라졌는지 힌트를 줄 수 있다. 다만 Trailer를 보낸 송신자가 항상 그 이름의 필드를 실제로 보낸다는 보장은 없다.

## 7. HTTP 메시지 라우팅

> 이 번역에는 7.1–7.2절만 포함했다.

HTTP 요청 메시지의 라우팅은 각 클라이언트가 대상 리소스, 클라이언트의 프록시 설정, 인바운드 연결의 수립 또는 재사용을 바탕으로 결정한다. 대응하는 응답의 라우팅은 같은 연결 체인을 따라 클라이언트로 되돌아간다.

### 7.1. 대상 리소스 결정

HTTP는 매우 다양한 애플리케이션에서 쓰이지만, 대부분의 클라이언트는 범용 웹 브라우저와 같은 리소스 식별 메커니즘과 설정 기법에 의존한다. 통신 옵션이 클라이언트 설정에 하드코딩되어 있더라도, 그 결합된 효과를 URI 참조(4.1절)로 생각할 수 있다.

URI 참조를 절대 형태로 해석(resolve)해서 "대상 URI(target URI)"를 얻는다. 프래그먼트 식별자는 클라이언트 쪽 처리를 위해 예약되어 있으므로([URI] 3.5절), 대상 URI에는 참조의 프래그먼트 구성 요소(있다면)가 포함되지 않는다.

"대상 리소스(target resource)"에 어떤 동작을 수행하기 위해, 클라이언트는 수신자가 같은 리소스를 식별할 수 있을 만큼 파싱된 대상 URI의 구성 요소를 담은 요청 메시지를 보낸다. 역사적인 이유로, 통틀어 "요청 대상(request target)"이라고 부르는 파싱된 대상 URI 구성 요소는 메시지 제어 데이터와 Host 헤더 필드(7.2절) 안에 담겨 전송된다.

요청 대상 구성 요소가 메서드별 형태를 갖는 특이한 경우가 두 가지 있다.

- CONNECT(9.3.6절)의 경우, 요청 대상은 터널 목적지의 호스트 이름과 포트 번호를 콜론으로 구분한 것이다.
- OPTIONS(9.3.7절)의 경우, 요청 대상은 별표 하나("*")일 수 있다.

자세한 내용은 각 메서드 정의를 참고하라. 이 형태는 다른 메서드에 써서는 안 된다(MUST NOT).

클라이언트의 요청을 받으면, 서버는 로컬 설정과 들어온 연결의 컨텍스트에 따라 받은 구성 요소로부터 대상 URI를 재구성한다. 이 재구성은 메이저 프로토콜 버전마다 다르다. 예를 들어 [HTTP/1.1] 3.3절은 서버가 HTTP/1.1 요청의 대상 URI를 결정하는 방법을 정의한다.

> **참고:** 이전 명세에서는 재구성된 대상 URI를 "유효 요청 URI(effective request URI)"라는 별개의 개념으로 정의했다.

### 7.2. Host와 :authority

요청의 "Host" 헤더 필드는 대상 URI의 호스트와 포트 정보를 제공해서, 오리진 서버가 여러 호스트 이름에 대한 요청을 처리하면서 리소스를 구별할 수 있게 한다.

HTTP/2[HTTP/2]와 HTTP/3[HTTP/3]에서는 경우에 따라 Host 헤더 필드 대신 요청 제어 데이터의 ":authority" 의사 헤더 필드를 쓴다.

```
  Host = uri-host [ ":" port ] ; Section 4
```

대상 URI의 authority 정보는 요청 처리에 매우 중요하다. 사용자 에이전트는 그 정보를 ":authority" 의사 헤더 필드로 보내지 않는 한, 요청에 Host 헤더 필드를 생성해야 한다(MUST). Host를 보내는 사용자 에이전트는 그 필드를 요청 헤더 섹션의 첫 필드로 보내야 한다(SHOULD).

예를 들어 <http://www.example.org/pub/WWW/>에 대해 오리진 서버로 보내는 GET 요청은 다음과 같이 시작한다.

```
GET /pub/WWW/ HTTP/1.1
Host: www.example.org
```

호스트와 포트 정보는 애플리케이션 수준의 라우팅 메커니즘 역할을 하므로, 공유 캐시를 오염시키거나 요청을 의도하지 않은 서버로 돌리려는 악성 코드의 단골 표적이다. 가로채기 프록시가 가로챈 연결이 그 호스트에 대한 유효한 IP 주소를 향하는지 먼저 확인하지 않고, 호스트와 포트 정보에 의존해 요청을 내부 서버로 돌리거나 공유 캐시의 캐시 키로 쓴다면 특히 취약하다.

## 8. 표현 데이터와 메타데이터

> 이 번역에는 8.1–8.6절만 포함했다.

### 8.1. 표현 데이터

HTTP 메시지와 관련된 표현 데이터는 메시지의 콘텐츠로 제공되거나, 메시지 의미와 대상 URI로 참조된다. 표현 데이터는 표현 메타데이터 헤더 필드가 정의하는 형식과 인코딩으로 되어 있다.

표현 데이터의 데이터 타입은 Content-Type과 Content-Encoding 헤더 필드로 결정된다. 이 두 필드는 순서가 있는 2계층 인코딩 모델을 정의한다.

```
  representation-data := Content-Encoding( Content-Type( data ) )
```

### 8.2. 표현 메타데이터

표현 헤더 필드는 표현에 대한 메타데이터를 제공한다. 메시지에 콘텐츠가 있으면, 표현 헤더 필드는 그 데이터를 해석하는 방법을 설명한다. HEAD 요청에 대한 응답에서는, 같은 요청이 GET이었다면 콘텐츠에 담겼을 표현 데이터를 설명한다.

### 8.3. Content-Type

"Content-Type" 헤더 필드는 관련 표현의 미디어 타입을 나타낸다. 관련 표현은 메시지 의미에 따라 메시지 콘텐츠에 담긴 표현이거나 선택된 표현이다. 나타낸 미디어 타입은 데이터 형식과, Content-Encoding이 나타내는 콘텐츠 코딩을 디코딩한 뒤 받은 메시지 의미의 범위 안에서 수신자가 그 데이터를 어떻게 처리해야 하는지를 모두 정의한다.

```
  Content-Type = media-type
```

미디어 타입은 8.3.1절에 정의되어 있다. 필드 예시는 다음과 같다.

```
Content-Type: text/html; charset=ISO-8859-4
```

콘텐츠를 담은 메시지를 생성하는 송신자는, 담긴 표현의 의도된 미디어 타입을 모르는 경우가 아니면 그 메시지에 Content-Type 헤더 필드를 생성해야 한다(SHOULD). Content-Type 헤더 필드가 없으면, 수신자는 미디어 타입을 "application/octet-stream"([RFC2046] 4.5.1절)으로 가정하거나, 데이터를 살펴보고 타입을 판단할 수 있다(MAY).

실제로는 리소스 소유자가 주어진 표현에 올바른 Content-Type을 제공하도록 오리진 서버를 항상 제대로 설정하지는 않는다. 일부 사용자 에이전트는 콘텐츠를 살펴보고, 특정 경우에 받은 타입을 무시한다(예: [Sniffing] 참고). 이런 "MIME 스니핑"은 데이터에 대해 잘못된 결론을 내릴 위험이 있으며, 사용자를 추가 보안 위험(예: "권한 상승")에 노출시킬 수 있다. 게다가 서로 다른 미디어 타입이 같은 데이터 형식을 공유하고 데이터를 처리하는 방식만 다른 경우가 많은데, 이는 데이터만 살펴봐서는 구별할 수 없다. 스니핑을 구현한다면, 사용자가 이를 끌 수 있는 수단을 제공하는 것이 좋다.

Content-Type은 단일 필드로 정의되어 있지만, 가끔 잘못해서 여러 번 생성되어 결합된 필드 값이 리스트처럼 보이게 된다. 수신자는 흔히 리스트에서 문법적으로 유효한 마지막 멤버를 써서 이 오류를 처리하려 하는데, 구현마다 오류 처리 동작이 다르면 상호운용성과 보안 문제로 이어질 수 있다.

#### 8.3.1. 미디어 타입

HTTP는 개방적이고 확장 가능한 데이터 타입 지정과 타입 협상을 위해 Content-Type(8.3절)과 Accept(12.5.1절) 헤더 필드에서 미디어 타입[RFC2046]을 쓴다. 미디어 타입은 데이터 형식과 다양한 처리 모델, 즉 메시지 컨텍스트에 따라 그 데이터를 처리하는 방법을 모두 정의한다.

```
  media-type = type "/" subtype parameters
  type       = token
  subtype    = token
```

type과 subtype 토큰은 대소문자를 구분하지 않는다.

type/subtype 뒤에는 이름/값 쌍 형태의 세미콜론으로 구분된 매개변수(5.6.6절)가 올 수 있다(MAY). 매개변수의 유무는 미디어 타입 레지스트리의 정의에 따라 미디어 타입 처리에 중요할 수 있다. 매개변수 값은 매개변수 이름의 의미에 따라 대소문자를 구분할 수도, 구분하지 않을 수도 있다.

예를 들어 다음 미디어 타입들은 UTF-8 문자 인코딩 방식으로 인코딩된 HTML 텍스트 데이터를 설명한다는 점에서 동등하지만, 일관성을 위해 첫 번째를 선호한다("charset" 매개변수 값은 [RFC2046] 4.1.2절에서 대소문자를 구분하지 않는다고 정의되어 있다).

```
  text/html;charset=utf-8
  Text/HTML;Charset="utf-8"
  text/html; charset="utf-8"
  text/html;charset=UTF-8
```

미디어 타입은 [BCP13]에 정의된 절차에 따라 IANA에 등록되어야 한다.

#### 8.3.2. Charset

HTTP는 텍스트 표현의 문자 인코딩 방식([RFC6365] 2절)을 나타내거나 협상하기 위해 "charset" 이름을 쓴다. 이 문서가 정의하는 필드에서 charset 이름은 매개변수(Content-Type) 안에 나타나거나, Accept-Encoding의 경우 일반 토큰 형태로 나타난다. 두 경우 모두 charset 이름은 대소문자를 구분하지 않고 비교한다.

charset 이름은 [RFC2978] 2절에 정의된 절차에 따라 IANA "Character Sets" 레지스트리(<https://www.iana.org/assignments/character-sets>)에 등록되어야 한다.

> **참고:** 이론적으로 charset 이름은 [RFC2978] 2.3절에 정의된("mime-charset" ABNF 규칙([Err1912]에서 정정됨)으로 정의된다. 이 규칙은 "token"에 포함되지 않는 두 문자("{"와 "}")를 허용하지만, 이 글을 쓰는 시점에 등록된 charset 이름 중 중괄호를 포함하는 것은 없다([Err5433] 참고).

#### 8.3.3. 멀티파트 타입

MIME은 여러 "multipart" 타입을 제공한다. 이는 하나의 메시지 본문 안에 하나 이상의 표현을 캡슐화한 것이다. 모든 멀티파트 타입은 [RFC2046] 5.1.1절에 정의된 공통 문법을 공유하며, 미디어 타입 값의 일부로 boundary 매개변수를 포함한다. 메시지 본문 자체가 프로토콜 요소이므로, 송신자는 본문 부분 사이의 줄바꿈을 나타낼 때 CRLF만 생성해야 한다(MUST).

HTTP 메시지 프레이밍은 멀티파트 경계(boundary)를 메시지 본문 길이의 표시로 쓰지 않는다. 다만 콘텐츠를 생성하거나 처리하는 구현은 이를 쓸 수 있다. 예를 들어 "multipart/form-data" 타입은 [RFC7578]에 설명된 대로 요청에서 폼 데이터를 전달하는 데 자주 쓰이고, "multipart/byteranges" 타입은 일부 206(Partial Content) 응답에서 쓰도록 이 명세가 정의한다(15.3.7절 참고).

### 8.4. Content-Encoding

"Content-Encoding" 헤더 필드는 미디어 타입에 본래 포함된 것 외에 표현에 어떤 콘텐츠 코딩이 적용되었는지, 따라서 Content-Type 헤더 필드가 가리키는 미디어 타입의 데이터를 얻으려면 어떤 디코딩 메커니즘을 적용해야 하는지를 나타낸다. Content-Encoding은 주로 표현의 데이터를 기반 미디어 타입의 정체성을 잃지 않고 압축할 수 있게 하는 데 쓰인다.

```
  Content-Encoding = #content-coding
```

사용 예시는 다음과 같다.

```
Content-Encoding: gzip
```

표현에 하나 이상의 인코딩이 적용되었다면, 인코딩을 적용한 송신자는 적용한 순서대로 콘텐츠 코딩을 나열한 Content-Encoding 헤더 필드를 생성해야 한다(MUST). "identity"라는 이름의 코딩은 Accept-Encoding에서의 특별한 역할을 위해 예약되어 있으므로 포함하지 않아야 한다는(SHOULD NOT) 점에 유의하라.

인코딩 매개변수에 대한 추가 정보는 이 명세가 정의하지 않는 다른 헤더 필드로 제공할 수 있다.

Transfer-Encoding([HTTP/1.1] 6.1절)과 달리, Content-Encoding에 나열된 코딩은 표현의 특성이다. 표현은 코딩된 형태로 정의되며, 메타데이터 정의에서 따로 언급하지 않는 한 표현에 대한 다른 모든 메타데이터는 코딩된 형태에 관한 것이다. 보통 표현은 렌더링하거나 그와 비슷하게 쓰기 직전에만 디코딩된다.

항상 압축되는 데이터 형식처럼 미디어 타입에 본래의 인코딩이 포함되어 있다면, 그 인코딩이 콘텐츠 코딩 중 하나와 우연히 같은 알고리즘이더라도 Content-Encoding에 다시 적지 않는다. 그런 콘텐츠 코딩은 어떤 기이한 이유로 표현을 만들 때 두 번째로 적용된 경우에만 나열된다. 마찬가지로 오리진 서버는 코딩이 Content-Type의 일부로 정의되는지 Content-Encoding의 일부로 정의되는지만 다른 여러 표현으로 같은 데이터를 공개할 수 있다. 일부 사용자 에이전트는 각 응답을 다르게 처리하기 때문이다(예: 콘텐츠를 자동으로 압축 해제하고 렌더링하는 대신 "다른 이름으로 저장..." 대화 상자를 연다).

요청 메시지의 표현에 받아들일 수 없는 콘텐츠 코딩이 있으면, 오리진 서버는 415(Unsupported Media Type) 상태 코드로 응답할 수 있다(MAY).

#### 8.4.1. 콘텐츠 코딩

콘텐츠 코딩 값은 표현에 적용되었거나 적용할 수 있는 인코딩 변환을 나타낸다. 콘텐츠 코딩은 주로 기반 미디어 타입의 정체성을 잃지 않고 정보 손실 없이 표현을 압축하거나 다른 유용한 방식으로 변환하는 데 쓰인다. 표현은 코딩된 형태로 저장되어 그대로 전송되고, 최종 수신자만 디코딩하는 경우가 많다.

```
  content-coding   = token
```

모든 콘텐츠 코딩은 대소문자를 구분하지 않으며, 16.6절에 설명된 대로 "HTTP Content Coding Registry"에 등록되어야 한다.

콘텐츠 코딩 값은 Accept-Encoding(12.5.3절)과 Content-Encoding(8.4절) 헤더 필드에서 쓰인다.

##### 8.4.1.1. Compress 코딩

"compress" 코딩은 UNIX 파일 압축 프로그램 "compress"가 흔히 만들어 내는 적응형 Lempel-Ziv-Welch(LZW) 코딩[Welch]이다. 수신자는 "x-compress"를 "compress"와 동등하게 여겨야 한다(SHOULD).

##### 8.4.1.2. Deflate 코딩

"deflate" 코딩은 Lempel-Ziv(LZ77) 압축 알고리즘과 허프만 코딩을 조합해 쓰는 "deflate" 압축 데이터 스트림[RFC1951]을 담은 "zlib" 데이터 형식[RFC1950]이다.

> **참고:** 일부 비준수 구현은 "deflate" 압축 데이터를 zlib 래퍼 없이 보낸다.

##### 8.4.1.3. Gzip 코딩

"gzip" 코딩은 gzip 파일 압축 프로그램[RFC1952]이 흔히 만들어 내는, 32비트 순환 중복 검사(CRC)가 붙은 LZ77 코딩이다. 수신자는 "x-gzip"을 "gzip"과 동등하게 여겨야 한다(SHOULD).

### 8.5. Content-Language

"Content-Language" 헤더 필드는 표현이 대상으로 하는 독자의 자연어(들)를 설명한다. 이것이 표현 안에서 쓰인 모든 언어와 같지 않을 수 있다는 점에 유의하라.

```
  Content-Language = #language-tag
```

언어 태그는 8.5.1절에 정의되어 있다. Content-Language의 주된 목적은 사용자가 자신이 선호하는 언어에 따라 표현을 식별하고 구별할 수 있게 하는 것이다. 그래서 콘텐츠가 덴마크어를 읽는 독자만을 위한 것이라면 적절한 필드는 다음과 같다.

```
Content-Language: da
```

Content-Language를 지정하지 않으면, 기본적으로 콘텐츠가 모든 언어의 독자를 위한 것으로 본다. 이는 송신자가 콘텐츠를 특정 자연어에 한정된 것으로 보지 않거나, 어떤 언어를 위한 것인지 모른다는 뜻일 수 있다.

여러 독자를 위한 콘텐츠에는 여러 언어를 나열할 수 있다(MAY). 예를 들어 원본 마오리어판과 영어판을 동시에 제시하는 "와이탕이 조약"의 판본에는 다음이 필요하다.

```
Content-Language: mi, en
```

하지만 표현 안에 여러 언어가 있다고 해서 여러 언어 독자를 위한 것은 아니다. 예를 들어 "라틴어 첫걸음" 같은 초급 언어 입문서는 분명히 영어를 읽는 독자를 위한 것이다. 이 경우 Content-Language에는 "en"만 포함하는 것이 맞다.

Content-Language는 어떤 미디어 타입에든 적용할 수 있다(MAY). 텍스트 문서에만 한정되지 않는다.

#### 8.5.1. 언어 태그

[RFC5646]에 정의된 언어 태그는 사람이 다른 사람에게 정보를 전달하기 위해 말하거나, 쓰거나, 다른 방식으로 전달하는 자연어를 식별한다. 컴퓨터 언어는 명시적으로 제외된다.

HTTP는 Accept-Language와 Content-Language 헤더 필드에서 언어 태그를 쓴다. Accept-Language는 12.5.4절에 정의된 더 넓은 language-range 규칙을 쓰는 반면, Content-Language는 아래 정의된 language-tag 규칙을 쓴다.

```
  language-tag = <Language-Tag, see [RFC5646], Section 2.1>
```

언어 태그는 대소문자를 구분하지 않는 하나 이상의 하위 태그를 하이픈 문자("-", %x2D)로 구분한 것이다. 대부분의 경우 언어 태그는 관련 언어의 넓은 계열을 식별하는 주 언어 하위 태그(예: "en" = 영어)와, 선택적으로 그 언어의 범위를 구체화하거나 좁히는 일련의 하위 태그(예: "en-CA" = 캐나다에서 쓰는 영어)로 이루어진다. 언어 태그 안에는 공백이 허용되지 않는다. 태그 예시는 다음과 같다.

```
  fr, en-US, es-419, az-Arab, x-pig-latin, man-Nkoo-GN
```

자세한 내용은 [RFC5646]을 참고하라.

### 8.6. Content-Length

"Content-Length" 헤더 필드는 관련 표현의 데이터 길이를 10진수의 음이 아닌 정수 옥텟 수로 나타낸다. 표현을 콘텐츠로 전송할 때, Content-Length는 특히 담긴 데이터의 양을 가리키므로 프레이밍을 구분하는 데 쓸 수 있다(예: [HTTP/1.1] 6.2절). 그 밖의 경우 Content-Length는 선택된 표현의 현재 길이를 나타내며, 수신자가 전송 시간을 추정하거나 이전에 저장한 표현과 비교하는 데 쓸 수 있다.

```
  Content-Length = 1*DIGIT
```

예시는 다음과 같다.

```
Content-Length: 3495
```

사용자 에이전트는 메서드가 담긴 콘텐츠에 대한 의미를 정의하고 Transfer-Encoding을 보내지 않을 때 요청에 Content-Length를 보내야 한다(SHOULD). 예를 들어 사용자 에이전트는 보통 POST 요청에 값이 0(빈 콘텐츠를 나타냄)이더라도 Content-Length를 보낸다. 요청 메시지에 콘텐츠가 없고 메서드 의미가 그런 데이터를 예상하지 않을 때, 사용자 에이전트는 Content-Length 헤더 필드를 보내지 않아야 한다(SHOULD NOT).

서버는 HEAD 요청(9.3.2절)에 대한 응답에 Content-Length 헤더 필드를 보낼 수 있다(MAY). 서버는 같은 요청이 GET 메서드를 썼다면 응답 콘텐츠로 보냈을 옥텟 수의 10진수와 필드 값이 같지 않으면, 그런 응답에 Content-Length를 보내서는 안 된다(MUST NOT).

서버는 조건부 GET 요청(15.4.5절)에 대한 304(Not Modified) 응답에 Content-Length 헤더 필드를 보낼 수 있다(MAY). 서버는 같은 요청에 대한 200(OK) 응답의 콘텐츠로 보냈을 옥텟 수의 10진수와 필드 값이 같지 않으면, 그런 응답에 Content-Length를 보내서는 안 된다(MUST NOT).

서버는 상태 코드가 1xx(Informational)나 204(No Content)인 응답에 Content-Length 헤더 필드를 보내서는 안 된다(MUST NOT). 서버는 CONNECT 요청(9.3.6절)에 대한 2xx(Successful) 응답에 Content-Length 헤더 필드를 보내서는 안 된다(MUST NOT).

위에서 정의한 경우를 제외하고, Transfer-Encoding이 없을 때 오리진 서버는 헤더 섹션 전체를 보내기 전에 콘텐츠 크기를 안다면 Content-Length 헤더 필드를 보내야 한다(SHOULD). 그러면 다운스트림 수신자가 전송 진행 상황을 측정하고, 받은 메시지가 언제 완료되는지 알고, 연결을 다른 요청에 재사용할 수 있다.

0 이상인 모든 Content-Length 필드 값은 유효하다. 콘텐츠 길이에 미리 정해진 제한이 없으므로, 수신자는 매우 큰 10진수가 올 수 있음을 예상하고, 정수 변환 오버플로로 인한 파싱 오류나 정수 변환으로 인한 정밀도 손실을 막아야 한다(MUST)(17.5절).

HTTP/1.1에서는 Content-Length가 메시지 구분에 쓰이므로, 인접 연결이 HTTP/1.1을 쓰지 않더라도 그 필드 값이 다운스트림 수신자의 메시지 파싱 방식에 영향을 줄 수 있다. 다운스트림 중개자가 메시지를 전달할 때, 받은 메시지 프레이밍과 맞지 않는 Content-Length 필드 값은 요청 스머글링이나 응답 분할로 인한 보안 실패를 일으킬 수 있다.

그래서 송신자는 잘못된 것으로 알려진 Content-Length 헤더 필드 값을 가진 메시지를 전달해서는 안 된다(MUST NOT).

마찬가지로 송신자는 위 ABNF에 맞지 않는 Content-Length 헤더 필드 값을 가진 메시지를 전달해서는 안 된다(MUST NOT). 단, 한 가지 예외가 있다. 같은 10진수 값이 쉼표로 구분된 리스트로 반복된 Content-Length 헤더 필드 값(예: "Content-Length: 42, 42")을 받은 수신자는, 메시지를 유효하지 않은 것으로 거절하거나, 그 유효하지 않은 필드 값을 10진수 값 하나로 바꿀 수 있다(MAY). 이는 업스트림 메시지 처리기가 중복을 생성하거나 결합했다는 뜻일 가능성이 높기 때문이다.

## 9. 메서드

### 9.1. 개요

요청 메서드 토큰은 요청 의미의 주된 출처이다. 클라이언트가 이 요청을 보낸 목적과, 클라이언트가 성공적인 결과로 무엇을 기대하는지를 나타낸다.

요청 메서드의 의미는 요청에 있는 일부 헤더 필드의 의미로 더 구체화될 수 있다. 단, 그 추가 의미가 메서드와 충돌하지 않아야 한다. 예를 들어 클라이언트는 조건부 요청 헤더 필드(13.1절)를 보내서, 요청한 동작을 대상 리소스의 현재 상태에 따라 조건부로 만들 수 있다.

HTTP는 분산 객체 시스템의 인터페이스로 쓸 수 있도록 설계되었다. 요청 메서드는 원격 메서드 호출을 식별된 객체에 보내는 것과 거의 같은 방식으로, 대상 리소스에 적용할 동작을 호출한다.

```
  method = token
```

메서드 토큰은 대소문자를 구분한다. 메서드 이름이 대소문자를 구분하는 객체 기반 시스템으로 가는 게이트웨이로 쓰일 수 있기 때문이다. 관례상 표준화된 메서드는 모두 대문자 US-ASCII 문자로 정의된다.

분산 객체와 달리 HTTP의 표준화된 요청 메서드는 리소스마다 다르지 않다. 균일한 인터페이스가 네트워크 기반 시스템에서 더 나은 가시성과 재사용성을 제공하기 때문이다[REST]. 표준화된 메서드는 일단 정의되면 어떤 리소스에 적용하든 같은 의미를 가져야 한다. 다만 그 의미를 구현하거나 허용할지는 각 리소스가 스스로 정한다.

이 명세는 HTTP에서 흔히 쓰이는 여러 표준화된 메서드를 정의하며, 다음 표에 정리되어 있다.

| 메서드 이름 | 설명 | 절 |
|---|---|---|
| GET | 대상 리소스의 현재 표현을 전송한다. | 9.3.1 |
| HEAD | GET과 같지만, 응답 콘텐츠를 전송하지 않는다. | 9.3.2 |
| POST | 요청 콘텐츠에 대해 리소스별 처리를 수행한다. | 9.3.3 |
| PUT | 대상 리소스의 모든 현재 표현을 요청 콘텐츠로 교체한다. | 9.3.4 |
| DELETE | 대상 리소스의 모든 현재 표현을 제거한다. | 9.3.5 |
| CONNECT | 대상 리소스가 식별하는 서버로 터널을 수립한다. | 9.3.6 |
| OPTIONS | 대상 리소스의 통신 옵션을 설명한다. | 9.3.7 |
| TRACE | 대상 리소스까지의 경로를 따라 메시지 루프백 테스트를 수행한다. | 9.3.8 |

<p align="center">표 4</p>

모든 범용 서버는 GET과 HEAD 메서드를 지원해야 한다(MUST). 그 밖의 메서드는 모두 선택 사항(OPTIONAL)이다.

대상 리소스가 허용하는 메서드 집합은 Allow 헤더 필드(10.2.1절)에 나열할 수 있다. 하지만 허용되는 메서드 집합은 동적으로 바뀔 수 있다. 인식하지 못했거나 구현하지 않은 요청 메서드를 받은 오리진 서버는 501(Not Implemented) 상태 코드로 응답해야 한다(SHOULD). 인식하고 구현했지만 대상 리소스에 허용되지 않은 요청 메서드를 받은 오리진 서버는 405(Method Not Allowed) 상태 코드로 응답해야 한다(SHOULD).

이 명세의 범위 밖에서 HTTP에 쓰도록 명세된 추가 메서드들이 있다. 이런 메서드는 모두 16.1절에 설명된 대로 "Hypertext Transfer Protocol (HTTP) Method Registry"에 등록되어야 한다.

### 9.2. 메서드의 공통 속성

#### 9.2.1. 안전한 메서드

요청 메서드의 정의된 의미가 본질적으로 읽기 전용이라면, 즉 대상 리소스에 안전한 메서드를 적용한 결과로 클라이언트가 오리진 서버의 상태 변경을 요청하지도 기대하지도 않는다면, 그 메서드를 "안전하다(safe)"고 본다. 마찬가지로 안전한 메서드를 합리적으로 사용하면 오리진 서버에 해를 끼치거나, 재산을 잃게 하거나, 비정상적인 부담을 주지 않을 것으로 예상한다.

안전한 메서드의 이 정의는 구현이 안전한 메서드를 호출하는 동안 잠재적으로 해로운 동작, 완전히 읽기 전용이 아닌 동작, 또는 부작용을 일으키는 동작을 포함하는 것을 막지 않는다. 중요한 것은 클라이언트가 그 추가 동작을 요청하지 않았고, 그에 대한 책임을 질 수 없다는 점이다. 예를 들어 대부분의 서버는 메서드와 상관없이 모든 응답이 완료될 때마다 요청 정보를 접근 로그 파일에 덧붙인다. 로그 저장소가 가득 차서 서버가 실패할 수 있더라도 이는 안전한 것으로 본다. 마찬가지로 웹에서 광고를 선택해서 시작된 안전한 요청은 종종 광고 계정에 요금을 부과하는 부작용을 낳는다.

이 명세가 정의하는 요청 메서드 중 GET, HEAD, OPTIONS, TRACE가 안전한 메서드로 정의된다.

안전한 메서드와 안전하지 않은 메서드를 구분하는 목적은, 자동화된 검색 프로세스(스파이더)와 캐시 성능 최적화(미리 가져오기)가 해를 끼칠 걱정 없이 동작할 수 있게 하는 것이다. 또한 사용자 에이전트가 신뢰할 수 없을 수도 있는 콘텐츠를 처리할 때, 안전하지 않은 메서드의 자동 사용에 적절한 제약을 걸 수 있게 한다.

사용자 에이전트는 사용자에게 가능한 동작을 제시할 때 안전한 메서드와 안전하지 않은 메서드를 구분해서, 사용자가 안전하지 않은 동작을 요청하기 전에 이를 알 수 있게 해야 한다(SHOULD).

대상 URI 안의 매개변수가 동작을 선택하는 효과를 갖도록 리소스가 만들어져 있다면, 그 동작이 요청 메서드의 의미와 일치하도록 보장하는 것은 리소스 소유자의 책임이다. 예를 들어 웹 기반 콘텐츠 편집 소프트웨어는 "page?do=delete"처럼 쿼리 매개변수 안에 동작을 넣는 경우가 흔하다. 그런 리소스의 목적이 안전하지 않은 동작을 수행하는 것이라면, 리소스 소유자는 안전한 요청 메서드로 접근했을 때 그 동작을 비활성화하거나 허용하지 않아야 한다(MUST). 그렇지 않으면 링크 유지 관리, 미리 가져오기, 검색 색인 구축 등을 위해 자동화된 프로세스가 모든 URI 참조에 GET을 수행할 때 불행한 부작용이 생긴다.

#### 9.2.2. 멱등 메서드

어떤 메서드로 같은 요청을 여러 번 보냈을 때 서버에 의도된 효과가 그런 요청을 한 번 보냈을 때와 같다면, 그 요청 메서드를 "멱등(idempotent)"이라고 본다. 이 명세가 정의하는 요청 메서드 중 PUT, DELETE, 그리고 안전한 요청 메서드가 멱등이다.

안전함의 정의처럼, 멱등 속성은 사용자가 요청한 것에만 적용된다. 서버는 각 요청을 따로 로깅하거나, 수정 이력을 보관하거나, 각 멱등 요청에 대해 멱등이 아닌 다른 부작용을 구현해도 된다.

멱등 메서드를 구분하는 이유는, 클라이언트가 서버의 응답을 읽기 전에 통신 장애가 발생하면 요청을 자동으로 반복할 수 있기 때문이다. 예를 들어 클라이언트가 PUT 요청을 보냈는데 응답을 받기 전에 하위 연결이 닫히면, 클라이언트는 새 연결을 수립하고 멱등 요청을 재시도할 수 있다. 원래 요청이 성공했더라도 요청을 반복하면 같은 의도된 효과를 낸다는 것을 알기 때문이다. 다만 응답은 다를 수 있다.

클라이언트는 메서드와 상관없이 요청 의미가 실제로 멱등임을 알 수단이 있거나, 원래 요청이 적용되지 않았음을 감지할 수단이 없다면, 멱등이 아닌 메서드의 요청을 자동으로 재시도하지 않아야 한다(SHOULD NOT).

예를 들어 사용자 에이전트는 (설계나 설정을 통해) 그 리소스에 대한 요청이 안전하다는 것을 안다면 POST 요청을 자동으로 반복할 수 있다. 마찬가지로 버전 관리 저장소를 다루도록 특별히 설계된 사용자 에이전트는, 연결이 실패한 뒤 대상 리소스의 리비전을 확인하고, 부분적으로 적용된 변경을 되돌리거나 고친 다음, 실패한 요청을 자동으로 재시도해서 부분 실패 상황에서 복구할 수 있을 것이다.

일부 클라이언트는 더 위험한 방식을 택해서, 자동 재시도가 가능한 때를 추측하려 한다. 예를 들어 클라이언트는 응답의 어떤 부분도 받기 전에 하위 전송 연결이 닫혔다면, 특히 유휴 지속 연결을 썼다면, POST 요청을 자동으로 재시도할 수 있다.

프록시는 멱등이 아닌 요청을 자동으로 재시도해서는 안 된다(MUST NOT). 클라이언트는 실패한 자동 재시도를 다시 자동으로 재시도하지 않아야 한다(SHOULD NOT).

#### 9.2.3. 메서드와 캐싱

캐시가 응답을 저장하고 사용하려면, 관련 메서드가 캐싱을 명시적으로 허용하고 어떤 조건에서 응답을 이후 요청에 쓸 수 있는지 자세히 설명해야 한다. 그렇게 하지 않는 메서드 정의는 캐시될 수 없다. 추가 요구 사항은 [CACHING]을 참고하라.

이 명세는 GET, HEAD, POST에 대한 캐싱 의미를 정의하지만, 압도적 다수의 캐시 구현은 GET과 HEAD만 지원한다.

### 9.3. 메서드 정의

#### 9.3.1. GET

GET 메서드는 대상 리소스의 현재 선택된 표현의 전송을 요청한다. 성공한 응답은 대상 URI가 식별하는 "동일성(sameness)"의 성질을 반영한다([URI] 1.2.2절). 그래서 HTTP로 식별 가능한 정보를 가져오는 것은 보통 200(OK) 응답으로 그 정보를 제공할 가능성이 있는 식별자에 GET 요청을 보내는 방식으로 이루어진다.

GET은 정보 검색의 주된 메커니즘이며 거의 모든 성능 최적화의 초점이다. 중요한 리소스마다 URI를 만드는 애플리케이션은 그런 최적화의 혜택을 받으면서 다른 애플리케이션이 그 리소스를 재사용할 수 있게 하고, 웹의 확장을 더욱 촉진하는 네트워크 효과를 만든다.

리소스 식별자를 원격 파일 시스템 경로 이름으로, 표현을 그런 파일 내용의 사본으로 생각하고 싶을 수 있다. 실제로 많은 리소스가 그렇게 구현되어 있다(관련 보안 고려 사항은 17.3절 참고). 하지만 실제로 그런 제한은 없다.

리소스의 HTTP 인터페이스는 콘텐츠 객체의 트리, 여러 데이터베이스 레코드에 대한 프로그래밍된 뷰, 또는 다른 정보 시스템으로 가는 게이트웨이로 구현될 가능성도 그만큼 높다. URI 매핑 메커니즘이 파일 시스템에 묶여 있더라도, 오리진 서버는 파일을 직접 전송하는 대신 요청을 입력으로 파일을 실행하고 그 출력을 표현으로 보내도록 설정될 수 있다. 어쨌든 각 리소스 식별자가 어떤 구현에 대응하고, 그 구현이 대상 리소스의 현재 표현을 어떻게 선택해서 보내는지는 오리진 서버만 알면 된다.

클라이언트는 요청에 Range 헤더 필드(14.2절)를 보내서 GET의 의미를 선택된 표현의 일부만 전송을 요청하는 "범위 요청(range request)"으로 바꿀 수 있다.

요청 메시지 프레이밍은 사용하는 메서드와 독립적이지만, GET 요청에서 받은 콘텐츠에는 일반적으로 정의된 의미가 없고, 요청의 의미나 대상을 바꿀 수 없으며, 요청 스머글링 공격([HTTP/1.1] 11.2절)이 될 가능성 때문에 일부 구현이 요청을 거절하고 연결을 닫게 만들 수 있다. 클라이언트는 그런 요청에 목적이 있고 적절히 지원될 것이라고 대역 안팎에서 미리 알린 오리진 서버에 직접 보내는 경우가 아니면, GET 요청에 콘텐츠를 생성하지 않아야 한다(SHOULD NOT). HTTP 통신 참여자는 요청 체인상의 중개자를 모르는 경우가 많으므로, 오리진 서버는 콘텐츠를 받기 위해 비공개 합의에 의존하지 않아야 한다(SHOULD NOT).

GET 요청에 대한 응답은 캐시 가능하다. Cache-Control 헤더 필드([CACHING] 5.2절)가 달리 나타내지 않는 한, 캐시는 이를 이후의 GET과 HEAD 요청에 응답하는 데 쓸 수 있다(MAY).

GET을 쓰는 폼의 쿼리 필드처럼 사용자가 제공한 정보로 대상 URI를 구성하는 메커니즘으로 정보 검색을 수행할 때, URI 안에 공개하기에 적절하지 않은 민감한 데이터가 제공될 수 있다(17.9절 참고). 어떤 경우에는 그런 정보가 드러나지 않도록 데이터를 걸러내거나 변환할 수 있다. 다른 경우, 특히 응답을 캐시해서 얻는 이점이 없을 때는 GET 대신 POST 메서드(9.3.3절)를 쓰면 그런 정보를 대상 URI 대신 요청 콘텐츠에 담아 전송할 수 있다.

#### 9.3.2. HEAD

HEAD 메서드는 서버가 응답에 콘텐츠를 보내서는 안 된다는(MUST NOT) 점을 제외하면 GET과 같다. HEAD는 표현 데이터를 전송하지 않고 선택된 표현에 대한 메타데이터를 얻는 데 쓰이며, 하이퍼텍스트 링크를 테스트하거나 최근 수정 사항을 찾기 위해 자주 쓰인다.

서버는 HEAD 요청에 대한 응답으로, 요청 메서드가 GET이었다면 보냈을 것과 같은 헤더 필드를 보내야 한다(SHOULD). 하지만 서버는 콘텐츠를 생성하는 동안에만 값이 정해지는 헤더 필드는 생략할 수 있다(MAY). 예를 들어 일부 서버는 작은 응답을 더 효율적으로 구분하거나 콘텐츠 선택에 관한 결정을 늦게 내리기 위해, 최소한의 데이터가 생성될 때까지 GET에 대한 동적 응답을 버퍼링한다. 그런 GET 응답에는 HEAD 응답에서는 생성되지 않는 Content-Length와 Vary 필드 등이 들어 있을 수 있다. HEAD는 보통 효율을 위해 요청되므로, 이런 사소한 불일치가 HEAD 요청을 위해 콘텐츠를 생성했다가 버리는 것보다 낫다고 본다.

요청 메시지 프레이밍은 사용하는 메서드와 독립적이지만, HEAD 요청에서 받은 콘텐츠에는 일반적으로 정의된 의미가 없고, 요청의 의미나 대상을 바꿀 수 없으며, 요청 스머글링 공격([HTTP/1.1] 11.2절)이 될 가능성 때문에 일부 구현이 요청을 거절하고 연결을 닫게 만들 수 있다. 클라이언트는 그런 요청에 목적이 있고 적절히 지원될 것이라고 대역 안팎에서 미리 알린 오리진 서버에 직접 보내는 경우가 아니면, HEAD 요청에 콘텐츠를 생성하지 않아야 한다(SHOULD NOT). HTTP 통신 참여자는 요청 체인상의 중개자를 모르는 경우가 많으므로, 오리진 서버는 콘텐츠를 받기 위해 비공개 합의에 의존하지 않아야 한다(SHOULD NOT).

HEAD 요청에 대한 응답은 캐시 가능하다. Cache-Control 헤더 필드([CACHING] 5.2절)가 달리 나타내지 않는 한, 캐시는 이를 이후의 HEAD 요청에 응답하는 데 쓸 수 있다(MAY). HEAD 응답은 이전에 캐시된 GET 응답에도 영향을 줄 수 있다. [CACHING] 4.3.5절을 참고하라.

#### 9.3.3. POST

POST 메서드는 대상 리소스가 요청에 담긴 표현을 리소스 고유의 의미에 따라 처리하도록 요청한다. 예를 들어 POST는 (여러 용도 중에서도) 다음 기능에 쓰인다.

- HTML 폼에 입력한 필드 같은 데이터 블록을 데이터 처리 프로세스에 제공한다.
- 게시판, 뉴스그룹, 메일링 리스트, 블로그, 또는 그와 비슷한 글 모음에 메시지를 게시한다.
- 오리진 서버가 아직 식별하지 않은 새 리소스를 만든다.
- 리소스의 기존 표현에 데이터를 덧붙인다.

오리진 서버는 POST 요청 처리 결과에 따라 적절한 상태 코드를 골라 응답 의미를 나타낸다. 이 명세가 정의하는 거의 모든 상태 코드를 POST에 대한 응답으로 받을 수 있다(예외는 206(Partial Content), 304(Not Modified), 416(Range Not Satisfiable)이다).

POST 요청을 성공적으로 처리한 결과 오리진 서버에 하나 이상의 리소스가 만들어졌다면, 오리진 서버는 만들어진 주 리소스의 식별자를 제공하는 Location 헤더 필드(10.2.2절)와, 새 리소스를 참조하면서 요청의 상태를 설명하는 표현을 담은 201(Created) 응답을 보내야 한다(SHOULD).

POST 요청에 대한 응답은 명시적인 신선도 정보([CACHING] 4.2.1절 참고)와 POST의 대상 URI와 같은 값을 가진 Content-Location 헤더 필드(8.7절)를 포함할 때만 캐시 가능하다. 캐시된 POST 응답은 이후의 GET이나 HEAD 요청에 응답하는 데 재사용할 수 있다. 반면 POST는 안전하지 않을 수 있으므로, 캐시된 POST 응답으로 POST 요청에 응답할 수는 없다. [CACHING] 4장을 참고하라.

POST 처리 결과가 기존 리소스의 표현과 동등하다면, 오리진 서버는 Location 필드에 기존 리소스의 식별자를 담은 303(See Other) 응답을 보내서 사용자 에이전트를 그 리소스로 리다이렉트할 수 있다(MAY). 이렇게 하면 사용자 에이전트에 리소스 식별자를 제공하고, 공유 캐싱에 더 적합한 메서드로 표현을 전송할 수 있다는 이점이 있다. 다만 사용자 에이전트가 그 표현을 아직 캐시하지 않았다면 요청이 하나 더 드는 비용이 있다.

#### 9.3.4. PUT

PUT 메서드는 대상 리소스의 상태를 요청 메시지 콘텐츠에 담긴 표현이 정의하는 상태로 만들거나 교체하도록 요청한다. 주어진 표현의 PUT이 성공했다면, 같은 대상 리소스에 대한 이후의 GET이 200(OK) 응답으로 동등한 표현을 보낼 것이라고 짐작할 수 있다. 하지만 그런 상태 변경을 관찰할 수 있다는 보장은 없다. 이후의 GET을 받기 전에 다른 사용자 에이전트가 대상 리소스에 동시에 작업하거나, 오리진 서버가 동적으로 처리할 수 있기 때문이다. 성공한 응답은 오리진 서버가 처리한 시점에 사용자 에이전트의 의도가 달성되었다는 것만 뜻한다.

대상 리소스에 현재 표현이 없고 PUT이 성공적으로 하나를 만들었다면, 오리진 서버는 201(Created) 응답을 보내서 사용자 에이전트에 알려야 한다(MUST). 대상 리소스에 현재 표현이 있고 그 표현이 담긴 표현의 상태에 따라 성공적으로 수정되었다면, 오리진 서버는 요청의 성공적인 완료를 나타내기 위해 200(OK)이나 204(No Content) 응답을 보내야 한다(MUST).

오리진 서버는 PUT 표현이 대상 리소스에 대해 설정된 제약과 일치하는지 확인해야 한다(SHOULD). 예를 들어 오리진 서버가 URI를 바탕으로 리소스의 표현 메타데이터를 정한다면, 성공한 PUT 요청에서 받은 콘텐츠가 그 메타데이터와 일치하도록 보장해야 한다. PUT 표현이 대상 리소스와 일치하지 않으면, 오리진 서버는 표현을 변환하거나 리소스 설정을 바꿔서 일치시키거나, 표현이 왜 적합하지 않은지 설명할 충분한 정보를 담은 적절한 오류 메시지로 응답해야 한다(SHOULD). 409(Conflict)나 415(Unsupported Media Type) 상태 코드를 권장하며, 후자는 Content-Type 값에 대한 제약에 특화된 것이다.

예를 들어 대상 리소스가 항상 Content-Type "text/html"을 갖도록 설정되어 있는데 PUT으로 보내는 표현의 Content-Type이 "image/jpeg"이라면, 오리진 서버는 다음 중 하나를 해야 한다.

a. 새 미디어 타입을 반영하도록 대상 리소스를 다시 설정한다.
b. 새 리소스 상태로 저장하기 전에 PUT 표현을 리소스와 일치하는 형식으로 변환한다.
c. 대상 리소스가 "text/html"로 제한되어 있음을 나타내는 415(Unsupported Media Type) 응답으로 요청을 거절한다. 새 표현에 적합한 대상이 될 다른 리소스로 가는 링크를 포함할 수도 있다.

HTTP는 사용자 에이전트 요청의 의도와 오리진 서버 응답의 의미로 표현할 수 있는 것 이상으로, PUT 메서드가 오리진 서버의 상태에 정확히 어떤 영향을 주는지 정의하지 않는다. HTTP로 제공되는 인터페이스 외에 리소스가 어떤 의미에서든 무엇일 수 있는지 정의하지 않는다. 리소스 상태가 어떻게 "저장"되는지, 리소스 상태가 바뀌면 그 저장소가 어떻게 바뀌는지, 오리진 서버가 리소스 상태를 어떻게 표현으로 바꾸는지도 정의하지 않는다. 일반적으로 리소스 인터페이스 뒤의 모든 구현 세부 사항은 서버가 의도적으로 숨긴다.

이는 헤더와 트레일러 필드를 저장하는 방식에도 해당한다. Content-Type 같은 흔한 헤더 필드는 보통 저장되었다가 이후의 GET 요청에 반환되지만, 헤더와 트레일러 필드의 처리는 요청을 받은 리소스마다 다르다. 그래서 오리진 서버는 PUT 요청에서 받은 인식하지 못한 헤더와 트레일러 필드를 무시해야 한다(SHOULD). 즉, 리소스 상태의 일부로 저장하지 않아야 한다.

오리진 서버는 요청의 표현 데이터가 콘텐츠에 아무 변환도 적용되지 않은 채 저장되었고(즉, 리소스의 새 표현 데이터가 PUT 요청에서 받은 콘텐츠와 동일하고), 검증자 필드 값이 새 표현을 반영하는 경우가 아니면, PUT에 대한 성공 응답에 ETag나 Last-Modified 같은 검증자 필드(8.8절)를 보내서는 안 된다(MUST NOT). 이 요구 사항 덕분에 사용자 에이전트는 자신이 보낸(그리고 메모리에 보관하고 있는) 표현이 PUT의 결과인지 알 수 있고, 그래서 오리진 서버에서 다시 가져올 필요가 없다. 응답으로 받은 새 검증자는 실수로 덮어쓰는 것을 막기 위해 이후의 조건부 요청에 쓸 수 있다(13.1절).

POST와 PUT 메서드의 근본적인 차이는 담긴 표현에 대한 의도가 다르다는 점에서 드러난다. POST 요청의 대상 리소스는 담긴 표현을 리소스 고유의 의미에 따라 처리하도록 의도되는 반면, PUT 요청에 담긴 표현은 대상 리소스의 상태를 교체하는 것으로 정의된다. 그래서 정확한 효과는 오리진 서버만 알지만, PUT의 의도는 멱등이며 중개자에게도 보인다.

PUT 요청을 올바르게 해석하려면 사용자 에이전트가 어떤 대상 리소스를 원하는지 알고 있다고 전제해야 한다. 상태를 바꾸는 요청을 받은 뒤 클라이언트를 대신해 적절한 URI를 선택하는 서비스는 PUT 대신 POST 메서드로 구현해야 한다(SHOULD). 오리진 서버가 요청받은 PUT 상태 변경을 대상 리소스에 적용하지 않고 다른 리소스에 적용하려 한다면(리소스가 다른 URI로 옮겨진 경우 등), 오리진 서버는 적절한 3xx(Redirection) 응답을 보내야 한다(MUST). 그러면 사용자 에이전트는 요청을 리다이렉트할지 스스로 결정할 수 있다(MAY).

대상 리소스에 적용한 PUT 요청은 다른 리소스에 부작용을 줄 수 있다. 예를 들어 글에는 각 특정 버전을 식별하는 URI(한때 현재 버전 리소스와 같은 상태를 공유했던 서로 다른 리소스)와 별개로, "현재 버전"(하나의 리소스)을 식별하는 URI가 있을 수 있다. 그러면 "현재 버전" URI에 대한 성공한 PUT 요청은 대상 리소스의 상태를 바꾸는 것 외에 새 버전 리소스를 만들 수 있고, 관련 리소스 사이에 링크가 추가되게 할 수도 있다.

일부 오리진 서버는 14.5절에 설명된 대로 부분 PUT을 수행하기 위한 요청 수식자로 Content-Range 헤더 필드(14.4절)를 쓰는 것을 지원한다.

PUT 메서드에 대한 응답은 캐시할 수 없다. 성공한 PUT 요청이 대상 URI에 대해 하나 이상의 저장된 응답을 가진 캐시를 거치면, 그 저장된 응답들은 무효화된다([CACHING] 4.4절 참고).

#### 9.3.5. DELETE

DELETE 메서드는 오리진 서버가 대상 리소스와 그 현재 기능 사이의 연결을 제거하도록 요청한다. 사실상 이 메서드는 UNIX의 "rm" 명령과 비슷하다. 이전에 연결된 정보가 삭제되기를 기대하는 것이 아니라, 오리진 서버의 URI 매핑에 대한 삭제 연산을 표현한다.

대상 리소스에 하나 이상의 현재 표현이 있다면, 오리진 서버가 그것을 파기할 수도 안 할 수도 있고, 관련 저장소를 회수할 수도 안 할 수도 있다. 이는 전적으로 리소스의 성격과 오리진 서버의 구현에 달려 있다(이 명세의 범위 밖이다). 마찬가지로 DELETE의 결과로 데이터베이스나 게이트웨이 연결처럼 리소스의 다른 구현 측면을 비활성화하거나 보관해야 할 수도 있다. 일반적으로 오리진 서버는 삭제를 수행하는 정해진 메커니즘이 있는 리소스에만 DELETE를 허용한다고 가정한다.

DELETE 메서드를 허용하는 리소스는 비교적 적다. 주된 용도는 사용자가 그 효과에 대해 어느 정도 지시할 수 있는 원격 저작 환경이다. 예를 들어 이전에 PUT 요청으로 만들었거나, POST 요청에 대한 201(Created) 응답 후 Location 헤더 필드로 식별된 리소스는, 그 동작을 되돌리기 위한 대응 DELETE 요청을 허용할 수 있다. 마찬가지로 원격 작업에 HTTP를 쓰는 버전 관리 클라이언트처럼 저작 기능을 구현한 맞춤 사용자 에이전트는, 서버의 URI 공간이 버전 저장소에 대응하도록 만들어져 있다는 가정 아래 DELETE를 쓸 수 있다.

DELETE 메서드가 성공적으로 적용되면, 오리진 서버는 다음을 보내야 한다(SHOULD).

- 동작이 성공할 가능성이 높지만 아직 실행되지 않았다면 202(Accepted) 상태 코드
- 동작이 실행되었고 더 제공할 정보가 없다면 204(No Content) 상태 코드
- 동작이 실행되었고 응답 메시지에 상태를 설명하는 표현이 포함되어 있다면 200(OK) 상태 코드

요청 메시지 프레이밍은 사용하는 메서드와 독립적이지만, DELETE 요청에서 받은 콘텐츠에는 일반적으로 정의된 의미가 없고, 요청의 의미나 대상을 바꿀 수 없으며, 요청 스머글링 공격([HTTP/1.1] 11.2절)이 될 가능성 때문에 일부 구현이 요청을 거절하고 연결을 닫게 만들 수 있다. 클라이언트는 그런 요청에 목적이 있고 적절히 지원될 것이라고 대역 안팎에서 미리 알린 오리진 서버에 직접 보내는 경우가 아니면, DELETE 요청에 콘텐츠를 생성하지 않아야 한다(SHOULD NOT). HTTP 통신 참여자는 요청 체인상의 중개자를 모르는 경우가 많으므로, 오리진 서버는 콘텐츠를 받기 위해 비공개 합의에 의존하지 않아야 한다(SHOULD NOT).

DELETE 메서드에 대한 응답은 캐시할 수 없다. 성공한 DELETE 요청이 대상 URI에 대해 하나 이상의 저장된 응답을 가진 캐시를 거치면, 그 저장된 응답들은 무효화된다([CACHING] 4.4절 참고).

#### 9.3.6. CONNECT

CONNECT 메서드는 수신자가 요청 대상이 식별하는 목적지 오리진 서버로 터널을 수립하고, 성공하면 그 뒤로 터널이 닫힐 때까지 양방향으로 데이터를 맹목적으로 전달하는 것으로만 동작을 제한하도록 요청한다. 터널은 보통 하나 이상의 프록시를 거치는 종단 간 가상 연결을 만드는 데 쓰이며, 그 연결은 TLS(Transport Layer Security, [TLS13])로 보호할 수 있다.

CONNECT는 이 메서드에만 있는 특별한 형태의 요청 대상을 쓴다. 터널 목적지의 호스트와 포트 번호만 콜론으로 구분해 적은 것이다. 기본 포트는 없다. CONNECT 요청이 포트가 생략된 authority 구성 요소를 담은 URI 참조(4.1절)를 바탕으로 하더라도, 클라이언트는 포트 번호를 보내야 한다(MUST). 예를 들면 다음과 같다.

```
CONNECT server.example.com:80 HTTP/1.1
Host: server.example.com
```

서버는 비어 있거나 유효하지 않은 포트 번호를 대상으로 하는 CONNECT 요청을 거절해야 하며(MUST), 보통 400(Bad Request) 상태 코드로 응답한다.

CONNECT는 HTTP 연결의 요청/응답 성격을 바꾸므로, HTTP 버전마다 그 의미를 프로토콜의 전송 형식에 대응시키는 방법이 다를 수 있다.

CONNECT는 프록시에 보내는 요청에 쓰도록 의도되었다. 수신자는 요청 대상이 식별하는 서버에 직접 연결하거나, 다른 프록시를 쓰도록 설정되어 있다면 CONNECT 요청을 다음 인바운드 프록시로 전달해서 터널을 수립할 수 있다. 오리진 서버는 CONNECT 요청을 받아들일 수 있지만(MAY), 대부분의 오리진 서버는 CONNECT를 구현하지 않는다.

2xx(Successful) 응답은 송신자(와 모든 인바운드 프록시)가 응답 헤더 섹션 직후 터널 모드로 전환한다는 것을 나타낸다. 그 헤더 섹션 뒤에 받는 데이터는 요청 대상이 식별하는 서버에서 온 것이다. 성공 응답이 아닌 응답은 터널이 아직 만들어지지 않았다는 것을 나타낸다.

터널 중개자가 어느 한쪽이 연결을 닫은 것을 감지하면 터널이 닫힌다. 중개자는 닫힌 쪽에서 온 아직 보내지 않은 데이터를 다른 쪽으로 보내려고 시도하고, 두 연결을 모두 닫은 다음, 전달하지 못하고 남은 데이터를 버려야 한다(MUST).

터널을 만들 권한을 확인하는 데 프록시 인증을 쓸 수 있다. 예를 들면 다음과 같다.

```
CONNECT server.example.com:443 HTTP/1.1
Host: server.example.com:443
Proxy-Authorization: basic aGVsbG86d29ybGQ=
```

임의의 서버로 터널을 수립하는 데는 큰 위험이 따르며, 특히 목적지가 웹 트래픽용이 아닌 잘 알려진 포트나 예약된 TCP 포트일 때 그렇다. 예를 들어 "example.com:25"로의 CONNECT는 프록시가 SMTP 트래픽용 예약 포트에 연결하라는 뜻이다. 이를 허용하면 프록시를 속여 스팸 메일을 중계하게 만들 수 있다. CONNECT를 지원하는 프록시는 그 사용을 제한된 알려진 포트 집합이나 설정 가능한 안전한 요청 대상 목록으로 제한해야 한다(SHOULD).

서버는 CONNECT에 대한 2xx(Successful) 응답에 Transfer-Encoding이나 Content-Length 헤더 필드를 보내서는 안 된다(MUST NOT). 클라이언트는 CONNECT에 대한 성공 응답에서 받은 Content-Length나 Transfer-Encoding 헤더 필드를 무시해야 한다(MUST).

CONNECT 요청 메시지에는 콘텐츠가 없다. CONNECT 요청 메시지의 헤더 섹션 뒤에 보낸 데이터의 해석은 사용 중인 HTTP 버전에 따라 다르다.

CONNECT 메서드에 대한 응답은 캐시할 수 없다.

#### 9.3.7. OPTIONS

OPTIONS 메서드는 오리진 서버나 중간의 중개자에서 대상 리소스에 사용할 수 있는 통신 옵션에 대한 정보를 요청한다. 이 메서드를 쓰면 클라이언트는 리소스 동작을 암시하지 않고도 리소스와 관련된 옵션이나 요구 사항, 또는 서버의 능력을 알아낼 수 있다.

요청 대상(7.1절)이 별표("*")인 OPTIONS 요청은 특정 리소스가 아니라 서버 전반에 적용된다. 서버의 통신 옵션은 보통 리소스에 따라 다르므로, "*" 요청은 "ping"이나 "no-op" 종류의 메서드로만 유용하다. 클라이언트가 서버의 능력을 테스트할 수 있게 하는 것 외에는 아무것도 하지 않는다. 예를 들어 프록시가 HTTP/1.1을 준수하는지(또는 준수하지 않는지) 테스트하는 데 쓸 수 있다.

요청 대상이 별표가 아니면, OPTIONS 요청은 대상 리소스와 통신할 때 사용할 수 있는 옵션에 적용된다.

OPTIONS에 대한 성공 응답을 생성하는 서버는, 서버가 구현하고 대상 리소스에 적용할 수 있는 선택적 기능을 나타낼 수 있는 헤더(예: Allow)를 이 명세가 정의하지 않는 잠재적 확장까지 포함해 보내야 한다(SHOULD). 응답 콘텐츠(있다면)도 기계나 사람이 읽을 수 있는 표현으로 통신 옵션을 설명할 수 있다. 이 명세는 그런 표현의 표준 형식을 정의하지 않지만, 앞으로의 HTTP 확장에서 정의될 수 있다.

클라이언트는 요청 체인의 특정 수신자를 대상으로 하기 위해 OPTIONS 요청에 Max-Forwards 헤더 필드를 보낼 수 있다(MAY)(7.6.2절 참고). 프록시는 Max-Forwards 필드와 함께 받은 요청이 아니면, 요청을 전달하면서 Max-Forwards 헤더 필드를 생성해서는 안 된다(MUST NOT).

콘텐츠를 담은 OPTIONS 요청을 생성하는 클라이언트는 표현 미디어 타입을 설명하는 유효한 Content-Type 헤더 필드를 보내야 한다(MUST). 이 명세는 그런 콘텐츠의 용도를 정의하지 않는다는 점에 유의하라.

OPTIONS 메서드에 대한 응답은 캐시할 수 없다.

#### 9.3.8. TRACE

TRACE 메서드는 요청 메시지의 원격 애플리케이션 수준 루프백을 요청한다. 요청의 최종 수신자는 받은 메시지를, 아래에 설명하는 일부 필드를 제외하고, 200(OK) 응답의 콘텐츠로 클라이언트에 되돌려 보내야 한다(SHOULD). "message/http" 형식([HTTP/1.1] 10.1절)이 그렇게 하는 한 가지 방법이다. 최종 수신자는 오리진 서버이거나, 요청에서 Max-Forwards 값 0을 받은 첫 서버(7.6.2절)이다.

클라이언트는 TRACE 요청에 응답으로 노출될 수 있는 민감한 데이터를 담은 필드를 생성해서는 안 된다(MUST NOT). 예를 들어 사용자 에이전트가 저장된 사용자 자격 증명(11장)이나 쿠키[COOKIE]를 TRACE 요청에 보내는 것은 어리석은 일이다. 요청의 최종 수신자는 응답 콘텐츠를 생성할 때 민감한 데이터를 담고 있을 가능성이 높은 요청 필드를 제외해야 한다(SHOULD).

TRACE를 쓰면 클라이언트는 요청 체인의 반대쪽 끝에서 무엇을 받는지 보고, 그 데이터를 테스트나 진단 정보로 쓸 수 있다. Via 헤더 필드(7.6.3절)의 값은 요청 체인의 추적 역할을 하므로 특히 흥미롭다. Max-Forwards 헤더 필드를 쓰면 클라이언트가 요청 체인의 길이를 제한할 수 있어서, 무한 루프로 메시지를 전달하는 프록시 체인을 테스트하는 데 유용하다.

클라이언트는 TRACE 요청에 콘텐츠를 보내서는 안 된다(MUST NOT).

TRACE 메서드에 대한 응답은 캐시할 수 없다.

## 10. 메시지 컨텍스트

### 10.1. 요청 컨텍스트 필드

아래 요청 헤더 필드는 요청 뒤에 있는 사용자, 사용자 에이전트, 리소스에 대한 정보를 포함해 요청 컨텍스트에 대한 추가 정보를 제공한다.

#### 10.1.1. Expect

요청의 "Expect" 헤더 필드는 이 요청을 제대로 처리하려면 서버가 지원해야 하는 특정 동작 집합(기대 사항)을 나타낸다.

```
  Expect =      #expectation
  expectation = token [ "=" ( token / quoted-string ) parameters ]
```

Expect 필드 값은 대소문자를 구분하지 않는다.

이 명세가 정의하는 유일한 기대 사항은 (정의된 매개변수가 없는) "100-continue"이다.

100-continue 외의 멤버를 담은 Expect 필드 값을 받은 서버는, 예상하지 못한 기대 사항을 충족할 수 없다는 것을 나타내기 위해 417(Expectation Failed) 상태 코드로 응답할 수 있다(MAY).

"100-continue" 기대 사항은 클라이언트가 이 요청에서 (아마도 큰) 콘텐츠를 보내려 하며, 메서드, 대상 URI, 헤더 필드만으로 즉시 성공, 리다이렉트, 오류 응답을 낼 수 없다면 100(Continue) 중간 응답을 받고 싶다는 것을 수신자에게 알린다. 그러면 클라이언트는 실제로 콘텐츠를 보내기 전에 보낼 가치가 있다는 신호를 기다릴 수 있다. 데이터가 매우 크거나, 클라이언트가 오류 가능성이 높다고 예상할 때(예: 미리 검증된 인증 자격 증명 없이 상태를 바꾸는 메서드를 처음 보낼 때) 효율을 높일 수 있다.

예를 들어 다음과 같이 시작하는 요청은

```
PUT /somewhere/fun HTTP/1.1
Host: origin.example.com
Content-Type: video/h264
Content-Length: 1234567890987
Expect: 100-continue
```

클라이언트가 불필요한 데이터 전송으로 파이프를 채우기 시작하기 전에, 오리진 서버가 401(Unauthorized)이나 405(Method Not Allowed) 같은 오류 메시지로 즉시 응답할 수 있게 한다.

클라이언트 요구 사항:

- 클라이언트는 콘텐츠가 없는 요청에 100-continue 기대 사항을 생성해서는 안 된다(MUST NOT).
- 요청 콘텐츠를 보내기 전에 100(Continue) 응답을 기다릴 클라이언트는 100-continue 기대 사항을 담은 Expect 헤더 필드를 보내야 한다(MUST).
- 100-continue 기대 사항을 보낸 클라이언트가 특정 시간 동안 기다려야 하는 것은 아니다. 그런 클라이언트는 아직 응답을 받지 못했더라도 콘텐츠를 보내기 시작할 수 있다(MAY). 게다가 100(Continue) 응답은 HTTP/1.0 중개자를 통과할 수 없으므로, 그런 클라이언트는 콘텐츠를 보내기 전에 무기한 기다리지 않아야 한다(SHOULD NOT).
- 100-continue 기대 사항을 담은 요청에 대한 응답으로 417(Expectation Failed) 상태 코드를 받은 클라이언트는 100-continue 기대 사항 없이 그 요청을 반복해야 한다(SHOULD). 417 응답은 응답 체인이 기대 사항을 지원하지 않는다(예: HTTP/1.0 서버를 거친다)는 것을 나타낼 뿐이기 때문이다.

서버 요구 사항:

- HTTP/1.0 요청에서 100-continue 기대 사항을 받은 서버는 그 기대 사항을 무시해야 한다(MUST).
- 서버는 대응하는 요청의 콘텐츠 일부나 전부를 이미 받았거나, 프레이밍이 콘텐츠가 없다고 나타내면 100(Continue) 응답을 보내지 않을 수 있다(MAY).
- 100(Continue) 응답을 보낸 서버는, 연결이 일찍 닫히지 않는 한, 요청 콘텐츠를 받아 처리한 뒤 결국 최종 상태 코드를 보내야 한다(MUST).
- 요청 콘텐츠 전체를 읽기 전에 최종 상태 코드로 응답하는 서버는 연결을 닫을지(예: [HTTP/1.1] 9.6절 참고), 아니면 요청 콘텐츠를 계속 읽을지 나타내야 한다(SHOULD).

메서드, 대상 URI, 그리고 100-continue 기대 사항과 요청 콘텐츠가 뒤따른다는 표시를 담은 완전한 헤더 섹션을 가진 HTTP/1.1(이상) 요청을 받으면, 오리진 서버는 다음 중 하나를 보내야 한다(MUST).

- 메서드, 대상 URI, 헤더 필드만 살펴보고 상태를 결정할 수 있다면, 최종 상태 코드로 즉시 응답
- 클라이언트가 요청 콘텐츠를 보내도록 즉시 100(Continue) 응답

오리진 서버는 100(Continue) 응답을 보내기 전에 콘텐츠를 기다려서는 안 된다(MUST NOT).

메서드, 대상 URI, 그리고 100-continue 기대 사항과 요청 콘텐츠가 뒤따른다는 표시를 담은 완전한 헤더 섹션을 가진 HTTP/1.1(이상) 요청을 받으면, 프록시는 다음 중 하나를 해야 한다(MUST).

- 메서드, 대상 URI, 헤더 필드만 살펴보고 상태를 결정할 수 있다면, 최종 상태 코드로 즉시 응답
- 대응하는 요청 라인과 헤더 섹션을 다음 인바운드 서버로 보내서 오리진 서버 쪽으로 요청을 전달

프록시가 (설정이나 과거의 상호작용으로) 다음 인바운드 서버가 HTTP/1.0만 지원한다고 생각하면, 클라이언트가 콘텐츠를 보내기 시작하도록 즉시 100(Continue) 응답을 생성할 수 있다(MAY).

#### 10.1.2. From

"From" 헤더 필드는 요청하는 사용자 에이전트를 제어하는 사람 사용자의 인터넷 이메일 주소를 담는다. 주소는 [RFC5322] 3.4절의 "mailbox"에 정의된 대로 기계가 쓸 수 있는 형태여야 한다.

```
  From    = mailbox

  mailbox = <mailbox, see [RFC5322], Section 3.4>
```

예시는 다음과 같다.

```
From: spider-admin@example.org
```

From 헤더 필드는 로봇이 아닌 사용자 에이전트가 보내는 경우가 드물다. 사용자 에이전트는 사용자의 명시적인 설정 없이 From 헤더 필드를 보내지 않아야 한다(SHOULD NOT). 사용자의 개인정보 이익이나 사이트 보안 정책과 충돌할 수 있기 때문이다.

로봇 사용자 에이전트는 유효한 From 헤더 필드를 보내야 한다(SHOULD). 그래야 로봇이 과도하거나, 원치 않거나, 유효하지 않은 요청을 보내는 등 서버에 문제가 생겼을 때 로봇 운영 책임자에게 연락할 수 있다.

서버는 접근 제어나 인증에 From 헤더 필드를 쓰지 않아야 한다(SHOULD NOT). 그 값은 요청을 받거나 관찰하는 누구에게나 보일 것으로 예상되며, 개인정보 보호에 대한 기대 없이 로그 파일과 오류 보고서에 기록되는 경우가 많기 때문이다.

#### 10.1.3. Referer

"Referer"[sic] 헤더 필드는 사용자 에이전트가 대상 URI를 얻은 리소스의 URI 참조(즉, 필드 이름의 철자는 틀렸지만 "referrer")를 지정할 수 있게 한다. 사용자 에이전트는 Referer 필드 값을 생성할 때 URI 참조[URI]의 fragment와 userinfo 구성 요소(있다면)를 포함해서는 안 된다(MUST NOT).

```
  Referer = absolute-URI / partial-URI
```

필드 값은 absolute-URI 또는 partial-URI이다. 후자의 경우(4장), 참조된 URI는 대상 URI에 대한 상대 참조이다([URI] 5장).

Referer 헤더 필드를 쓰면 서버가 간단한 분석, 로깅, 캐싱 최적화 등을 위해 다른 리소스로 가는 역링크를 생성할 수 있다. 또한 유지 관리를 위해 폐기되었거나 잘못 입력된 링크를 찾을 수 있다. 일부 서버는 Referer 헤더 필드를 다른 사이트의 링크(이른바 "딥 링크")를 거부하거나 크로스 사이트 요청 위조(CSRF)를 제한하는 수단으로 쓰지만, 모든 요청에 이 필드가 있는 것은 아니다.

예시:

```
Referer: http://www.example.org/hypertext/Overview.html
```

대상 URI를 자체 URI가 없는 출처(예: 사용자의 키보드 입력, 사용자의 북마크/즐겨찾기 항목)에서 얻었다면, 사용자 에이전트는 Referer 헤더 필드를 제외하거나 "about:blank" 값으로 보내야 한다(MUST).

Referer 헤더 필드 값이 참조 리소스의 전체 URI를 전달할 필요는 없다. 사용자 에이전트는 참조하는 오리진 외의 부분을 잘라낼 수 있다(MAY).

Referer 헤더 필드는 요청 컨텍스트나 사용자의 브라우징 기록에 대한 정보를 드러낼 가능성이 있다. 참조 리소스의 식별자가 개인 정보(계정 이름 등)나 기밀이어야 하는 리소스(방화벽 뒤에 있거나 보안 서비스 내부에 있는 것 등)를 드러낸다면 개인정보 문제가 된다. 대부분의 범용 사용자 에이전트는 참조 리소스가 로컬 "file"이나 "data" URI일 때 Referer 헤더 필드를 보내지 않는다. 참조 리소스에 보안 프로토콜로 접근했고 요청 대상의 오리진이 참조 리소스의 오리진과 다르면, 참조 리소스가 Referer 전송을 명시적으로 허용하지 않는 한 사용자 에이전트는 Referer 헤더 필드를 보내지 않아야 한다(SHOULD NOT). 참조 리소스에 보안 프로토콜로 접근했다면, 사용자 에이전트는 보호되지 않은 HTTP 요청에 Referer 헤더 필드를 보내서는 안 된다(MUST NOT). 추가 보안 고려 사항은 17.9절을 참고하라.

일부 중개자는 나가는 요청에서 Referer 헤더 필드를 무차별적으로 제거하는 것으로 알려져 있다. 이는 CSRF 공격 방어를 방해하는 불행한 부작용을 낳는데, CSRF 공격은 사용자에게 훨씬 더 해로울 수 있다. Referer의 정보 노출을 제한하려는 중개자와 사용자 에이전트 확장은 내부 도메인 이름을 가명으로 바꾸거나 쿼리나 경로 구성 요소를 잘라내는 것처럼 특정한 편집으로 변경을 제한하는 것이 좋다. 중개자는 필드 값이 대상 URI와 같은 스킴과 호스트를 공유할 때 Referer 헤더 필드를 수정하거나 삭제하지 않아야 한다(SHOULD NOT).

#### 10.1.4. TE

"TE" 헤더 필드는 전송 코딩과 트레일러 섹션에 관한 클라이언트의 능력을 설명한다.

6.5절에 설명된 대로, 요청에 "trailers" 멤버를 가진 TE 필드를 보내면 클라이언트가 트레일러 필드를 버리지 않는다는 뜻이다.

TE는 HTTP/1.1 안에서 클라이언트가 응답에서 어떤 전송 코딩을 받아들일 수 있는지 서버에 알리는 데도 쓰인다. 이 문서 발행 시점에 전송 코딩을 쓰는 것은 HTTP/1.1뿐이다([HTTP/1.1] 7장 참고).

TE 필드 값은 멤버 리스트이며, ("trailers"를 제외한) 각 멤버는 전송 코딩 이름 토큰과, 그 전송 코딩에 대한 클라이언트의 상대적 선호도를 나타내는 선택적 가중치(12.4.2절), 그리고 그 전송 코딩의 선택적 매개변수로 이루어진다.

```
  TE                 = #t-codings
  t-codings          = "trailers" / ( transfer-coding [ weight ] )
  transfer-coding    = token *( OWS ";" OWS transfer-parameter )
  transfer-parameter = token BWS "=" BWS ( token / quoted-string )
```

TE를 보내는 송신자는 중개자가 이 필드를 전달하지 않도록 알리기 위해 Connection 헤더 필드(7.6.1절) 안에 "TE" 연결 옵션도 보내야 한다(MUST).

#### 10.1.5. User-Agent

"User-Agent" 헤더 필드는 요청을 시작한 사용자 에이전트에 대한 정보를 담는다. 서버는 이 정보를 보고된 상호운용성 문제의 범위를 파악하거나, 특정 사용자 에이전트의 제약을 피하도록 응답을 우회하거나 맞추거나, 브라우저나 운영체제 사용에 대한 분석에 자주 쓴다. 사용자 에이전트는 그러지 않도록 특별히 설정되지 않는 한 모든 요청에 User-Agent 헤더 필드를 보내야 한다(SHOULD).

```
  User-Agent = product *( RWS ( product / comment ) )
```

User-Agent 필드 값은 하나 이상의 제품 식별자로 이루어지며, 각각 0개 이상의 주석(5.6.5절)이 뒤따를 수 있다. 이들이 함께 사용자 에이전트 소프트웨어와 그 주요 하위 제품을 식별한다. 관례상 제품 식별자는 사용자 에이전트 소프트웨어를 식별하는 데 중요한 순서대로 나열한다. 각 제품 식별자는 이름과 선택적 버전으로 이루어진다.

```
  product         = token ["/" product-version]
  product-version = token
```

송신자는 생성하는 제품 식별자를 제품을 식별하는 데 필요한 것으로 제한해야 한다(SHOULD). 송신자는 제품 식별자 안에 광고나 그 밖의 필수적이지 않은 정보를 생성해서는 안 된다(MUST NOT). 송신자는 product-version에 버전 식별자가 아닌 정보를 생성하지 않아야 한다(SHOULD NOT). 즉, 같은 제품 이름의 연속된 버전은 제품 식별자의 product-version 부분만 달라야 한다.

예시:

```
User-Agent: CERN-LineMode/2.15 libwww/2.17b3
```

사용자 에이전트는 불필요하게 세세한 정보를 담은 User-Agent 헤더 필드를 생성하지 않아야 하며(SHOULD NOT), 제3자가 하위 제품을 추가하는 것을 제한해야 한다(SHOULD). 지나치게 길고 자세한 User-Agent 필드 값은 요청 지연을 늘리고, 사용자가 원치 않게 식별될 위험("핑거프린팅")을 높인다.

마찬가지로 구현은 다른 구현과의 호환성을 선언하기 위해 그 구현의 제품 토큰을 쓰지 않는 것이 좋다. 이는 이 필드의 목적을 우회하는 것이기 때문이다. 사용자 에이전트가 다른 사용자 에이전트로 가장하면, 수신자는 실제로 쓰는 사용자 에이전트에서는 잘 동작하지 않을 수 있더라도 사용자가 그 식별된 사용자 에이전트에 맞춘 응답을 의도적으로 보고 싶어 한다고 가정할 수 있다.

### 10.2. 응답 컨텍스트 필드

아래 응답 헤더 필드는 서버, 대상 리소스, 관련 리소스에 대한 정보를 포함해, 상태 코드가 암시하는 것 이상으로 응답에 대한 추가 정보를 제공한다.

#### 10.2.1. Allow

"Allow" 헤더 필드는 대상 리소스가 지원한다고 알리는 메서드 집합을 나열한다. 이 필드의 목적은 엄밀히 말해 리소스와 관련된 유효한 요청 메서드를 수신자에게 알리는 것이다.

```
  Allow = #method
```

사용 예시:

```
Allow: GET, HEAD, PUT
```

실제로 허용되는 메서드 집합은 각 요청 시점에 오리진 서버가 정한다. 오리진 서버는 405(Method Not Allowed) 응답에 Allow 헤더 필드를 생성해야 하며(MUST), 다른 응답에도 생성할 수 있다(MAY). 빈 Allow 필드 값은 리소스가 어떤 메서드도 허용하지 않는다는 뜻으로, 리소스가 설정으로 일시적으로 비활성화되었다면 405 응답에서 나타날 수 있다.

프록시는 Allow 헤더 필드를 수정해서는 안 된다(MUST NOT). 일반 메시지 처리 규칙에 따라 처리하는 데 나타난 메서드를 모두 이해할 필요는 없다.

#### 10.2.2. Location

"Location" 헤더 필드는 일부 응답에서 응답과 관련된 특정 리소스를 가리키는 데 쓰인다. 관계의 종류는 요청 메서드와 상태 코드 의미의 조합으로 정의된다.

```
  Location = URI-reference
```

필드 값은 URI-reference 하나로 이루어진다. 상대 참조([URI] 4.2절) 형태일 때, 최종 값은 대상 URI를 기준으로 해석해서 계산한다([URI] 5장).

201(Created) 응답에서 Location 값은 요청으로 만들어진 주 리소스를 가리킨다. 3xx(Redirection) 응답에서 Location 값은 요청을 자동으로 리다이렉트할 때 선호되는 대상 리소스를 가리킨다.

3xx(Redirection) 응답에 제공된 Location 값에 fragment 구성 요소가 없으면, 사용자 에이전트는 그 값이 대상 URI를 생성하는 데 쓴 URI 참조의 fragment 구성 요소를 상속하는 것처럼 리다이렉션을 처리해야 한다(MUST). 즉, 리다이렉션은 원래 참조의 fragment(있다면)를 상속한다.

예를 들어 URI 참조 "http://www.example.org/~tim"에 대해 생성한 GET 요청은 다음 헤더 필드를 담은 303(See Other) 응답을 받을 수 있다.

```
Location: /People.html#tim
```

이는 사용자 에이전트가 "http://www.example.org/People.html#tim"으로 리다이렉트하라는 뜻이다.

마찬가지로 URI 참조 "http://www.example.org/index.html#larry"에 대해 생성한 GET 요청은 다음 헤더 필드를 담은 301(Moved Permanently) 응답을 받을 수 있다.

```
Location: http://www.example.net/index.html
```

이는 원래 fragment 식별자를 유지해서 사용자 에이전트가 "http://www.example.net/index.html#larry"로 리다이렉트하라는 뜻이다.

Location 값의 fragment 식별자가 적절하지 않은 상황도 있다. 예를 들어 201(Created) 응답의 Location 헤더 필드는 만들어진 리소스에 고유한 URI를 제공해야 한다.

> **참고:** 일부 수신자는 유효한 URI 참조가 아닌 Location 헤더 필드에서 복구를 시도한다. 이 명세는 그런 처리를 요구하거나 정의하지 않지만, 견고성을 위해 허용한다. 쉼표 리스트 구분자가 URI-reference 안에서 유효한 데이터 문자이므로, Location 필드 값은 멤버 리스트를 허용할 수 없다. 유효하지 않은 메시지가 여러 Location 필드 줄과 함께 보내지면, 경로상의 수신자가 그 필드 줄들을 하나의 값으로 결합할 수 있다. 그런 상황에서 유효한 Location 필드 값을 복구하는 것은 어렵고 구현 간에 상호운용되지 않는다.

> **참고:** Content-Location 헤더 필드(8.7절)는 담긴 표현에 대응하는 가장 구체적인 리소스를 가리킨다는 점에서 Location과 다르다. 그래서 응답에 Location과 Content-Location 헤더 필드가 모두 있을 수 있다.

#### 10.2.3. Retry-After

서버는 사용자 에이전트가 후속 요청을 보내기 전에 얼마나 기다려야 하는지 나타내기 위해 "Retry-After" 헤더 필드를 보낸다. 503(Service Unavailable) 응답과 함께 보내면, Retry-After는 서비스가 클라이언트에게 얼마나 오래 사용 불가능할 것으로 예상되는지를 나타낸다. 3xx(Redirection) 응답과 함께 보내면, Retry-After는 사용자 에이전트가 리다이렉트된 요청을 보내기 전에 기다려 달라고 요청받는 최소 시간을 나타낸다.

Retry-After 필드 값은 HTTP-date이거나, 응답을 받은 뒤 지연할 초 수일 수 있다.

```
  Retry-After = HTTP-date / delay-seconds
```

delay-seconds 값은 초 단위 시간을 나타내는 음이 아닌 10진수 정수이다.

```
  delay-seconds  = 1*DIGIT
```

사용 예시 두 가지는 다음과 같다.

```
Retry-After: Fri, 31 Dec 1999 23:59:59 GMT
Retry-After: 120
```

두 번째 예시에서 지연 시간은 2분이다.

#### 10.2.4. Server

"Server" 헤더 필드는 오리진 서버가 요청을 처리하는 데 쓴 소프트웨어에 대한 정보를 담는다. 클라이언트는 이 정보를 보고된 상호운용성 문제의 범위를 파악하거나, 특정 서버의 제약을 피하도록 요청을 우회하거나 맞추거나, 서버나 운영체제 사용에 대한 분석에 자주 쓴다. 오리진 서버는 응답에 Server 헤더 필드를 생성할 수 있다(MAY).

```
  Server = product *( RWS ( product / comment ) )
```

Server 헤더 필드 값은 하나 이상의 제품 식별자로 이루어지며, 각각 0개 이상의 주석(5.6.5절)이 뒤따를 수 있다. 이들이 함께 오리진 서버 소프트웨어와 그 주요 하위 제품을 식별한다. 관례상 제품 식별자는 오리진 서버 소프트웨어를 식별하는 데 중요한 순서대로 나열한다. 각 제품 식별자는 10.1.5절에 정의된 대로 이름과 선택적 버전으로 이루어진다.

예시:

```
Server: CERN/3.0 libwww/2.17
```

오리진 서버는 불필요하게 세세한 정보를 담은 Server 헤더 필드를 생성하지 않아야 하며(SHOULD NOT), 제3자가 하위 제품을 추가하는 것을 제한해야 한다(SHOULD). 지나치게 길고 자세한 Server 필드 값은 응답 지연을 늘리고, 공격자가 알려진 보안 허점을 찾아 악용하기를 (약간) 더 쉽게 만들 수 있는 내부 구현 세부 사항을 드러낼 수 있다.

## 15. 상태 코드

응답의 상태 코드는 요청의 결과와 응답의 의미를 설명하는 세 자리 정수 코드이다. 요청이 성공했는지, 어떤 콘텐츠가 담겨 있는지(있다면)도 여기에 포함된다. 유효한 상태 코드는 모두 100부터 599까지의 범위 안에 있다.

상태 코드의 첫 자리는 응답의 클래스를 정의한다. 뒤의 두 자리에는 분류 역할이 없다. 첫 자리에는 다섯 가지 값이 있다.

- **1xx (Informational)**: 요청을 받았고, 처리를 계속하고 있다.
- **2xx (Successful)**: 요청을 성공적으로 받았고, 이해했고, 받아들였다.
- **3xx (Redirection)**: 요청을 완료하려면 추가 동작이 필요하다.
- **4xx (Client Error)**: 요청에 잘못된 문법이 있거나 요청을 이행할 수 없다.
- **5xx (Server Error)**: 서버가 유효해 보이는 요청을 이행하지 못했다.

HTTP 상태 코드는 확장 가능하다. 클라이언트가 등록된 모든 상태 코드의 의미를 이해해야 하는 것은 아니지만, 이해하는 것이 분명 바람직하다. 하지만 클라이언트는 첫 자리로 나타나는 모든 상태 코드의 클래스를 이해해야 하며, 인식하지 못한 상태 코드를 그 클래스의 x00 상태 코드와 동등하게 다뤄야 한다(MUST).

예를 들어 클라이언트가 인식하지 못한 상태 코드 471을 받으면, 첫 자리를 보고 요청에 뭔가 문제가 있었다는 것을 알 수 있고, 응답을 400(Bad Request) 상태 코드를 받은 것처럼 다룰 수 있다. 응답 메시지에는 보통 상태를 설명하는 표현이 담겨 있다.

100..599 범위 밖의 값은 유효하지 않다. 구현은 HTTP가 아닌 상태(예: 라이브러리 오류)를 내부적으로 전달하기 위해 그 범위 밖의 세 자리 정수 값(즉, 600..999)을 쓰는 경우가 많다. 유효하지 않은 상태 코드를 가진 응답을 받은 클라이언트는 그 응답을 5xx(Server Error) 상태 코드를 가진 것처럼 처리해야 한다(SHOULD).

요청 하나에 여러 응답이 연관될 수 있다. "정보성"(1xx) 범위의 상태 코드를 가진 0개 이상의 "중간(interim)"(최종이 아닌) 응답 뒤에, 다른 범위 중 하나의 상태 코드를 가진 "최종(final)" 응답이 정확히 하나 온다.

### 15.1. 상태 코드 개요

아래 나열한 상태 코드는 이 명세에 정의되어 있다. 여기 나열한 사유 구절(reason phrase)은 권장 사항일 뿐이다. 프로토콜에 영향을 주지 않고 현지화된 표현으로 바꾸거나 아예 생략할 수 있다.

휴리스틱하게 캐시 가능하다고 정의된 상태 코드(예: 이 명세에서는 200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, 501)를 가진 응답은, 메서드 정의나 명시적 캐시 제어[CACHING]가 달리 나타내지 않는 한 캐시가 휴리스틱 만료로 재사용할 수 있다. 그 밖의 모든 상태 코드는 휴리스틱하게 캐시할 수 없다.

이 명세의 범위 밖에서 HTTP에 쓰도록 명세된 추가 상태 코드들이 있다. 이런 상태 코드는 모두 16.2절에 설명된 대로 "Hypertext Transfer Protocol (HTTP) Status Code Registry"에 등록되어야 한다.

### 15.2. 정보성 1xx

1xx(Informational) 클래스의 상태 코드는 요청된 동작을 완료하고 최종 응답을 보내기 전에, 연결 상태나 요청 진행 상황을 전달하기 위한 중간 응답을 나타낸다. HTTP/1.0은 1xx 상태 코드를 정의하지 않았으므로, 서버는 HTTP/1.0 클라이언트에 1xx 응답을 보내서는 안 된다(MUST NOT).

1xx 응답은 헤더 섹션의 끝에서 끝난다. 콘텐츠나 트레일러를 담을 수 없다.

클라이언트는 예상하지 않았더라도 최종 응답 전에 받은 하나 이상의 1xx 응답을 파싱할 수 있어야 한다(MUST). 사용자 에이전트는 예상하지 않은 1xx 응답을 무시할 수 있다(MAY).

프록시는 자신이 1xx 응답 생성을 요청한 경우가 아니면 1xx 응답을 전달해야 한다(MUST). 예를 들어 프록시가 요청을 전달할 때 "Expect: 100-continue" 헤더 필드를 추가했다면, 대응하는 100(Continue) 응답을 전달할 필요가 없다.

#### 15.2.1. 100 Continue

100(Continue) 상태 코드는 요청의 앞부분을 받았고 서버가 아직 거절하지 않았다는 것을 나타낸다. 서버는 요청을 다 받고 처리한 뒤 최종 응답을 보낼 생각이다.

요청에 100-continue 기대 사항을 포함한 Expect 헤더 필드가 있으면, 100 응답은 10.1.1절에 설명된 대로 서버가 요청 콘텐츠를 받고 싶다는 것을 나타낸다. 클라이언트는 요청을 계속 보내고 100 응답은 버려야 한다.

요청에 100-continue 기대 사항을 담은 Expect 헤더 필드가 없었다면, 클라이언트는 이 중간 응답을 그냥 버리면 된다.

#### 15.2.2. 101 Switching Protocols

101(Switching Protocols) 상태 코드는 서버가 Upgrade 헤더 필드(7.8절)를 통한, 이 연결에서 쓰는 애플리케이션 프로토콜을 바꿔 달라는 클라이언트의 요청을 이해했고 따를 의향이 있다는 것을 나타낸다. 서버는 응답에 이 응답 이후에 어떤 프로토콜(들)이 적용될지 나타내는 Upgrade 헤더 필드를 생성해야 한다(MUST).

서버는 프로토콜을 바꾸는 것이 유리할 때만 동의한다고 가정한다. 예를 들어 더 새로운 HTTP 버전으로 바꾸는 것이 예전 버전보다 유리할 수 있고, 실시간 동기 프로토콜의 기능을 쓰는 리소스를 전달할 때는 그런 프로토콜로 바꾸는 것이 유리할 수 있다.

### 15.3. 성공 2xx

2xx(Successful) 클래스의 상태 코드는 클라이언트의 요청을 성공적으로 받았고, 이해했고, 받아들였다는 것을 나타낸다.

#### 15.3.1. 200 OK

200(OK) 상태 코드는 요청이 성공했다는 것을 나타낸다. 200 응답으로 보내는 콘텐츠는 요청 메서드에 따라 다르다. 이 명세가 정의하는 메서드에 대해 콘텐츠의 의도된 의미를 요약하면 다음과 같다.

| 요청 메서드 | 응답 콘텐츠가 나타내는 표현 |
|---|---|
| GET | 대상 리소스 |
| HEAD | GET처럼 대상 리소스이지만, 표현 데이터를 전송하지 않음 |
| POST | 동작의 상태, 또는 동작으로 얻은 결과 |
| PUT, DELETE | 동작의 상태 |
| OPTIONS | 대상 리소스의 통신 옵션 |
| TRACE | 추적 결과를 돌려주는 서버가 받은 요청 메시지 |

<p align="center">표 6</p>

CONNECT에 대한 응답을 제외하면, 메시지 프레이밍이 콘텐츠 길이가 0이라고 명시적으로 나타내지 않는 한 200 응답에는 메시지 콘텐츠가 있을 것으로 예상한다. 요청의 어떤 측면이 성공 시 콘텐츠가 없는 것을 선호한다고 나타내면, 오리진 서버는 대신 204(No Content) 응답을 보내야 한다. CONNECT의 경우 성공 결과가 200 응답 헤더 섹션 직후 시작되는 터널이므로 콘텐츠가 없다.

200 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

GET이나 HEAD에 대한 200 응답에서 오리진 서버는 선택된 표현에 대해 사용할 수 있는 검증자 필드(8.8절)를 보내야 하며(SHOULD), 강한 엔티티 태그와 Last-Modified 날짜를 둘 다 보내는 것이 바람직하다.

상태를 바꾸는 메서드에 대한 200 응답에서, 응답으로 보낸 검증자 필드(8.8절)는 요청 의미를 성공적으로 적용한 결과로 만들어진 새 표현의 현재 검증자를 전달한다. PUT 메서드(9.3.4절)에는 그런 검증자를 보내지 못하게 할 수 있는 추가 요구 사항이 있다는 점에 유의하라.

#### 15.3.2. 201 Created

201(Created) 상태 코드는 요청이 이행되었고 그 결과 하나 이상의 새 리소스가 만들어졌다는 것을 나타낸다. 요청으로 만들어진 주 리소스는 응답의 Location 헤더 필드로 식별되며, Location 헤더 필드를 받지 못했다면 대상 URI로 식별된다.

201 응답 콘텐츠는 보통 만들어진 리소스(들)를 설명하고 그것으로 가는 링크를 제공한다. 응답으로 보낸 검증자 필드(8.8절)는 요청으로 만들어진 새 표현의 현재 검증자를 전달한다. PUT 메서드(9.3.4절)에는 그런 검증자를 보내지 못하게 할 수 있는 추가 요구 사항이 있다는 점에 유의하라.

#### 15.3.3. 202 Accepted

202(Accepted) 상태 코드는 요청이 처리를 위해 받아들여졌지만 처리가 완료되지 않았다는 것을 나타낸다. 실제로 처리할 때 허용되지 않을 수 있으므로, 요청이 결국 실행될 수도 있고 안 될 수도 있다. HTTP에는 비동기 작업의 상태 코드를 다시 보내는 기능이 없다.

202 응답은 의도적으로 확답을 하지 않는다. 그 목적은 사용자 에이전트와 서버의 연결이 처리가 끝날 때까지 유지될 필요 없이, 서버가 다른 프로세스(하루에 한 번만 실행되는 배치 지향 프로세스 등)를 위한 요청을 받아들일 수 있게 하는 것이다. 이 응답과 함께 보내는 표현은 요청의 현재 상태를 설명하고, 요청이 언제 이행될지 사용자에게 추정치를 제공할 수 있는 상태 모니터를 가리키거나(또는 포함해야) 한다.

#### 15.3.4. 203 Non-Authoritative Information

203(Non-Authoritative Information) 상태 코드는 요청이 성공했지만, 담긴 콘텐츠가 변환 프록시(7.7절)에 의해 오리진 서버의 200(OK) 응답과 다르게 수정되었다는 것을 나타낸다. 이 상태 코드를 쓰면 프록시가 변환이 적용되었다는 것을 수신자에게 알릴 수 있다. 그 사실이 콘텐츠에 대한 이후 결정에 영향을 줄 수 있기 때문이다. 예를 들어 그 콘텐츠에 대한 이후의 캐시 검증 요청은 같은 요청 경로(같은 프록시들)를 따라서만 적용될 수 있다.

203 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.3.5. 204 No Content

204(No Content) 상태 코드는 서버가 요청을 성공적으로 이행했고 응답 콘텐츠로 보낼 추가 콘텐츠가 없다는 것을 나타낸다. 응답 헤더 필드의 메타데이터는 요청된 동작이 적용된 뒤의 대상 리소스와 그 선택된 표현을 가리킨다.

예를 들어 PUT 요청에 대한 응답으로 204 상태 코드를 받았고 응답에 ETag 필드가 있다면, PUT이 성공했고 ETag 필드 값에 그 대상 리소스의 새 표현에 대한 엔티티 태그가 담겨 있다는 뜻이다.

204 응답을 쓰면 서버는 동작이 대상 리소스에 성공적으로 적용되었다는 것을 나타내면서, 사용자 에이전트가 현재 "문서 뷰"(있다면)에서 벗어날 필요가 없다는 것을 암시할 수 있다. 서버는 사용자 에이전트가 자체 인터페이스에 맞게 사용자에게 성공 표시를 제공하고, 응답의 새로운 또는 갱신된 메타데이터를 활성 표현에 적용할 것이라고 가정한다.

예를 들어 204 상태 코드는 문서 편집 인터페이스에서 "저장" 동작에 흔히 쓰여서, 저장하는 문서를 사용자가 계속 편집할 수 있게 한다. 분산 버전 관리 시스템처럼 자동화된 데이터 전송이 주를 이룰 것으로 예상하는 인터페이스에서도 자주 쓰인다.

204 응답은 헤더 섹션의 끝에서 끝난다. 콘텐츠나 트레일러를 담을 수 없다.

204 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.3.6. 205 Reset Content

205(Reset Content) 상태 코드는 서버가 요청을 이행했으며, 사용자 에이전트가 요청을 보내게 한 "문서 뷰"를 오리진 서버에서 받은 원래 상태로 초기화하기를 바란다는 것을 나타낸다.

이 응답은 흔한 데이터 입력 사용 사례를 지원하기 위한 것이다. 사용자가 데이터 입력을 지원하는 콘텐츠(폼, 메모장, 캔버스 등)를 받아서 그 공간에 데이터를 입력하거나 조작하고, 입력한 데이터를 요청으로 제출한 다음, 사용자가 다른 입력 동작을 쉽게 시작할 수 있도록 데이터 입력 메커니즘이 다음 입력을 위해 초기화되는 경우다.

205 상태 코드는 추가 콘텐츠가 제공되지 않는다는 뜻이므로, 서버는 205 응답에 콘텐츠를 생성해서는 안 된다(MUST NOT).

#### 15.3.7. 206 Partial Content

206(Partial Content) 상태 코드는 서버가 선택된 표현의 하나 이상의 부분을 전송해서 대상 리소스에 대한 범위 요청을 성공적으로 이행하고 있다는 것을 나타낸다.

범위 요청(14장)을 지원하는 서버는 보통 요청된 범위를 모두 충족하려고 한다. 더 적은 데이터를 보내면 클라이언트가 나머지를 위해 다시 요청할 가능성이 높기 때문이다. 하지만 서버는 일시적인 사용 불가, 캐시 효율, 부하 분산 등 자체적인 이유로 요청된 데이터의 일부만 보내고 싶을 수 있다. 206 응답은 자기 서술적이므로, 클라이언트는 범위 요청을 부분적으로만 충족하는 응답도 이해할 수 있다.

클라이언트는 어떤 부분이 담겨 있고 추가 요청이 필요한지 판단하기 위해 206 응답의 Content-Type과 Content-Range 필드(들)를 살펴봐야 한다(MUST).

206 응답을 생성하는 서버는 아래 하위 절에서 요구하는 것 외에, 같은 요청에 대한 200(OK) 응답에서 보냈을 필드라면 다음 헤더 필드를 생성해야 한다(MUST). Date, Cache-Control, ETag, Expires, Content-Location, Vary.

206 응답에 있는 Content-Length 헤더 필드는 이 메시지 콘텐츠의 옥텟 수를 나타내며, 이는 보통 선택된 표현의 전체 길이가 아니다. 각 Content-Range 헤더 필드에 선택된 표현의 전체 길이에 대한 정보가 들어 있다.

If-Range 헤더 필드가 있는 요청에 206 응답을 생성하는 송신자는, 클라이언트가 이미 그 헤더 필드들을 담은 이전 응답을 가지고 있으므로 필요한 것 외의 다른 표현 헤더 필드를 생성하지 않아야 한다(SHOULD NOT). 그렇지 않으면 송신자는 같은 요청에 대한 200(OK) 응답에서 보냈을 모든 표현 헤더 필드를 생성해야 한다(MUST).

206 응답은 휴리스틱하게 캐시 가능하다. 즉, 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

##### 15.3.7.1. 단일 부분

부분 하나를 전송한다면, 206 응답을 생성하는 서버는 선택된 표현의 어느 범위가 담겨 있는지 설명하는 Content-Range 헤더 필드와, 그 범위로 이루어진 콘텐츠를 생성해야 한다(MUST). 예를 들면 다음과 같다.

```
HTTP/1.1 206 Partial Content
Date: Wed, 15 Nov 1995 06:25:24 GMT
Last-Modified: Wed, 15 Nov 1995 04:58:08 GMT
Content-Range: bytes 21010-47021/47022
Content-Length: 26012
Content-Type: image/gif

... 26012 bytes of partial image data ...
```

##### 15.3.7.2. 여러 부분

여러 부분을 전송한다면, 206 응답을 생성하는 서버는 14.6절에 정의된 "multipart/byteranges" 콘텐츠와, "multipart/byteranges" 미디어 타입과 필수 boundary 매개변수를 담은 Content-Type 헤더 필드를 생성해야 한다(MUST). 단일 부분 응답과 혼동하지 않도록, 서버는 여러 부분 응답의 HTTP 헤더 섹션에 Content-Range 헤더 필드를 생성해서는 안 된다(MUST NOT)(이 필드는 대신 각 부분에 보낸다).

멀티파트 콘텐츠의 각 본문 부분 헤더 영역 안에, 서버는 그 본문 부분에 담긴 범위에 대응하는 Content-Range 헤더 필드를 생성해야 한다(MUST). 선택된 표현이 200(OK) 응답에서 Content-Type 헤더 필드를 가졌을 것이라면, 서버는 각 본문 부분의 헤더 영역에 같은 Content-Type 헤더 필드를 생성해야 한다(SHOULD). 예를 들면 다음과 같다.

```
HTTP/1.1 206 Partial Content
Date: Wed, 15 Nov 1995 06:25:24 GMT
Last-Modified: Wed, 15 Nov 1995 04:58:08 GMT
Content-Length: 1741
Content-Type: multipart/byteranges; boundary=THIS_STRING_SEPARATES

--THIS_STRING_SEPARATES
Content-Type: application/pdf
Content-Range: bytes 500-999/8000

...the first range...
--THIS_STRING_SEPARATES
Content-Type: application/pdf
Content-Range: bytes 7000-7999/8000

...the second range
--THIS_STRING_SEPARATES--
```

여러 범위를 요청받으면, 서버는 받은 Range 헤더 필드에서 대응하는 range-spec이 나타난 순서와 상관없이, 겹치는 범위나 여러 부분을 보내는 오버헤드보다 작은 간격으로 떨어진 범위를 합칠 수 있다(MAY). "multipart/byteranges"의 각 부분 사이의 일반적인 오버헤드는 선택된 표현의 미디어 타입과 선택한 boundary 매개변수 길이에 따라 약 80바이트이므로, 작고 떨어진 부분을 많이 전송하는 것이 선택된 표현 전체를 전송하는 것보다 비효율적일 수 있다.

여러 부분을 요청하지 않는 클라이언트는 멀티파트 응답을 지원하지 않을 수 있으므로, 서버는 단일 범위 요청에 멀티파트 응답을 생성해서는 안 된다(MUST NOT). 하지만 여러 범위를 요청받았는데 충족 가능한 범위가 하나뿐이거나 합친 뒤 범위가 하나만 남았다면, 서버는 본문 부분이 하나뿐인 "multipart/byteranges" 응답을 생성할 수 있다(MAY). "multipart/byteranges" 응답을 처리할 수 없는 클라이언트는 여러 범위를 요청하는 요청을 생성해서는 안 된다(MUST NOT).

멀티파트 응답을 생성하는 서버는 충족할 수 없다고 판단했거나 다른 범위로 합쳐진 범위를 제외하고, 받은 Range 헤더 필드에서 대응하는 range-spec이 나타난 순서대로 부분을 보내야 한다(SHOULD). 멀티파트 응답을 받은 클라이언트는 각 본문 부분에 어떤 범위가 담겨 있는지 판단하기 위해 각 본문 부분에 있는 Content-Range 헤더 필드를 살펴봐야 한다(MUST). 클라이언트는 요청한 것과 같은 범위를, 요청한 것과 같은 순서로 받는다고 기대할 수 없다.

##### 15.3.7.3. 부분 결합

연결이 일찍 닫혔거나 요청이 하나 이상의 Range 명세를 썼다면, 응답이 표현의 하위 범위만 전송할 수 있다. 이런 전송이 여러 번 있은 뒤, 클라이언트는 같은 표현의 여러 범위를 받았을 수 있다. 이 범위들은 모두 같은 강한 검증자(8.8.1절)를 공유할 때만 안전하게 결합할 수 있다.

대상 리소스에 대한 GET 요청의 부분 응답을 여러 개 받은 클라이언트는, 그 응답들이 같은 강한 검증자를 공유한다면 더 큰 연속 범위로 결합할 수 있다(MAY).

가장 최근 응답이 불완전한 200(OK) 응답이면, 그 응답의 헤더 필드가 결합된 응답에 쓰이며 일치하는 저장된 응답의 헤더 필드를 대체한다.

가장 최근 응답이 206(Partial Content) 응답이고 일치하는 저장된 응답 중 적어도 하나가 200(OK)이면, 결합된 응답 헤더 필드는 가장 최근 200 응답의 헤더 필드로 이루어진다. 일치하는 저장된 응답이 모두 206 응답이면, 가장 최근 헤더 필드를 가진 저장된 응답이 결합된 응답의 헤더 필드 출처로 쓰인다. 다만 클라이언트는 Content-Range를 제외하고 새 응답에 제공된 다른 헤더 필드를 써서, 저장된 응답에 있는 대응 헤더 필드의 모든 인스턴스를 대체해야 한다(MUST).

결합된 응답 콘텐츠는 새 응답과 일치하는 모든 저장된 응답 안의 부분 콘텐츠 범위의 합집합으로 이루어진다. 합집합이 표현의 전체 범위로 이루어지면, 클라이언트는 결합된 응답을 전체 길이를 반영하는 Content-Length 헤더 필드를 포함한 완전한 200(OK) 응답인 것처럼 처리해야 한다(MUST). 그렇지 않으면 클라이언트는 연속 범위 집합을 다음 중 하나로 처리해야 한다(MUST). 결합된 응답이 표현의 앞부분이면 불완전한 200(OK) 응답, "multipart/byteranges" 콘텐츠를 담은 하나의 206(Partial Content) 응답, 또는 각각 Content-Range 헤더 필드로 나타나는 연속 범위 하나를 가진 여러 206(Partial Content) 응답.

### 15.4. 리다이렉션 3xx

3xx(Redirection) 클래스의 상태 코드는 요청을 이행하려면 사용자 에이전트가 추가 동작을 해야 한다는 것을 나타낸다. 리다이렉트에는 여러 종류가 있다.

1. 301(Moved Permanently), 302(Found), 307(Temporary Redirect), 308(Permanent Redirect) 상태 코드처럼, 이 리소스를 Location 헤더 필드가 제공하는 다른 URI에서 사용할 수 있을 것임을 나타내는 리다이렉트
2. 300(Multiple Choices) 상태 코드처럼, 이 리소스를 표현할 수 있는 일치하는 리소스들 중에서 선택지를 제공하는 리다이렉션
3. 303(See Other) 상태 코드처럼, 요청에 대한 간접 응답을 나타낼 수 있는, Location 헤더 필드로 식별되는 다른 리소스로의 리다이렉션
4. 304(Not Modified) 상태 코드처럼, 이전에 저장된 결과로의 리다이렉션

> **참고:** HTTP/1.0에서 301(Moved Permanently)과 302(Found) 상태 코드는 원래 CERN의 구현에 맞춰 메서드를 유지하는 것으로 정의되었다([HTTP/1.0] 9.3절). 303(See Other)은 메서드를 GET으로 바꾸는 리다이렉션을 위해 정의되었다. 하지만 초기 사용자 에이전트들은 POST 요청을 (당시 명세에 따라) POST로 리다이렉트할지, (다른 사이트로 리다이렉트될 때 더 안전한 대안인) GET으로 리다이렉트할지 의견이 갈렸다. 결국 메서드를 GET으로 바꾸는 관행이 우세해졌다. 나중에 메서드를 유지하는 리다이렉트를 모호함 없이 나타내기 위해 307(Temporary Redirect)과 308(Permanent Redirect)[RFC7538]이 추가되었고, 301과 302 상태 코드는 POST 요청을 GET으로 리다이렉트하는 것을 허용하도록 조정되었다.

Location 헤더 필드(10.2.2절)가 제공되면, 사용자 에이전트는 특정 상태 코드를 이해하지 못하더라도 Location 필드 값이 참조하는 URI로 요청을 자동으로 리다이렉트할 수 있다(MAY). 사용자가 안전하지 않은 요청을 리다이렉트하기를 원하지 않을 수 있으므로, 9.2.1절에 정의된 대로 안전하다고 알려지지 않은 메서드의 자동 리다이렉션은 주의해서 해야 한다.

리다이렉트된 요청을 자동으로 따라갈 때, 사용자 에이전트는 원래 요청 메시지를 다음과 같이 수정해서 다시 보내야 한다(SHOULD).

1. 대상 URI를, 리다이렉션 응답의 Location 헤더 필드 값을 원래 요청의 대상 URI 기준으로 해석한 뒤 참조하는 URI로 바꾼다.
2. 구현이 자동으로 생성한 헤더 필드를 제거하고, 새 요청에 맞게 적절히 갱신된 값으로 바꾼다. 여기에는 다음이 포함된다.
   1. 연결별 헤더 필드(7.6.1절 참고)
   2. Proxy-Authorization을 포함하되 이에 국한되지 않는, 클라이언트의 프록시 설정에 특화된 헤더 필드
   3. Host를 포함하되 이에 국한되지 않는, 오리진별 헤더 필드(있다면)
   4. 구현의 캐시가 추가한 검증 헤더 필드(예: If-None-Match, If-Modified-Since)
   5. Referer, Origin, Authorization, Cookie를 포함하되 이에 국한되지 않는, 리소스별 헤더 필드
3. 구현이 자동으로 생성하지 않은 헤더 필드(즉, 호출하는 컨텍스트가 추가해서 요청에 있는 것) 중 보안상 영향이 있는 것은 제거를 고려한다. 여기에는 Authorization과 Cookie가 포함되며 이에 국한되지 않는다.
4. 해당한다면, 리다이렉트 상태 코드의 의미에 따라 요청 메서드를 바꾼다.
5. 요청 메서드가 GET이나 HEAD로 바뀌었다면, Content-Encoding, Content-Language, Content-Location, Content-Type, Content-Length, Digest, Last-Modified를 포함하되 이에 국한되지 않는 콘텐츠별 헤더 필드를 제거한다.

클라이언트는 순환 리다이렉션(즉, "무한" 리다이렉션 루프)을 감지하고 개입해야 한다(SHOULD).

> **참고:** 이 명세의 이전 버전은 리다이렉션을 최대 5회로 권장했다([RFC2068] 10.3절). 콘텐츠 개발자는 일부 클라이언트가 이런 고정 제한을 구현할 수 있다는 점을 알아야 한다.

#### 15.4.1. 300 Multiple Choices

300(Multiple Choices) 상태 코드는 대상 리소스에 각자 더 구체적인 식별자를 가진 표현이 둘 이상 있고, 사용자(또는 사용자 에이전트)가 그 식별자 중 하나 이상으로 요청을 리다이렉트해서 선호하는 표현을 선택할 수 있도록 대안에 대한 정보를 제공한다는 것을 나타낸다. 다시 말해 서버는 사용자 에이전트가 필요에 가장 적합한 표현(들)을 선택하기 위해 반응형 협상(12장)을 하기를 원한다.

서버에 선호하는 선택지가 있다면, 서버는 선호하는 선택지의 URI 참조를 담은 Location 헤더 필드를 생성해야 한다(SHOULD). 사용자 에이전트는 자동 리다이렉션에 Location 필드 값을 쓸 수 있다(MAY).

HEAD 외의 요청 메서드에 대해, 서버는 사용자나 사용자 에이전트가 가장 선호하는 것을 고를 수 있도록 표현 메타데이터와 URI 참조(들)의 목록을 담은 콘텐츠를 300 응답에 생성해야 한다(SHOULD). 사용자 에이전트는 제공된 미디어 타입을 이해한다면 그 목록에서 자동으로 선택할 수 있다(MAY). HTTP는 콘텐츠 정의와 직교하는 상태를 유지하려 하므로, 이 명세는 자동 선택을 위한 특정 형식을 정의하지 않는다. 실제로는 공유된 설계나 콘텐츠 협상으로 정해진, 사용자 에이전트가 받아들일 수 있다고 생각되는 쉽게 파싱되는 형식이나, 흔히 받아들여지는 하이퍼텍스트 형식으로 표현을 제공한다.

300 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

> **참고:** 300 상태 코드에 대한 원래 제안은 대안 표현의 목록을 제공하는 URI 헤더 필드를 정의해서, 200, 300, 406 응답에 쓸 수 있고 HEAD 메서드에 대한 응답으로도 전송되게 했다. 하지만 배포가 부족하고 문법에 대한 이견이 있어서 URI와 (그 뒤의 제안인) Alternates가 모두 이 명세에서 빠졌다. 멤버들이 "alternate" 관계를 가진 Link 헤더 필드 값[RFC8288]으로 목록을 전달할 수도 있지만, 배포는 닭이 먼저냐 달걀이 먼저냐의 문제다.

#### 15.4.2. 301 Moved Permanently

301(Moved Permanently) 상태 코드는 대상 리소스에 새 영구 URI가 할당되었으며, 이 리소스에 대한 앞으로의 참조는 담긴 URI 중 하나를 써야 한다는 것을 나타낸다. 서버는 링크 편집 기능이 있는 사용자 에이전트가 대상 URI에 대한 참조를 서버가 보낸 새 참조 중 하나로 영구히 바꿀 수 있다고 제안하는 것이다. 하지만 사용자 에이전트가 참조를 적극적으로 편집하고 있고(예: 콘텐츠를 저작하는 중), 연결이 보호되어 있고, 오리진 서버가 편집 중인 콘텐츠에 대해 신뢰할 수 있는 권한자인 경우가 아니면, 이 제안은 보통 무시된다.

서버는 응답에 새 영구 URI에 대한 선호하는 URI 참조를 담은 Location 헤더 필드를 생성해야 한다(SHOULD). 사용자 에이전트는 자동 리다이렉션에 Location 필드 값을 쓸 수 있다(MAY). 서버의 응답 콘텐츠에는 보통 새 URI(들)로 가는 하이퍼링크가 있는 짧은 하이퍼텍스트 메모가 들어 있다.

> **참고:** 역사적인 이유로, 사용자 에이전트는 이후 요청에서 요청 메서드를 POST에서 GET으로 바꿀 수 있다(MAY). 이 동작을 원하지 않는다면 대신 308(Permanent Redirect) 상태 코드를 쓸 수 있다.

301 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.4.3. 302 Found

302(Found) 상태 코드는 대상 리소스가 일시적으로 다른 URI에 있다는 것을 나타낸다. 리다이렉션은 때때로 바뀔 수 있으므로, 클라이언트는 앞으로의 요청에 대상 URI를 계속 써야 한다.

서버는 응답에 다른 URI에 대한 URI 참조를 담은 Location 헤더 필드를 생성해야 한다(SHOULD). 사용자 에이전트는 자동 리다이렉션에 Location 필드 값을 쓸 수 있다(MAY). 서버의 응답 콘텐츠에는 보통 다른 URI(들)로 가는 하이퍼링크가 있는 짧은 하이퍼텍스트 메모가 들어 있다.

> **참고:** 역사적인 이유로, 사용자 에이전트는 이후 요청에서 요청 메서드를 POST에서 GET으로 바꿀 수 있다(MAY). 이 동작을 원하지 않는다면 대신 307(Temporary Redirect) 상태 코드를 쓸 수 있다.

#### 15.4.4. 303 See Other

303(See Other) 상태 코드는 서버가 원래 요청에 대한 간접 응답을 제공하기 위해, Location 헤더 필드의 URI로 나타낸 다른 리소스로 사용자 에이전트를 리다이렉트하고 있다는 것을 나타낸다. 사용자 에이전트는 그 URI를 대상으로 검색 요청(HTTP를 쓴다면 GET이나 HEAD 요청)을 수행할 수 있으며, 그 요청도 리다이렉트될 수 있다. 그리고 최종 결과를 원래 요청에 대한 답으로 제시할 수 있다. Location 헤더 필드의 새 URI는 대상 URI와 동등한 것으로 보지 않는다는 점에 유의하라.

이 상태 코드는 모든 HTTP 메서드에 적용할 수 있다. 주로 POST 동작의 출력이 사용자 에이전트를 다른 리소스로 리다이렉트할 수 있게 하는 데 쓰인다. 그렇게 하면 POST 응답에 해당하는 정보를 따로 식별하고, 북마크하고, 캐시할 수 있는 리소스로 제공할 수 있기 때문이다.

GET 요청에 대한 303 응답은 오리진 서버에 서버가 HTTP로 전송할 수 있는 대상 리소스의 표현이 없다는 것을 나타낸다. 하지만 Location 필드 값은 대상 리소스를 설명하는 리소스를 가리키므로, 그 다른 리소스에 검색 요청을 하면 원래 대상 리소스를 나타낸다는 뜻은 아니지만 수신자에게 유용한 표현을 얻을 수 있다. 무엇을 표현할 수 있는지, 어떤 표현이 적절한지, 무엇이 유용한 설명일 수 있는지에 대한 답은 HTTP의 범위 밖이라는 점에 유의하라.

HEAD 요청에 대한 응답을 제외하면, 303 응답의 표현에는 Location 헤더 필드에 제공된 것과 같은 URI 참조로 가는 하이퍼링크가 있는 짧은 하이퍼텍스트 메모가 들어 있어야 한다.

#### 15.4.5. 304 Not Modified

304(Not Modified) 상태 코드는 조건부 GET이나 HEAD 요청을 받았으며, 조건이 거짓으로 평가되지 않았다면 200(OK) 응답이 되었을 것임을 나타낸다. 다시 말해 요청을 조건부로 만든 클라이언트가 이미 유효한 표현을 가지고 있다고 요청이 나타내므로, 서버가 대상 리소스의 표현을 전송할 필요가 없다. 그래서 서버는 클라이언트가 그 저장된 표현을 200(OK) 응답의 콘텐츠인 것처럼 쓰도록 리다이렉트하는 것이다.

304 응답을 생성하는 서버는 같은 요청에 대한 200(OK) 응답에서 보냈을 다음 헤더 필드를 모두 생성해야 한다(MUST).

- Content-Location, Date, ETag, Vary
- Cache-Control과 Expires([CACHING] 참고)

304 응답의 목적은 수신자가 이미 하나 이상의 캐시된 표현을 가지고 있을 때 정보 전송을 최소화하는 것이므로, 송신자는 위에 나열한 필드 외의 표현 메타데이터를 생성하지 않아야 한다(SHOULD NOT). 단, 그 메타데이터가 캐시 갱신을 안내하기 위해 존재하는 경우는 예외이다(예: 응답에 ETag 필드가 없으면 Last-Modified가 유용할 수 있다).

304 응답을 받은 캐시에 대한 요구 사항은 [CACHING] 4.3.4절에 정의되어 있다. 자체 캐시를 가진 사용자 에이전트가 공유 프록시에 조건부 GET을 보내는 경우처럼 조건부 요청이 아웃바운드 클라이언트에서 시작되었다면, 프록시는 304 응답을 그 클라이언트에 전달해야 한다(SHOULD).

304 응답은 헤더 섹션의 끝에서 끝난다. 콘텐츠나 트레일러를 담을 수 없다.

#### 15.4.6. 305 Use Proxy

305(Use Proxy) 상태 코드는 이 명세의 이전 버전에서 정의되었으며 이제 폐기되었다([RFC7231] 부록 B).

#### 15.4.7. 306 (Unused)

306 상태 코드는 이 명세의 이전 버전에서 정의되었으나 더 이상 쓰이지 않으며, 코드는 예약되어 있다.

#### 15.4.8. 307 Temporary Redirect

307(Temporary Redirect) 상태 코드는 대상 리소스가 일시적으로 다른 URI에 있으며, 사용자 에이전트가 그 URI로 자동 리다이렉션을 수행한다면 요청 메서드를 바꿔서는 안 된다는(MUST NOT) 것을 나타낸다. 리다이렉션은 시간이 지나면서 바뀔 수 있으므로, 클라이언트는 앞으로의 요청에 원래 대상 URI를 계속 써야 한다.

서버는 응답에 다른 URI에 대한 URI 참조를 담은 Location 헤더 필드를 생성해야 한다(SHOULD). 사용자 에이전트는 자동 리다이렉션에 Location 필드 값을 쓸 수 있다(MAY). 서버의 응답 콘텐츠에는 보통 다른 URI(들)로 가는 하이퍼링크가 있는 짧은 하이퍼텍스트 메모가 들어 있다.

#### 15.4.9. 308 Permanent Redirect

308(Permanent Redirect) 상태 코드는 대상 리소스에 새 영구 URI가 할당되었으며, 이 리소스에 대한 앞으로의 참조는 담긴 URI 중 하나를 써야 한다는 것을 나타낸다. 서버는 링크 편집 기능이 있는 사용자 에이전트가 대상 URI에 대한 참조를 서버가 보낸 새 참조 중 하나로 영구히 바꿀 수 있다고 제안하는 것이다. 하지만 사용자 에이전트가 참조를 적극적으로 편집하고 있고(예: 콘텐츠를 저작하는 중), 연결이 보호되어 있고, 오리진 서버가 편집 중인 콘텐츠에 대해 신뢰할 수 있는 권한자인 경우가 아니면, 이 제안은 보통 무시된다.

서버는 응답에 새 영구 URI에 대한 선호하는 URI 참조를 담은 Location 헤더 필드를 생성해야 한다(SHOULD). 사용자 에이전트는 자동 리다이렉션에 Location 필드 값을 쓸 수 있다(MAY). 서버의 응답 콘텐츠에는 보통 새 URI(들)로 가는 하이퍼링크가 있는 짧은 하이퍼텍스트 메모가 들어 있다.

308 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

> **참고:** 이 상태 코드는 형제 코드들보다 훨씬 최근(2014년 6월)에 생겼으므로 모든 곳에서 인식되지 않을 수 있다. 배포 고려 사항은 [RFC7538] 4장을 참고하라.

### 15.5. 클라이언트 오류 4xx

4xx(Client Error) 클래스의 상태 코드는 클라이언트가 잘못한 것으로 보인다는 것을 나타낸다. HEAD 요청에 응답할 때를 제외하면, 서버는 오류 상황에 대한 설명과 그것이 일시적인 상태인지 영구적인 상태인지를 담은 표현을 보내야 한다(SHOULD). 이 상태 코드들은 모든 요청 메서드에 적용할 수 있다. 사용자 에이전트는 포함된 표현을 사용자에게 보여 줘야 한다(SHOULD).

#### 15.5.1. 400 Bad Request

400(Bad Request) 상태 코드는 클라이언트 오류로 인식되는 무언가(예: 잘못된 형식의 요청 문법, 유효하지 않은 요청 메시지 프레이밍, 기만적인 요청 라우팅) 때문에 서버가 요청을 처리할 수 없거나 처리하지 않겠다는 것을 나타낸다.

#### 15.5.2. 401 Unauthorized

401(Unauthorized) 상태 코드는 대상 리소스에 대한 유효한 인증 자격 증명이 없어서 요청이 적용되지 않았다는 것을 나타낸다. 401 응답을 생성하는 서버는 대상 리소스에 적용할 수 있는 챌린지를 적어도 하나 담은 WWW-Authenticate 헤더 필드(11.6.1절)를 보내야 한다(MUST).

요청에 인증 자격 증명이 포함되어 있었다면, 401 응답은 그 자격 증명에 대한 인가가 거부되었다는 뜻이다. 사용자 에이전트는 새로운 또는 교체한 Authorization 헤더 필드(11.6.2절)로 요청을 반복할 수 있다(MAY). 401 응답이 이전 응답과 같은 챌린지를 담고 있고 사용자 에이전트가 이미 적어도 한 번 인증을 시도했다면, 담긴 표현에는 보통 관련 진단 정보가 들어 있으므로 사용자 에이전트는 그 표현을 사용자에게 보여 줘야 한다(SHOULD).

#### 15.5.3. 402 Payment Required

402(Payment Required) 상태 코드는 나중에 쓰기 위해 예약되어 있다.

#### 15.5.4. 403 Forbidden

403(Forbidden) 상태 코드는 서버가 요청을 이해했지만 이행하기를 거부한다는 것을 나타낸다. 요청이 왜 금지되었는지 공개하고 싶은 서버는 응답 콘텐츠(있다면)에 그 이유를 설명할 수 있다.

요청에 인증 자격 증명이 제공되었다면, 서버는 그것이 접근을 허용하기에 충분하지 않다고 본 것이다. 클라이언트는 같은 자격 증명으로 요청을 자동으로 반복하지 않아야 한다(SHOULD NOT). 클라이언트는 새롭거나 다른 자격 증명으로 요청을 반복할 수 있다(MAY). 하지만 요청은 자격 증명과 관계없는 이유로 금지될 수도 있다.

금지된 대상 리소스가 현재 존재한다는 사실을 "숨기고" 싶은 오리진 서버는 대신 404(Not Found) 상태 코드로 응답할 수 있다(MAY).

#### 15.5.5. 404 Not Found

404(Not Found) 상태 코드는 오리진 서버가 대상 리소스의 현재 표현을 찾지 못했거나, 표현이 존재한다는 것을 공개하지 않겠다는 것을 나타낸다. 404 상태 코드는 표현이 없는 상태가 일시적인지 영구적인지 나타내지 않는다. 오리진 서버가 (아마도 설정 가능한 어떤 수단으로) 그 상태가 영구적일 가능성이 높다는 것을 안다면 404보다 410(Gone) 상태 코드를 선호한다.

404 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.5.6. 405 Method Not Allowed

405(Method Not Allowed) 상태 코드는 요청 라인에서 받은 메서드를 오리진 서버가 알고 있지만 대상 리소스가 지원하지 않는다는 것을 나타낸다. 오리진 서버는 405 응답에 대상 리소스가 현재 지원하는 메서드 목록을 담은 Allow 헤더 필드를 생성해야 한다(MUST).

405 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.5.7. 406 Not Acceptable

406(Not Acceptable) 상태 코드는 요청에서 받은 사전 협상 헤더 필드(12.1절)에 따르면 대상 리소스에 사용자 에이전트가 받아들일 수 있는 현재 표현이 없고, 서버가 기본 표현을 제공할 생각도 없다는 것을 나타낸다.

서버는 사용자나 사용자 에이전트가 가장 적절한 것을 고를 수 있도록, 사용 가능한 표현 특성과 대응하는 리소스 식별자의 목록을 담은 콘텐츠를 생성해야 한다(SHOULD). 사용자 에이전트는 그 목록에서 가장 적절한 선택지를 자동으로 고를 수 있다(MAY). 하지만 15.4.1절에 설명된 대로, 이 명세는 그런 자동 선택에 대한 표준을 정의하지 않는다.

#### 15.5.8. 407 Proxy Authentication Required

407(Proxy Authentication Required) 상태 코드는 401(Unauthorized)과 비슷하지만, 클라이언트가 이 요청에 프록시를 쓰려면 스스로를 인증해야 한다는 것을 나타낸다. 프록시는 그 요청에 대해 그 프록시에 적용할 수 있는 챌린지를 담은 Proxy-Authenticate 헤더 필드(11.7.1절)를 보내야 한다(MUST). 클라이언트는 새로운 또는 교체한 Proxy-Authorization 헤더 필드(11.7.2절)로 요청을 반복할 수 있다(MAY).

#### 15.5.9. 408 Request Timeout

408(Request Timeout) 상태 코드는 서버가 기다릴 준비가 된 시간 안에 완전한 요청 메시지를 받지 못했다는 것을 나타낸다.

클라이언트에게 전송 중인 응답 대기 요청이 있다면, 그 요청을 반복할 수 있다(MAY). 현재 연결을 쓸 수 없다면(예: HTTP/1.1에서 요청 경계가 사라진 경우처럼), 새 연결을 쓰게 된다.

#### 15.5.10. 409 Conflict

409(Conflict) 상태 코드는 대상 리소스의 현재 상태와의 충돌 때문에 요청을 완료할 수 없었다는 것을 나타낸다. 이 코드는 사용자가 충돌을 해결하고 요청을 다시 제출할 수 있을 만한 상황에서 쓰인다. 서버는 사용자가 충돌의 원인을 알아볼 수 있을 만큼 충분한 정보를 담은 콘텐츠를 생성해야 한다(SHOULD).

충돌은 PUT 요청에 대한 응답에서 가장 일어나기 쉽다. 예를 들어 버전 관리를 쓰고 있고, PUT으로 보내는 표현에 이전의 (제3자) 요청이 만든 변경과 충돌하는 리소스 변경이 들어 있다면, 오리진 서버는 요청을 완료할 수 없다는 것을 나타내기 위해 409 응답을 쓸 수 있다. 이 경우 응답 표현에는 수정 이력을 바탕으로 차이를 병합하는 데 유용한 정보가 들어 있을 가능성이 높다.

#### 15.5.11. 410 Gone

410(Gone) 상태 코드는 오리진 서버에서 대상 리소스에 더 이상 접근할 수 없으며 이 상태가 영구적일 가능성이 높다는 것을 나타낸다. 오리진 서버가 그 상태가 영구적인지 모르거나 판단할 수단이 없다면, 대신 404(Not Found) 상태 코드를 써야 한다.

410 응답은 주로 리소스가 의도적으로 사용할 수 없게 되었으며 서버 소유자가 그 리소스로 가는 원격 링크가 제거되기를 바란다는 것을 수신자에게 알려서 웹 유지 관리 작업을 돕기 위한 것이다. 이런 일은 기간 한정 홍보 서비스나, 더 이상 오리진 서버의 사이트와 관련 없는 개인에게 속한 리소스에서 흔하다. 영구적으로 사용할 수 없는 모든 리소스를 "gone"으로 표시하거나 그 표시를 일정 기간 유지할 필요는 없다. 그것은 서버 소유자의 재량에 맡긴다.

410 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.5.12. 411 Length Required

411(Length Required) 상태 코드는 서버가 정의된 Content-Length(8.6절) 없이는 요청을 받아들이기를 거부한다는 것을 나타낸다. 클라이언트는 요청 콘텐츠의 길이를 담은 유효한 Content-Length 헤더 필드를 추가해서 요청을 반복할 수 있다(MAY).

#### 15.5.13. 412 Precondition Failed

412(Precondition Failed) 상태 코드는 요청 헤더 필드에 주어진 하나 이상의 조건이 서버에서 검사했을 때 거짓으로 평가되었다는 것을 나타낸다(13장). 이 응답 상태 코드를 쓰면 클라이언트가 현재 리소스 상태(현재 표현과 메타데이터)에 사전 조건을 걸 수 있으며, 그래서 대상 리소스가 예상하지 못한 상태일 때 요청 메서드가 적용되는 것을 막을 수 있다.

#### 15.5.14. 413 Content Too Large

413(Content Too Large) 상태 코드는 요청 콘텐츠가 서버가 처리할 의향이 있거나 처리할 수 있는 것보다 커서 서버가 요청 처리를 거부한다는 것을 나타낸다. 사용 중인 프로토콜 버전이 허용한다면 서버는 요청을 종료할 수 있다(MAY). 그렇지 않으면 서버는 연결을 닫을 수 있다(MAY).

그 상태가 일시적이라면, 서버는 일시적이라는 것과 클라이언트가 언제 다시 시도할 수 있는지(MAY) 나타내기 위해 Retry-After 헤더 필드를 생성해야 한다(SHOULD).

#### 15.5.15. 414 URI Too Long

414(URI Too Long) 상태 코드는 대상 URI가 서버가 해석할 의향이 있는 것보다 길어서 서버가 요청 처리를 거부한다는 것을 나타낸다. 이 드문 상황은 클라이언트가 POST 요청을 긴 쿼리 정보를 가진 GET 요청으로 잘못 변환했거나, 클라이언트가 무한 리다이렉션 루프(예: 자기 자신의 접미사를 가리키는 리다이렉트된 URI 접두사)에 빠졌거나, 서버가 잠재적인 보안 허점을 악용하려는 클라이언트의 공격을 받고 있을 때만 일어날 가능성이 높다.

414 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.5.16. 415 Unsupported Media Type

415(Unsupported Media Type) 상태 코드는 콘텐츠가 대상 리소스에서 이 메서드가 지원하지 않는 형식이어서 오리진 서버가 요청 처리를 거부한다는 것을 나타낸다.

형식 문제는 요청이 나타낸 Content-Type이나 Content-Encoding 때문일 수도 있고, 데이터를 직접 살펴본 결과일 수도 있다.

지원하지 않는 콘텐츠 코딩 때문에 문제가 생겼다면, 요청에서 어떤 콘텐츠 코딩(있다면)을 받아들였을지 나타내기 위해 Accept-Encoding 응답 헤더 필드(12.5.3절)를 써야 한다.

반면 지원하지 않는 미디어 타입이 원인이라면, 요청에서 어떤 미디어 타입을 받아들였을지 나타내기 위해 Accept 응답 헤더 필드(12.5.1절)를 쓸 수 있다.

#### 15.5.17. 416 Range Not Satisfiable

416(Range Not Satisfiable) 상태 코드는 요청된 범위 중 어느 것도 충족할 수 없거나, 클라이언트가 작거나 겹치는 범위를 지나치게 많이 요청해서(잠재적인 서비스 거부 공격) 요청의 Range 헤더 필드(14.2절)에 있는 범위 집합이 거절되었다는 것을 나타낸다.

각 범위 단위는 자신의 범위 집합을 충족할 수 있으려면 무엇이 필요한지 정의한다. 예를 들어 14.1.2절은 바이트 범위 집합을 충족할 수 있게 만드는 것이 무엇인지 정의한다.

바이트 범위 요청에 416 응답을 생성하는 서버는 선택된 표현의 현재 길이를 지정하는 Content-Range 헤더 필드를 생성해야 한다(SHOULD)(14.4절).

예를 들면 다음과 같다.

```
HTTP/1.1 416 Range Not Satisfiable
Date: Fri, 20 Jan 2012 15:41:54 GMT
Content-Range: bytes */47022
```

> **참고:** 서버는 Range를 무시해도 되므로, 많은 구현이 선택된 표현 전체를 200(OK) 응답으로 보낸다. 이는 부분적으로 대부분의 클라이언트가 (덜 효율적이지만) 작업을 완료하기 위해 200(OK)을 받을 준비가 되어 있기 때문이고, 부분적으로 클라이언트가 완전한 표현을 받을 때까지 유효하지 않은 범위 요청을 멈추지 않을 수 있기 때문이다. 그래서 클라이언트는 416(Range Not Satisfiable) 응답이 가장 적절한 상황에서도 그것을 받는다고 기대할 수 없다.

#### 15.5.18. 417 Expectation Failed

417(Expectation Failed) 상태 코드는 요청의 Expect 헤더 필드(10.1.1절)에 주어진 기대 사항을 인바운드 서버 중 적어도 하나가 충족할 수 없었다는 것을 나타낸다.

#### 15.5.19. 418 (Unused)

[RFC2324]는 HTTP가 남용되는 다양한 방식을 풍자한 만우절 RFC였다. 그런 남용 중 하나가 애플리케이션 전용 418 상태 코드의 정의였는데, 이 코드는 농담으로 너무 자주 배포되어서 앞으로 다른 용도로 쓸 수 없게 되었다.

그래서 418 상태 코드는 IANA HTTP Status Code Registry에 예약되어 있다. 이는 현재 이 상태 코드를 다른 애플리케이션에 할당할 수 없다는 뜻이다. 앞으로의 상황이 그 사용을 요구한다면(예: 4NN 상태 코드가 고갈되는 경우), 다른 용도로 다시 할당할 수 있다.

#### 15.5.20. 421 Misdirected Request

421(Misdirected Request) 상태 코드는 대상 URI에 대한 권한 있는 응답을 만들 수 없거나 만들 의향이 없는 서버로 요청이 향했다는 것을 나타낸다. 오리진 서버(또는 오리진 서버를 대신하는 게이트웨이)는 서버가 설정된 오리진과 일치하지 않거나(4.3.1절), 요청을 받은 연결 컨텍스트와 일치하지 않는(7.4절) 대상 URI를 거절하기 위해 421을 보낸다.

421(Misdirected Request) 응답을 받은 클라이언트는 요청 메서드가 멱등인지와 상관없이, 대상 리소스의 오리진에 특화된 새 연결처럼 다른 연결을 통해, 또는 대체 서비스[ALTSVC]를 통해 요청을 재시도할 수 있다(MAY).

프록시는 421 응답을 생성해서는 안 된다(MUST NOT).

#### 15.5.21. 422 Unprocessable Content

422(Unprocessable Content) 상태 코드는 서버가 요청 콘텐츠의 콘텐츠 타입을 이해하고(그래서 415(Unsupported Media Type) 상태 코드는 적절하지 않다), 요청 콘텐츠의 문법도 올바르지만, 담긴 지시를 처리할 수 없었다는 것을 나타낸다. 예를 들어 XML 요청 콘텐츠가 형식은 올바르지만(즉, 문법적으로 맞지만) 의미적으로 잘못된 XML 지시를 담고 있다면 이 상태 코드를 보낼 수 있다.

#### 15.5.22. 426 Upgrade Required

426(Upgrade Required) 상태 코드는 서버가 현재 프로토콜로는 요청을 수행하기를 거부하지만, 클라이언트가 다른 프로토콜로 업그레이드한 뒤에는 수행할 의향이 있을 수 있다는 것을 나타낸다. 서버는 필요한 프로토콜(들)을 나타내기 위해 426 응답에 Upgrade 헤더 필드를 보내야 한다(MUST)(7.8절).

예시:

```
HTTP/1.1 426 Upgrade Required
Upgrade: HTTP/3.0
Connection: Upgrade
Content-Length: 53
Content-Type: text/plain

This service requires use of the HTTP/3.0 protocol.
```

### 15.6. 서버 오류 5xx

5xx(Server Error) 클래스의 상태 코드는 서버가 자신이 잘못했거나 요청된 메서드를 수행할 수 없다는 것을 알고 있다는 것을 나타낸다. HEAD 요청에 응답할 때를 제외하면, 서버는 오류 상황에 대한 설명과 그것이 일시적인 상태인지 영구적인 상태인지를 담은 표현을 보내야 한다(SHOULD). 사용자 에이전트는 포함된 표현을 사용자에게 보여 줘야 한다(SHOULD). 이 상태 코드들은 모든 요청 메서드에 적용할 수 있다.

#### 15.6.1. 500 Internal Server Error

500(Internal Server Error) 상태 코드는 서버가 요청을 이행하지 못하게 하는 예상하지 못한 상황을 만났다는 것을 나타낸다.

#### 15.6.2. 501 Not Implemented

501(Not Implemented) 상태 코드는 서버가 요청을 이행하는 데 필요한 기능을 지원하지 않는다는 것을 나타낸다. 서버가 요청 메서드를 인식하지 못하고 어떤 리소스에 대해서도 지원할 수 없을 때 적절한 응답이다.

501 응답은 휴리스틱하게 캐시 가능하다. 즉, 메서드 정의나 명시적 캐시 제어가 달리 나타내지 않는 한 그렇다([CACHING] 4.2.2절 참고).

#### 15.6.3. 502 Bad Gateway

502(Bad Gateway) 상태 코드는 서버가 게이트웨이나 프록시로 동작하면서, 요청을 이행하려고 접근한 인바운드 서버로부터 유효하지 않은 응답을 받았다는 것을 나타낸다.

#### 15.6.4. 503 Service Unavailable

503(Service Unavailable) 상태 코드는 일시적인 과부하나 예정된 유지 보수 때문에 서버가 현재 요청을 처리할 수 없으며, 얼마 뒤에는 해소될 가능성이 높다는 것을 나타낸다. 서버는 클라이언트가 요청을 재시도하기 전에 기다릴 적절한 시간을 제안하기 위해 Retry-After 헤더 필드(10.2.3절)를 보낼 수 있다(MAY).

> **참고:** 503 상태 코드가 있다고 해서 서버가 과부하 상태가 될 때 반드시 이를 써야 하는 것은 아니다. 일부 서버는 그냥 연결을 거부할 수도 있다.

#### 15.6.5. 504 Gateway Timeout

504(Gateway Timeout) 상태 코드는 서버가 게이트웨이나 프록시로 동작하면서, 요청을 완료하기 위해 접근해야 했던 업스트림 서버로부터 제때 응답을 받지 못했다는 것을 나타낸다.

#### 15.6.6. 505 HTTP Version Not Supported

505(HTTP Version Not Supported) 상태 코드는 서버가 요청 메시지에 쓰인 HTTP 메이저 버전을 지원하지 않거나 지원하기를 거부한다는 것을 나타낸다. 서버는 2.5절에 설명된 대로, 이 오류 메시지 말고는 클라이언트와 같은 메이저 버전으로 요청을 완료할 수 없거나 그럴 의향이 없다는 것을 나타내는 것이다. 서버는 505 응답에 왜 그 버전을 지원하지 않는지, 그리고 그 서버가 다른 어떤 프로토콜을 지원하는지 설명하는 표현을 생성해야 한다(SHOULD).
