# RFC 9112 — HTTP/1.1 (한국어 번역)

> 이 문서는 [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112)의 비공식 한국어 번역이다. 원문과 차이가 있으면 원문이 우선한다.
> 요구 수준 키워드(MUST, SHOULD, MAY 등)는 번역문 뒤에 괄호로 원어를 함께 적었다. ABNF 문법과 예시는 원문 그대로 두었다.
> 13장(참고 문헌), 감사의 글, 색인, 저자 주소는 번역하지 않았다.

- 원문 저자: R. Fielding(편집, Adobe), M. Nottingham(편집, Fastly), J. Reschke(편집, greenbytes)
- 발행: 2022년 6월 · IETF Standards Track · STD 99 · RFC 7230 대체

## 초록

HTTP(Hypertext Transfer Protocol)는 분산·협업형 하이퍼텍스트 정보 시스템을 위한 무상태(stateless) 애플리케이션 계층 프로토콜이다. 이 문서는 HTTP/1.1의 메시지 문법, 메시지 파싱, 연결 관리, 그리고 관련 보안 문제를 정의한다.

이 문서는 RFC 7230의 일부를 대체한다.

## 1. 소개

HTTP(Hypertext Transfer Protocol)는 확장 가능한 의미론과 자기 서술적(self-descriptive) 메시지를 사용해 네트워크 기반 하이퍼텍스트 정보 시스템과 유연하게 상호작용하는 무상태 애플리케이션 계층 요청/응답 프로토콜이다. HTTP/1.1은 다음 문서들로 정의된다.

- 이 문서
- "HTTP Semantics" [HTTP] (RFC 9110)
- "HTTP Caching" [CACHING] (RFC 9111)

이 문서는 HTTP/1.1의 메시지 문법, 프레이밍(framing), 연결 관리 메커니즘을 사용해 HTTP 의미론이 어떻게 전달되는지를 정의한다. 목표는 HTTP/1.1 메시지 파서와 메시지를 전달하는 중개자(intermediary)가 따라야 할 요구 사항 전체를 정의하는 것이다.

이 문서는 RFC 7230 중 HTTP/1.1 메시징과 연결 관리에 관한 부분을 대체하며, 변경 사항은 부록 C.3에 요약되어 있다. RFC 7230의 나머지 부분은 "HTTP Semantics" [HTTP]가 대체한다.

### 1.1. 요구 사항 표기

이 문서의 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"은 여기 보인 것처럼 모두 대문자로 쓰였을 때, 그리고 그때에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석한다.

> 번역 관례: MUST/REQUIRED/SHALL = "반드시 ~해야 한다", MUST NOT/SHALL NOT = "절대 ~해서는 안 된다", SHOULD/RECOMMENDED = "~해야 한다(권장)", SHOULD NOT/NOT RECOMMENDED = "~하지 않아야 한다(권장)", MAY/OPTIONAL = "~할 수 있다".

적합성 기준과 오류 처리에 관한 고려 사항은 [HTTP]의 2장에 정의되어 있다.

### 1.2. 문법 표기

이 명세는 [RFC5234]의 ABNF(Augmented Backus-Naur Form) 표기법을 사용하며, [RFC7405]에 정의된 문자열 대소문자 구분 표기를 확장으로 사용한다.

또한 [HTTP] 5.6.1절에 정의된 리스트 확장을 사용한다. 이 확장은 "#" 연산자로 쉼표로 구분된 리스트를 간결하게 정의할 수 있게 해 준다("*" 연산자가 반복을 나타내는 것과 비슷하다). 부록 A에는 모든 리스트 연산자를 표준 ABNF 표기로 풀어 쓴 전체 문법이 있다.

관례상 "obs-"로 시작하는 ABNF 규칙 이름은 역사적인 이유로 남아 있는 폐기된(obsolete) 문법 규칙을 뜻한다.

다음 핵심 규칙은 [RFC5234] 부록 B.1의 정의를 참조로 포함한다: ALPHA(영문자), CR(캐리지 리턴), CRLF(CR LF), CTL(제어 문자), DIGIT(10진 숫자 0-9), DQUOTE(큰따옴표), HEXDIG(16진 숫자 0-9/A-F/a-f), HTAB(수평 탭), LF(라인 피드), OCTET(임의의 8비트 데이터), SP(공백), VCHAR(눈에 보이는 [USASCII] 문자).

다음 규칙은 [HTTP]에 정의되어 있다.

```
  BWS           = <BWS, see [HTTP], Section 5.6.3>
  OWS           = <OWS, see [HTTP], Section 5.6.3>
  RWS           = <RWS, see [HTTP], Section 5.6.3>
  absolute-path = <absolute-path, see [HTTP], Section 4.1>
  field-name    = <field-name, see [HTTP], Section 5.1>
  field-value   = <field-value, see [HTTP], Section 5.5>
  obs-text      = <obs-text, see [HTTP], Section 5.6.4>
  quoted-string = <quoted-string, see [HTTP], Section 5.6.4>
  token         = <token, see [HTTP], Section 5.6.2>
  transfer-coding =
                  <transfer-coding, see [HTTP], Section 10.1.4>
```

다음 규칙은 [URI]에 정의되어 있다.

```
  absolute-URI  = <absolute-URI, see [URI], Section 4.3>
  authority     = <authority, see [URI], Section 3.2>
  uri-host      = <host, see [URI], Section 3.2.2>
  port          = <port, see [URI], Section 3.2.3>
  query         = <query, see [URI], Section 3.4>
```

## 2. 메시지

HTTP/1.1 클라이언트와 서버는 메시지를 보내 통신한다. HTTP의 일반 용어와 핵심 개념은 [HTTP]의 3장을 보라.

### 2.1. 메시지 형식

HTTP/1.1 메시지는 시작 줄(start-line)과 그 뒤의 CRLF, 그리고 인터넷 메시지 형식 [RFC5322]과 비슷한 형식의 옥텟 시퀀스로 이루어진다. 이 시퀀스는 0개 이상의 헤더 필드 줄(통틀어 "헤더" 또는 "헤더 섹션"이라 부른다), 헤더 섹션의 끝을 나타내는 빈 줄, 그리고 선택적인 메시지 본문으로 구성된다.

```
  HTTP-message   = start-line CRLF
                   *( field-line CRLF )
                   CRLF
                   [ message-body ]
```

메시지는 클라이언트가 서버에 보내는 요청일 수도 있고, 서버가 클라이언트에 보내는 응답일 수도 있다. 문법적으로 두 메시지는 시작 줄(요청이면 request-line, 응답이면 status-line)과 메시지 본문 길이를 결정하는 알고리즘(6장)에서만 차이가 난다.

```
  start-line     = request-line / status-line
```

이론적으로는 클라이언트가 요청을 받고 서버가 응답을 받으면서 시작 줄 형식으로 둘을 구분할 수도 있다. 하지만 실제로 서버는 요청만 받는다고 가정하고 구현되며(응답을 받으면 알 수 없거나 잘못된 요청 메서드로 해석한다), 클라이언트는 응답만 받는다고 가정하고 구현된다.

HTTP는 MIME(Multipurpose Internet Mail Extensions) [RFC2045]와 비슷한 프로토콜 요소를 일부 사용한다. HTTP 메시지와 MIME 메시지의 차이는 부록 B를 보라.

### 2.2. 메시지 파싱

HTTP 메시지를 파싱하는 일반적인 절차는 다음과 같다. 시작 줄을 읽어 구조체에 담고, 빈 줄이 나올 때까지 각 헤더 필드 줄을 필드 이름 기준으로 해시 테이블에 읽어 들인 뒤, 파싱한 데이터를 보고 메시지 본문이 있는지 판단한다. 메시지 본문이 있다고 표시되어 있으면, 메시지 본문 길이만큼의 옥텟을 읽거나 연결이 닫힐 때까지 본문을 스트림으로 읽는다.

수신자는 HTTP 메시지를 US-ASCII [USASCII]의 상위 집합인 인코딩의 옥텟 시퀀스로 파싱해야 한다(MUST). 특정 인코딩을 고려하지 않고 HTTP 메시지를 유니코드 문자 스트림으로 파싱하면 보안 취약점이 생긴다. 문자열 처리 라이브러리마다 옥텟 LF(%x0A)를 포함한 잘못된 멀티바이트 문자 시퀀스를 다루는 방식이 다르기 때문이다. 문자열 기반 파서는 메시지에서 프로토콜 요소를 추출한 다음에만 그 요소 안에서 안전하게 쓸 수 있다. 예를 들어 메시지 파싱으로 각 필드 줄의 경계를 구분한 뒤, 헤더 필드 줄의 값 안에서 쓰는 것은 안전하다.

시작 줄과 필드의 줄 종결자는 CRLF 시퀀스이지만, 수신자는 LF 하나만 있어도 줄 종결자로 인식하고 그 앞의 CR은 무시할 수 있다(MAY).

송신자는 콘텐츠를 제외한 프로토콜 요소 안에 단독 CR(바로 뒤에 LF가 오지 않는 CR 문자)을 절대 생성해서는 안 된다(MUST NOT). 이런 단독 CR을 받은 수신자는 그 요소를 잘못된 것으로 간주하거나, 요소를 처리하거나 메시지를 전달하기 전에 각 단독 CR을 SP로 바꿔야 한다(MUST).

예전 HTTP/1.0 사용자 에이전트 구현 중에는 줄 끝으로 끝나지 않은 메시지 본문을 읽지 못하는 초기 서버 애플리케이션을 우회하려고 POST 요청 뒤에 CRLF를 하나 더 보내는 경우가 있었다. HTTP/1.1 사용자 에이전트는 요청 앞이나 뒤에 추가 CRLF를 절대 붙여서는 안 된다(MUST NOT). 요청 메시지 본문을 줄 끝으로 끝내고 싶다면, 사용자 에이전트는 마지막 CRLF 옥텟을 메시지 본문 길이에 포함해서 세야 한다(MUST).

견고성을 위해, 요청 라인을 받아 파싱하려는 서버는 요청 라인 앞에 받은 빈 줄(CRLF)을 적어도 하나는 무시해야 한다(SHOULD).

송신자는 시작 줄과 첫 번째 헤더 필드 사이에 공백을 절대 보내서는 안 된다(MUST NOT).

시작 줄과 첫 번째 헤더 필드 사이에서 공백을 받은 수신자는 메시지를 잘못된 것으로 거부하거나, 공백으로 시작하는 각 줄을 더 이상 처리하지 않고 소비해야 한다(MUST). 즉, 올바른 형식의 헤더 필드를 받거나 헤더 섹션이 끝날 때까지, 그 줄과 그 뒤에 이어지는 공백으로 시작하는 줄 전체를 무시한다. 공백으로 시작하는 잘못된 줄을 거부하거나 제거하는 것은, 요청 스머글링(11.2절)이나 응답 분할(11.1절) 공격에 취약할 수 있는 하위(downstream) 수신자가 이를 잘못 해석하지 않도록 하기 위해 필요하다.

HTTP 요청 메시지만 받는 서버, 또는 시작 줄을 보아 HTTP 요청 메시지로 보이는 것을 처리하는 서버가, 위에 나열한 견고성 예외를 제외하고 HTTP-message 문법에 맞지 않는 옥텟 시퀀스를 받으면 400(Bad Request) 응답을 보내고 연결을 닫아야 한다(SHOULD).

### 2.3. HTTP 버전

HTTP는 프로토콜 버전을 나타내기 위해 "<major>.<minor>" 번호 체계를 사용한다. 이 명세는 버전 "1.1"을 정의한다. HTTP 버전 번호의 의미는 [HTTP] 2.5절에 정의되어 있다.

HTTP/1.x 메시지의 버전은 시작 줄의 HTTP-version 필드로 나타낸다. HTTP-version은 대소문자를 구분한다.

```
  HTTP-version  = HTTP-name "/" DIGIT "." DIGIT
  HTTP-name     = %s"HTTP"
```

HTTP/1.1 메시지를 HTTP/1.0 수신자 [HTTP/1.0]나 버전을 알 수 없는 수신자에게 보낼 때, HTTP/1.1 메시지는 새로운 기능을 모두 무시하면 유효한 HTTP/1.0 메시지로 해석될 수 있도록 구성된다. 이 명세는 일부 새 기능에 수신자 버전 요구 사항을 두어, 적합한 송신자가 설정이나 메시지 수신을 통해 수신자가 HTTP/1.1을 지원한다는 것을 확인하기 전까지는 호환되는 기능만 쓰도록 한다.

HTTP 메시지를 처리하는 중개자(즉, 터널로 동작하는 것을 제외한 모든 중개자)는 상위(upstream) 문제를 우회하기 위해 의도적으로 버전을 낮추는 경우가 아니라면, 전달하는 메시지에 자기 자신의 HTTP-version을 넣어 보내야 한다(MUST). 다시 말해, 중개자는 메시지의 프로토콜 버전이 자신이 송수신 양쪽 모두에서 적합하게 지원하는 버전인지 확인하지 않고 시작 줄을 그대로 전달해서는 안 된다. HTTP-version을 다시 쓰지 않고 HTTP 메시지를 전달하면, 하위 수신자가 메시지 송신자의 버전을 보고 이후 그 송신자와의 통신에서 어떤 기능을 안전하게 쓸 수 있는지 판단할 때 통신 오류가 생길 수 있다.

서버는 클라이언트가 HTTP 명세를 잘못 구현해서 상위 버전 응답을 제대로 처리하지 못한다는 것이 알려져 있거나 의심되는 경우, HTTP/1.1 요청에 HTTP/1.0 응답을 보낼 수 있다(MAY). 예를 들어 클라이언트가 버전 번호를 제대로 파싱하지 못하거나, 어떤 중개자가 해당 마이너 버전에 적합하지 않은데도 HTTP-version을 그대로 전달한다고 알려진 경우가 그렇다. 이런 프로토콜 다운그레이드는 특정 클라이언트 속성으로 촉발된 경우가 아니라면 하지 않아야 한다(SHOULD NOT). 예를 들어 하나 이상의 요청 헤더 필드(예: User-Agent)가 오류가 있다고 알려진 클라이언트가 보내는 값과 정확히 일치하는 경우가 그런 속성에 해당한다.

## 3. 요청 라인

요청 라인(request-line)은 메서드 토큰으로 시작하고, 공백 하나(SP), 요청 대상(request-target), 다시 공백 하나(SP)가 이어진 뒤, 프로토콜 버전으로 끝난다.

```
  request-line   = method SP request-target SP HTTP-version
```

요청 라인 문법 규칙은 각 구성 요소가 SP 옥텟 하나로 구분되어야 한다고 정하지만, 수신자는 대신 공백으로 구분된 단어 경계로 파싱할 수 있으며(MAY), CRLF 종결자를 제외한 모든 형태의 공백을 SP 구분자로 취급하고 앞뒤 공백은 무시할 수 있다. 여기서 공백은 SP, HTAB, VT(%x0B), FF(%x0C), 단독 CR 중 하나 이상의 옥텟을 말한다. 하지만 이렇게 관대하게 파싱하면, 메시지 수신자가 여럿이고 각자 견고성을 다르게 해석할 때 요청 스머글링 보안 취약점이 생길 수 있다(11.2절 참조).

[HTTP] 2.3절에 설명된 것처럼, HTTP는 요청 라인 길이에 미리 정한 제한을 두지 않는다. 자신이 구현한 어떤 메서드보다 긴 메서드를 받은 서버는 501(Not Implemented) 상태 코드로 응답해야 한다(SHOULD). 파싱하려는 어떤 URI보다 긴 요청 대상을 받은 서버는 반드시 414(URI Too Long) 상태 코드로 응답해야 한다(MUST)([HTTP] 15.5.15절 참조).

실제로는 요청 라인 길이에 대한 다양한 임시 제한이 존재한다. 모든 HTTP 송신자와 수신자는 최소 8000옥텟 길이의 요청 라인을 지원할 것을 권장한다(RECOMMENDED).

### 3.1. 메서드

메서드 토큰은 대상 리소스에 수행할 요청 메서드를 나타낸다. 요청 메서드는 대소문자를 구분한다.

```
  method         = token
```

이 명세가 정의하는 요청 메서드는 [HTTP] 9장에 있으며, HTTP 메서드 레지스트리와 새 메서드 정의 시 고려 사항도 함께 설명되어 있다.

### 3.2. 요청 대상

요청 대상(request-target)은 요청을 적용할 대상 리소스를 식별한다. 클라이언트는 원하는 대상 URI로부터 요청 대상을 만든다. 요청 대상에는 요청하는 메서드와 프록시로 보내는 요청인지에 따라 네 가지 형식이 있다.

```
  request-target = origin-form
                 / absolute-form
                 / authority-form
                 / asterisk-form
```

요청 대상에는 공백이 허용되지 않는다. 안타깝게도 일부 사용자 에이전트는 하이퍼텍스트 참조에 있는 공백을 제대로 인코딩하거나 제외하지 못해서, 허용되지 않는 문자가 잘못된 형식의 요청 라인 안에 요청 대상으로 전송되기도 한다.

잘못된 요청 라인을 받은 수신자는 400(Bad Request) 오류로 응답하거나, 요청 대상을 올바르게 인코딩한 301(Moved Permanently) 리다이렉트로 응답해야 한다(SHOULD). 수신자는 리다이렉트 없이 자동으로 고쳐서 요청을 처리하려 하지 않아야 한다(SHOULD NOT). 잘못된 요청 라인은 요청 경로상의 보안 필터를 우회하려고 의도적으로 만든 것일 수 있기 때문이다.

클라이언트는 모든 HTTP/1.1 요청 메시지에 Host 헤더 필드([HTTP] 7.2절)를 반드시 보내야 한다(MUST). 대상 URI에 authority 구성 요소가 있으면, 클라이언트는 userinfo 하위 구성 요소와 그 구분자 "@"를 제외하고 그 authority 구성 요소와 똑같은 Host 필드 값을 반드시 보내야 한다(MUST)([HTTP] 4.2절). 대상 URI에 authority 구성 요소가 없거나 정의되지 않았으면, 클라이언트는 빈 필드 값의 Host 헤더 필드를 반드시 보내야 한다(MUST).

서버는 Host 헤더 필드가 없는 HTTP/1.1 요청 메시지, Host 헤더 필드 줄이 둘 이상인 요청 메시지, 또는 Host 헤더 필드 값이 잘못된 요청 메시지에 반드시 400(Bad Request) 상태 코드로 응답해야 한다(MUST).

#### 3.2.1. origin-form

가장 흔한 요청 대상 형식은 "origin-form"이다.

```
  origin-form    = absolute-path [ "?" query ]
```

오리진 서버에 직접 요청할 때, CONNECT 요청이나 서버 전체 대상 OPTIONS 요청(아래에서 설명)이 아니라면, 클라이언트는 대상 URI의 절대 경로(absolute path)와 쿼리 구성 요소만 요청 대상으로 보내야 한다(MUST). 대상 URI의 경로 구성 요소가 비어 있으면, 클라이언트는 origin-form 요청 대상의 경로로 "/"를 보내야 한다(MUST). [HTTP] 7.2절에 정의된 대로 Host 헤더 필드도 함께 보낸다.

예를 들어 다음과 같이 식별되는 리소스의 표현을

```
  http://www.example.org/where?q=now
```

오리진 서버에서 직접 가져오려는 클라이언트는 호스트 "www.example.org"의 80번 포트로 TCP 연결을 열거나 재사용하고, 다음 줄들을 보낸다.

```
GET /where?q=now HTTP/1.1
Host: www.example.org
```

그 뒤에 요청 메시지의 나머지 부분이 이어진다.

#### 3.2.2. absolute-form

프록시에 요청할 때, CONNECT 요청이나 서버 전체 대상 OPTIONS 요청(아래에서 설명)이 아니라면, 클라이언트는 대상 URI를 "absolute-form"으로 요청 대상에 넣어 보내야 한다(MUST).

```
  absolute-form  = absolute-URI
```

프록시는 가능하면 유효한 캐시로 요청을 처리하거나, 클라이언트를 대신해 다음 내부(inbound) 프록시 서버나 요청 대상이 가리키는 오리진 서버에 같은 요청을 보내도록 요청받는다. 이런 메시지 "전달(forwarding)"에 대한 요구 사항은 [HTTP] 7.6절에 정의되어 있다.

absolute-form 요청 라인의 예는 다음과 같다.

```
GET http://www.example.org/pub/WWW/TheProject.html HTTP/1.1
```

요청 대상이 absolute-form이더라도 클라이언트는 HTTP/1.1 요청에 Host 헤더 필드를 반드시 보내야 한다(MUST). 그래야 Host를 구현하지 않았을 수 있는 오래된 HTTP/1.0 프록시를 거쳐서도 Host 정보가 전달될 수 있다.

프록시가 absolute-form 요청 대상을 가진 요청을 받으면, 받은 Host 헤더 필드(있다면)를 반드시 무시하고 요청 대상의 호스트 정보로 대체해야 한다(MUST). 이런 요청을 전달하는 프록시는 받은 Host 필드 값을 그대로 전달하지 말고, 받은 요청 대상을 바탕으로 새 Host 필드 값을 반드시 생성해야 한다(MUST).

오리진 서버가 absolute-form 요청 대상을 가진 요청을 받으면, 받은 Host 헤더 필드(있다면)를 반드시 무시하고 요청 대상의 호스트 정보를 사용해야 한다(MUST). 이 경우 요청 대상에 authority 구성 요소가 없으면 빈 Host 헤더 필드가 전송된다는 점에 유의하라.

대부분의 HTTP/1.1 클라이언트는 absolute-form을 프록시에만 보내지만, 서버는 요청에 쓰인 absolute-form을 반드시 받아들여야 한다(MUST).

#### 3.2.3. authority-form

"authority-form" 요청 대상은 CONNECT 요청([HTTP] 9.3.6절)에서만 쓰인다. 터널 목적지의 uri-host와 포트 번호를 콜론(":")으로 구분해 적은 것만으로 이루어진다.

```
  authority-form = uri-host ":" port
```

하나 이상의 프록시를 거치는 터널을 만들기 위해 CONNECT 요청을 보낼 때, 클라이언트는 터널 목적지의 호스트와 포트만 요청 대상으로 보내야 한다(MUST). 클라이언트는 대상 URI의 authority 구성 요소에서 호스트와 포트를 얻되, 대상 URI에 포트가 생략되어 있으면 스킴의 기본 포트를 보낸다. 예를 들어 "http://www.example.com"으로의 CONNECT 요청은 다음과 같다.

```
CONNECT www.example.com:80 HTTP/1.1
Host: www.example.com
```

#### 3.2.4. asterisk-form

"asterisk-form" 요청 대상은 서버 전체를 대상으로 하는 OPTIONS 요청([HTTP] 9.3.7절)에서만 쓰인다.

```
  asterisk-form  = "*"
```

클라이언트가 서버의 특정 리소스가 아니라 서버 전체에 대해 OPTIONS를 요청하려면, 요청 대상으로 "*"(%x2A)만 보내야 한다(MUST). 예를 들면 다음과 같다.

```
OPTIONS * HTTP/1.1
```

프록시가 URI의 경로가 비어 있고 쿼리 구성 요소도 없는 absolute-form 요청 대상을 가진 OPTIONS 요청을 받으면, 요청 경로의 마지막 프록시는 그 요청을 지정된 오리진 서버로 전달할 때 요청 대상으로 "*"를 보내야 한다(MUST).

예를 들어 다음 요청은

```
OPTIONS http://www.example.org:8001 HTTP/1.1
```

마지막 프록시가 호스트 "www.example.org"의 8001번 포트에 연결한 뒤 다음과 같이 전달한다.

```
OPTIONS * HTTP/1.1
Host: www.example.org:8001
```

### 3.3. 대상 URI 재구성

요청 대상이 absolute-form이면 요청 대상이 곧 대상 URI이다. 이 경우 서버는 URI를 일반 구성 요소로 파싱해 추가로 평가한다.

그렇지 않으면, 서버는 대상 리소스를 식별하기 위해 연결 컨텍스트와 요청 메시지의 여러 부분으로부터 대상 URI를 재구성한다([HTTP] 7.1절).

- 서버 설정이 고정된 URI 스킴을 제공하거나 신뢰할 수 있는 외부(outbound) 게이트웨이가 스킴을 제공하면, 그 스킴을 대상 URI에 사용한다. 대규모 배포에서는 흔한 일이다. 게이트웨이 서버가 클라이언트의 연결 컨텍스트를 받아 내부(inbound) 서버로의 자기 연결로 대체하기 때문이다. 그렇지 않은 경우, 보안 연결로 요청을 받았으면 대상 URI의 스킴은 "https"이고, 아니면 "http"이다.
- 요청 대상이 authority-form이면 대상 URI의 authority 구성 요소는 요청 대상이다. 그렇지 않으면 대상 URI의 authority 구성 요소는 Host 헤더 필드의 값이다. Host 헤더 필드가 없거나 그 값이 비어 있거나 잘못되었으면 대상 URI의 authority 구성 요소는 비어 있다.
- 요청 대상이 authority-form이거나 asterisk-form이면 대상 URI의 경로와 쿼리를 합친 구성 요소는 비어 있다. 그렇지 않으면 대상 URI의 경로와 쿼리를 합친 구성 요소는 요청 대상이다.
- 위와 같이 결정된 재구성 대상 URI의 구성 요소는 스킴, "://", authority, 경로와 쿼리를 합친 구성 요소를 이어 붙여 absolute-URI 형식으로 다시 합칠 수 있다.

예시 1: 보안 연결로 받은 다음 메시지는

```
GET /pub/WWW/TheProject.html HTTP/1.1
Host: www.example.org
```

대상 URI가 다음과 같다.

```
  https://www.example.org/pub/WWW/TheProject.html
```

예시 2: 보안이 적용되지 않은 연결로 받은 다음 메시지는

```
OPTIONS * HTTP/1.1
Host: www.example.org:8080
```

대상 URI가 다음과 같다.

```
  http://www.example.org:8080
```

대상 URI의 authority 구성 요소가 비어 있고 그 URI 스킴이 비어 있지 않은 authority를 요구한다면("http"와 "https"가 그렇다), 서버는 요청을 거부하거나, 들어온 연결의 컨텍스트와 일치하는 설정된 기본값을 적용할지 판단할 수 있다. 컨텍스트에는 주소와 포트 같은 연결 세부 정보, 적용된 보안, 그 서버 설정에 특화된 로컬 정보가 포함될 수 있다. 빈 authority는 요청을 더 처리하기 전에 설정된 기본값으로 대체된다.

보안 연결의 컨텍스트에서 authority의 기본 이름을 제공하는 것은, 사용자 에이전트가 의도한 authority가 기본값과 다를 가능성이 조금이라도 있다면 본질적으로 안전하지 않다. 요청 컨텍스트로부터 authority를 유일하게 식별할 수 있는 서버는 이런 위험 없이 그 식별 정보를 기본값으로 사용할 수 있다(MAY). 아니면 새 클라이언트를 얻는 방법을 설명하는 안전한 리소스로 요청을 리다이렉트하는 편이 나을 수도 있다.

클라이언트의 대상 URI를 재구성하는 것은 대상 리소스를 식별하는 과정의 절반일 뿐이라는 점에 유의하라. 나머지 절반은 [HTTP] 7.4절에 정의된 대로, 그 대상 URI가 서버가 응답을 보낼 의지와 능력이 있는 리소스를 식별하는지 판단하는 것이다.

## 4. 상태 라인

응답 메시지의 첫 줄은 상태 라인(status-line)이다. 프로토콜 버전, 공백(SP), 상태 코드, 다시 공백이 오고, 상태 코드를 설명하는 선택적(OPTIONAL) 텍스트 문구로 끝난다.

```
  status-line = HTTP-version SP status-code SP [ reason-phrase ]
```

상태 라인 문법 규칙은 각 구성 요소가 SP 옥텟 하나로 구분되어야 한다고 정하지만, 수신자는 대신 공백으로 구분된 단어 경계로 파싱할 수 있으며(MAY), 줄 종결자를 제외한 모든 형태의 공백을 SP 구분자로 취급하고 앞뒤 공백은 무시할 수 있다. 여기서 공백은 SP, HTAB, VT(%x0B), FF(%x0C), 단독 CR 중 하나 이상의 옥텟을 말한다. 하지만 이렇게 관대하게 파싱하면, 메시지 수신자가 여럿이고 각자 견고성을 다르게 해석할 때 응답 분할 보안 취약점이 생길 수 있다(11.1절 참조).

status-code 요소는 클라이언트의 요청을 이해하고 처리하려 한 서버의 시도 결과를 나타내는 3자리 정수 코드이다. 수신자가 그 상태 코드를 알고 있으면 그 상태 코드에 정의된 의미에 비추어, 특정 코드를 모르면 그 상태 코드의 분류(class)에 따라 응답 메시지의 나머지를 파싱하고 해석한다.

```
  status-code    = 3DIGIT
```

HTTP의 핵심 상태 코드는 [HTTP] 15장에 정의되어 있으며, 상태 코드 분류, 새 상태 코드 정의 시 고려 사항, 그런 정의를 모으는 IANA 레지스트리도 함께 설명되어 있다.

reason-phrase 요소는 숫자 상태 코드에 연관된 텍스트 설명을 제공하는 목적으로만 존재한다. 주로 대화형 텍스트 클라이언트에서 더 자주 쓰이던 초기 인터넷 애플리케이션 프로토콜을 존중하기 위한 것이다.

```
  reason-phrase  = 1*( HTAB / SP / VCHAR / obs-text )
```

클라이언트는 reason-phrase 내용을 무시해야 한다(SHOULD). 이 내용은 신뢰할 수 있는 정보 전달 수단이 아니기 때문이다(특정 로케일에 맞게 번역되거나, 중개자가 덮어쓰거나, 다른 HTTP 버전을 거쳐 전달될 때 버려질 수 있다). 서버는 reason-phrase가 없더라도 status-code와 reason-phrase를 구분하는 공백을 반드시 보내야 한다(MUST)(즉, 상태 라인이 공백으로 끝나게 된다).

## 5. 필드 문법

각 필드 줄은 대소문자를 구분하지 않는 필드 이름, 콜론(":"), 선택적인 앞쪽 공백, 필드 줄 값, 선택적인 뒤쪽 공백으로 이루어진다.

```
  field-line   = field-name ":" OWS field-value OWS
```

필드 값 내부의 파싱 규칙은 [HTTP] 5.5절에 정의되어 있다. 이 절은 HTTP/1.1 메시지에 헤더 필드를 넣고 꺼내는 일반 문법을 다룬다.

### 5.1. 필드 줄 파싱

메시지는 개별 필드 이름과 상관없는 일반적인 알고리즘으로 파싱한다. 특정 필드 줄 값의 내용은 메시지 해석의 이후 단계(보통 메시지의 필드 섹션 전체를 처리한 뒤)가 되어서야 파싱한다.

필드 이름과 콜론 사이에는 공백이 허용되지 않는다. 과거에 이런 공백을 다루는 방식의 차이 때문에 요청 라우팅과 응답 처리에서 보안 취약점이 생겼다. 서버는 헤더 필드 이름과 콜론 사이에 공백이 있는 요청 메시지를 받으면 반드시 400(Bad Request) 응답 상태 코드로 거부해야 한다(MUST). 프록시는 응답 메시지를 하위로 전달하기 전에 그런 공백을 반드시 제거해야 한다(MUST).

필드 줄 값 앞뒤에는 선택적 공백(OWS)이 올 수 있다. 사람이 일관되게 읽기 쉽도록 필드 줄 값 앞에 SP 하나를 두는 것이 좋다. 필드 줄 값에는 그 앞뒤 공백이 포함되지 않는다. 즉, 파서는 필드 줄에서 필드 줄 값을 추출할 때 필드 줄 값의 공백이 아닌 첫 옥텟 앞, 또는 공백이 아닌 마지막 옥텟 뒤에 있는 OWS를 제외한다.

### 5.2. 폐기된 줄 접기

과거에는 HTTP/1.x 필드 값을 여러 줄에 걸쳐 확장할 수 있었다. 추가되는 각 줄 앞에 공백이나 수평 탭을 하나 이상 두는 방식이다(obs-fold). 이 명세는 "message/http" 미디어 타입(10.1절) 안에서를 제외하고 이런 줄 접기를 폐기한다.

```
  obs-fold     = OWS CRLF RWS
               ; obsolete line folding
```

송신자는 메시지를 "message/http" 미디어 타입 안에 담을 목적이 아니라면, 줄 접기를 포함한 메시지(즉, obs-fold 규칙에 맞는 부분을 포함한 필드 줄 값이 있는 메시지)를 절대 생성해서는 안 된다(MUST NOT).

"message/http" 컨테이너 안에 있지 않은 요청 메시지에서 obs-fold를 받은 서버는, 400(Bad Request)을 보내 메시지를 거부하거나(가능하면 폐기된 줄 접기를 받아들일 수 없다고 설명하는 표현과 함께), 필드 값을 해석하거나 메시지를 하위로 전달하기 전에 받은 각 obs-fold를 하나 이상의 SP 옥텟으로 바꿔야 한다(MUST).

"message/http" 컨테이너 안에 있지 않은 응답 메시지에서 obs-fold를 받은 프록시나 게이트웨이는, 메시지를 버리고 502(Bad Gateway) 응답으로 대체하거나(가능하면 받아들일 수 없는 줄 접기를 받았다고 설명하는 표현과 함께), 필드 값을 해석하거나 메시지를 하위로 전달하기 전에 받은 각 obs-fold를 하나 이상의 SP 옥텟으로 바꿔야 한다(MUST).

"message/http" 컨테이너 안에 있지 않은 응답 메시지에서 obs-fold를 받은 사용자 에이전트는 필드 값을 해석하기 전에 받은 각 obs-fold를 하나 이상의 SP 옥텟으로 바꿔야 한다(MUST).

## 6. 메시지 본문

HTTP/1.1 메시지의 메시지 본문(있다면)은 요청이나 응답의 콘텐츠([HTTP] 6.4절)를 운반하는 데 쓰인다. 6.1절에 설명된 전송 코딩이 적용되지 않았다면 메시지 본문은 콘텐츠와 똑같다.

```
  message-body = *OCTET
```

HTTP/1.1 메시지에 메시지 본문이 있는지 판단하는 규칙은 요청과 응답이 다르다.

요청에 메시지 본문이 있다는 것은 Content-Length 또는 Transfer-Encoding 헤더 필드로 알린다. 요청 메시지의 프레이밍은 메서드 의미와 무관하다.

6.3절에서 자세히 설명하듯이, 응답에 메시지 본문이 있는지는 응답하는 요청의 메서드와 응답 상태 코드 둘 다에 달려 있다. 이는 HTTP 의미론에서 응답 콘텐츠가 허용되는 경우([HTTP] 6.4.1절)에 해당한다.

### 6.1. Transfer-Encoding

Transfer-Encoding 헤더 필드는 메시지 본문을 만들기 위해 콘텐츠에 적용된(또는 적용될) 전송 코딩 순서에 해당하는 전송 코딩 이름을 나열한다. 전송 코딩은 7장에 정의되어 있다.

```
  Transfer-Encoding = #transfer-coding
                       ; defined in [HTTP], Section 10.1.4
```

Transfer-Encoding은 MIME의 Content-Transfer-Encoding 필드와 비슷하다. Content-Transfer-Encoding은 7비트 전송 서비스에서 바이너리 데이터를 안전하게 전송할 수 있도록 설계되었다([RFC2045] 6장). 하지만 8비트를 그대로 전송할 수 있는 프로토콜에서 안전한 전송은 다른 데 초점을 둔다. HTTP의 경우 Transfer-Encoding은 주로 동적으로 생성된 콘텐츠의 경계를 정확히 구분하기 위한 것이다. 또한 전송 중에만 적용되는 인코딩을, 선택된 표현(representation)의 특성인 인코딩과 구분하는 역할도 한다.

수신자는 청크 전송 코딩(7.1절)을 반드시 파싱할 수 있어야 한다(MUST). 콘텐츠 크기를 미리 알 수 없을 때 메시지 프레이밍에서 결정적인 역할을 하기 때문이다. 송신자는 메시지 본문에 청크 전송 코딩을 두 번 이상 적용해서는 절대 안 된다(MUST NOT)(즉, 이미 청크로 나뉜 메시지를 다시 청크로 나누는 것은 허용되지 않는다). 요청 콘텐츠에 chunked 이외의 전송 코딩을 적용했다면, 송신자는 메시지가 제대로 프레이밍되도록 마지막 전송 코딩으로 chunked를 반드시 적용해야 한다(MUST). 응답 콘텐츠에 chunked 이외의 전송 코딩을 적용했다면, 송신자는 마지막 전송 코딩으로 chunked를 적용하거나 연결을 닫아 메시지를 끝내야 한다(MUST).

예를 들어

```
Transfer-Encoding: gzip, chunked
```

는 메시지 본문을 만들면서 콘텐츠를 gzip 코딩으로 압축한 다음 chunked 코딩으로 청크화했다는 뜻이다.

Content-Encoding([HTTP] 8.4.1절)과 달리 Transfer-Encoding은 표현이 아니라 메시지의 속성이다. 요청/응답 경로상의 어떤 수신자든, Transfer-Encoding 필드 값에 해당 변경을 반영한다면, 받은 전송 코딩을 디코딩하거나 메시지 본문에 전송 코딩을 추가로 적용할 수 있다(MAY). 인코딩 매개변수에 관한 추가 정보는 이 명세에서 정의하지 않는 다른 헤더 필드로 제공될 수 있다.

Transfer-Encoding은 HEAD 요청에 대한 응답이나 GET 요청에 대한 304(Not Modified) 응답([HTTP] 15.4.5절)에 보낼 수 있다(MAY). 둘 다 메시지 본문을 포함하지 않지만, 요청이 조건 없는 GET이었다면 오리진 서버가 메시지 본문에 전송 코딩을 적용했을 것임을 나타내기 위해서이다. 하지만 이 표시는 필수가 아니다. 응답 경로상의 어떤 수신자든(오리진 서버 포함) 필요 없으면 전송 코딩을 제거할 수 있기 때문이다.

서버는 1xx(Informational) 또는 204(No Content) 상태 코드의 어떤 응답에도 Transfer-Encoding 헤더 필드를 절대 보내서는 안 된다(MUST NOT). 서버는 CONNECT 요청([HTTP] 9.3.6절)에 대한 어떤 2xx(Successful) 응답에도 Transfer-Encoding 헤더 필드를 절대 보내서는 안 된다(MUST NOT).

이해하지 못하는 전송 코딩이 적용된 요청 메시지를 받은 서버는 501(Not Implemented)로 응답해야 한다(SHOULD).

Transfer-Encoding은 HTTP/1.1에서 추가되었다. 일반적으로 HTTP/1.0만 지원한다고 알리는 구현은 전송 인코딩된 콘텐츠를 처리하는 방법을 모를 것이라고 가정한다. 또한 Transfer-Encoding이 있는 HTTP/1.0 메시지를 받았다면, 전송 도중 청크 전송 코딩이 제대로 처리되지 않은 채 전달되었을 가능성이 높다고 가정한다.

클라이언트는 서버가 HTTP/1.1(또는 이후 마이너 버전) 요청을 처리할 수 있다는 것을 알지 못하면 Transfer-Encoding을 포함한 요청을 절대 보내서는 안 된다(MUST NOT). 그런 정보는 특정 사용자 설정이나, 이전에 받은 응답의 버전을 기억하는 방식으로 얻을 수 있다. 서버는 해당 요청이 HTTP/1.1(또는 이후 마이너 버전)을 나타내지 않으면 Transfer-Encoding을 포함한 응답을 절대 보내서는 안 된다(MUST NOT).

Transfer-Encoding의 초기 구현 중에는 메시지 프레이밍을 위한 청크 전송 코딩과, 진행 표시줄에 쓸 추정 Content-Length 헤더 필드를 함께 보내는 경우가 종종 있었다. 이 때문에 Transfer-Encoding은 Content-Length와 서로 양립할 수 없는 것이 아니라 Content-Length보다 우선하는 것으로 정의되었다. 안타깝게도 이런 메시지를 전달하면, 하위 수신자가 이 명세대로 메시지를 파싱하지 못할 때(특히 하위 수신자가 HTTP/1.0만 구현한 경우) 요청 스머글링(11.2절)이나 응답 분할(11.1절) 공격에 관한 취약점이 생길 수 있다.

서버는 Content-Length와 Transfer-Encoding을 모두 포함한 요청을 거부하거나, Transfer-Encoding만 따라 처리할 수 있다(MAY). 어느 쪽이든 서버는 잠재적 공격을 피하기 위해 그런 요청에 응답한 뒤 반드시 연결을 닫아야 한다(MUST).

Transfer-Encoding 헤더 필드를 포함한 HTTP/1.0 메시지를 받은 서버나 클라이언트는, Content-Length가 있더라도 그 메시지의 프레이밍이 잘못된 것처럼 다루고, 메시지를 처리한 뒤 연결을 반드시 닫아야 한다(MUST). 메시지 송신자가 메시지의 일부를 버퍼에 남겨 두었을 수 있고, 연결을 계속 쓰면 그 부분이 잘못 해석될 수 있기 때문이다.

### 6.2. Content-Length

메시지에 Transfer-Encoding 헤더 필드가 없으면, Content-Length 헤더 필드([HTTP] 8.6절)가 잠재적 콘텐츠의 예상 크기를 10진수 옥텟 수로 제공할 수 있다. 콘텐츠를 포함한 메시지에서는 Content-Length 필드 값이 데이터(와 메시지)가 어디서 끝나는지 판단하는 데 필요한 프레이밍 정보를 제공한다. 콘텐츠를 포함하지 않는 메시지에서는 Content-Length가 선택된 표현의 크기를 나타낸다([HTTP] 8.6절).

송신자는 Transfer-Encoding 헤더 필드를 포함한 메시지에 Content-Length 헤더 필드를 절대 보내서는 안 된다(MUST NOT).

> **참고:** HTTP가 메시지 프레이밍에 Content-Length를 사용하는 방식은 MIME에서 같은 필드를 사용하는 방식과 크게 다르다. MIME에서 이 필드는 "message/external-body" 미디어 타입 안에서만 쓰이는 선택적 필드이다.

### 6.3. 메시지 본문 길이

메시지 본문의 길이는 다음 중 하나로 결정된다(우선순위 순).

1. HEAD 요청에 대한 모든 응답, 그리고 1xx(Informational), 204(No Content), 304(Not Modified) 상태 코드의 모든 응답은 메시지에 어떤 헤더 필드가 있든 상관없이 항상 헤더 필드 뒤의 첫 빈 줄에서 끝난다. 따라서 메시지 본문이나 트레일러 섹션을 포함할 수 없다.

2. CONNECT 요청에 대한 모든 2xx(Successful) 응답은 헤더 필드를 마치는 빈 줄 직후에 연결이 터널이 된다는 것을 뜻한다. 클라이언트는 이런 메시지에서 받은 Content-Length나 Transfer-Encoding 헤더 필드를 반드시 무시해야 한다(MUST).

3. Transfer-Encoding과 Content-Length 헤더 필드를 모두 가진 메시지를 받으면, Transfer-Encoding이 Content-Length보다 우선한다. 이런 메시지는 요청 스머글링(11.2절)이나 응답 분할(11.1절)을 시도한 것일 수 있으므로 오류로 다뤄야 한다. 이 메시지를 전달하기로 한 중개자는 하위로 전달하기 전에 먼저 받은 Content-Length 필드를 제거하고 (아래 설명대로) Transfer-Encoding을 처리해야 한다(MUST).

4. Transfer-Encoding 헤더 필드가 있고 청크 전송 코딩(7.1절)이 마지막 인코딩이면, 메시지 본문 길이는 전송 코딩이 데이터가 끝났다고 나타낼 때까지 청크 데이터를 읽고 디코딩해서 결정한다.

   응답에 Transfer-Encoding 헤더 필드가 있고 청크 전송 코딩이 마지막 인코딩이 아니면, 메시지 본문 길이는 서버가 연결을 닫을 때까지 연결을 읽어서 결정한다.

   요청에 Transfer-Encoding 헤더 필드가 있고 청크 전송 코딩이 마지막 인코딩이 아니면, 메시지 본문 길이를 신뢰성 있게 결정할 수 없다. 서버는 반드시 400(Bad Request) 상태 코드로 응답한 뒤 연결을 닫아야 한다(MUST).

5. Transfer-Encoding 없이 잘못된 Content-Length 헤더 필드가 있는 메시지를 받으면, 메시지 프레이밍이 잘못된 것이며 수신자는 이를 복구할 수 없는 오류로 다뤄야 한다(MUST). 단, 필드 값을 쉼표로 구분된 리스트([HTTP] 5.6.1절)로 파싱할 수 있고, 리스트의 모든 값이 유효하며, 모든 값이 같다면 예외이다(이 경우 그 단일 값을 Content-Length 필드 값으로 사용해 메시지를 처리한다). 복구할 수 없는 오류가 요청 메시지에 있으면, 서버는 반드시 400(Bad Request) 상태 코드로 응답한 뒤 연결을 닫아야 한다(MUST). 프록시가 받은 응답 메시지에 있으면, 프록시는 서버와의 연결을 닫고, 받은 응답을 버리고, 클라이언트에 502(Bad Gateway) 응답을 보내야 한다(MUST). 사용자 에이전트가 받은 응답 메시지에 있으면, 사용자 에이전트는 서버와의 연결을 닫고 받은 응답을 버려야 한다(MUST).

6. Transfer-Encoding 없이 유효한 Content-Length 헤더 필드가 있으면, 그 10진수 값이 예상 메시지 본문 길이를 옥텟 단위로 정의한다. 지정된 옥텟 수를 다 받기 전에 송신자가 연결을 닫거나 수신자의 시간이 초과되면, 수신자는 메시지가 불완전하다고 간주하고 연결을 닫아야 한다(MUST).

7. 요청 메시지이고 위의 어느 것에도 해당하지 않으면, 메시지 본문 길이는 0이다(메시지 본문이 없다).

8. 그 밖의 경우는 메시지 본문 길이가 선언되지 않은 응답 메시지이므로, 메시지 본문 길이는 서버가 연결을 닫기 전까지 받은 옥텟 수로 결정된다.

연결 종료로 끝을 표시하는(close-delimited) 응답 메시지가 성공적으로 완료된 것인지, 네트워크 장애로 중단되어 일부만 받은 것인지 구분할 방법이 없으므로, 서버는 가능하면 인코딩이나 길이로 끝을 표시하는 메시지를 생성해야 한다(SHOULD). 연결 종료로 끝을 표시하는 기능은 주로 HTTP/1.0과의 하위 호환성을 위해 존재한다.

> **참고:** 요청 메시지는 연결 종료로 끝을 표시하지 않는다. 요청은 항상 길이나 전송 코딩으로 명시적으로 프레이밍되며, 둘 다 없다면 요청이 헤더 섹션 직후에 끝난다는 뜻이다.

서버는 메시지 본문이 있지만 Content-Length가 없는 요청을 411(Length Required)로 응답해 거절할 수 있다(MAY).

청크 이외의 전송 코딩이 적용되지 않았다면, 메시지 본문을 담은 요청을 보내는 클라이언트는 메시지 본문 길이를 미리 알 때 청크 전송 코딩 대신 유효한 Content-Length 헤더 필드를 사용해야 한다(SHOULD). 일부 기존 서비스는 청크 전송 코딩을 이해하면서도 청크 요청에 411(Length Required) 상태 코드로 응답하기 때문이다. 이런 서비스는 보통 호출되기 전에 콘텐츠 길이를 미리 알아야 하는 게이트웨이를 통해 구현되어 있고, 서버가 처리 전에 요청 전체를 버퍼링할 수 없거나 그러려 하지 않기 때문이다.

메시지 본문을 담은 요청을 보내는 사용자 에이전트는 유효한 Content-Length 헤더 필드를 보내거나 청크 전송 코딩을 사용해야 한다(MUST). 클라이언트는 서버가 HTTP/1.1 이상의 요청을 처리할 수 있다는 것을 알지 못하면 청크 전송 코딩을 사용해서는 안 된다(MUST NOT). 이 정보는 사용자 설정이나, 이전에 받은 응답의 버전을 기억하는 방식으로 얻을 수 있다.

연결의 마지막 요청에 대한 최종 응답을 다 받았는데도 읽을 데이터가 더 남아 있으면, 사용자 에이전트는 남은 데이터를 버리거나, 그 데이터가 이전 메시지 본문의 일부인지 판단해 볼 수 있다(MAY). 이전 메시지의 Content-Length 값이 잘못된 경우가 그렇다. 클라이언트는 이런 추가 데이터를 별도 응답으로 처리하거나, 캐시하거나, 전달해서는 안 된다(MUST NOT). 그렇게 하면 캐시 오염(cache poisoning)에 취약해진다.

## 7. 전송 코딩

전송 코딩 이름은 네트워크를 "안전하게 전송"하기 위해 메시지 콘텐츠에 적용되었거나, 적용할 수 있거나, 적용해야 할 수도 있는 인코딩 변환을 나타낸다. 전송 코딩은 전송되는 표현(representation)의 속성이 아니라 메시지의 속성이라는 점에서 콘텐츠 코딩과 다르다.

모든 전송 코딩 이름은 대소문자를 구분하지 않으며, 7.3절에 정의된 HTTP 전송 코딩 레지스트리에 등록되어야 한다. 전송 코딩 이름은 Transfer-Encoding(6.1절)과 TE([HTTP] 10.1.4절) 헤더 필드에서 쓰인다(TE 쪽에서 "transfer-coding" 문법도 정의한다).

### 7.1. 청크 전송 코딩

청크(chunked) 전송 코딩은 콘텐츠를 감싸서, 각자 크기 표시를 가진 청크들의 연속과 그 뒤에 오는 트레일러 필드를 담은 트레일러 섹션(선택, OPTIONAL)으로 전송한다. 청크 코딩을 쓰면 크기를 모르는 콘텐츠 스트림을 길이로 구분된 버퍼의 연속으로 보낼 수 있다. 그래서 송신자는 연결을 계속 유지할 수 있고, 수신자는 메시지 전체를 다 받았는지 알 수 있다.

```
  chunked-body   = *chunk
                   last-chunk
                   trailer-section
                   CRLF

  chunk          = chunk-size [ chunk-ext ] CRLF
                   chunk-data CRLF
  chunk-size     = 1*HEXDIG
  last-chunk     = 1*("0") [ chunk-ext ] CRLF

  chunk-data     = 1*OCTET ; a sequence of chunk-size octets
```

chunk-size 필드는 chunk-data의 크기를 옥텟 단위로 나타내는 16진수 문자열이다. 청크 크기가 0인 청크를 받고, 그 뒤에 트레일러 섹션이 올 수 있으며, 마지막으로 빈 줄로 끝나면 청크 전송 코딩이 완료된다.

수신자는 청크 전송 코딩을 파싱하고 디코딩할 수 있어야 한다(MUST).

HTTP/1.1은 중개자가 응답 전체를 버퍼링할 수 있도록 청크 응답의 크기를 제한하는 방법을 정의하지 않는다. 또한 청크 크기가 매우 크면 수신 구현에서 값을 정확히 표현하지 못해 오버플로나 정밀도 손실이 생길 수 있다. 따라서 수신자는 매우 큰 16진수가 올 수 있음을 예상하고, 정수 변환 오버플로로 인한 파싱 오류나 정수 표현으로 인한 정밀도 손실을 막아야 한다(MUST).

청크 코딩은 매개변수를 정의하지 않는다. 매개변수가 있으면 오류로 다뤄야 한다(SHOULD).

#### 7.1.1. 청크 확장

청크 코딩에서는 서명이나 해시 같은 청크별 메타데이터, 메시지 중간의 제어 정보, 메시지 본문 크기 무작위화 등을 위해, 각 청크의 chunk-size 바로 뒤에 0개 이상의 청크 확장을 붙일 수 있다.

```
  chunk-ext      = *( BWS ";" BWS chunk-ext-name
                      [ BWS "=" BWS chunk-ext-val ] )

  chunk-ext-name = token
  chunk-ext-val  = token / quoted-string
```

청크 코딩은 연결마다 다르며, 상위 애플리케이션이 확장을 살펴볼 기회를 얻기 전에 각 수신자(중개자 포함)가 제거하거나 다시 인코딩할 가능성이 높다. 그래서 청크 확장은 보통 "롱 폴링"처럼 클라이언트와 서버가 청크 확장 사용에 대해 기대를 공유할 수 있는 특수한 HTTP 서비스나, 종단 간 보안 연결 안에서의 패딩 용도로만 쓰인다.

수신자는 인식하지 못한 청크 확장을 무시해야 한다(MUST). 서버는 메시지의 다른 부분에 길이 제한과 타임아웃을 적용하는 것과 같은 방식으로, 요청에서 받는 청크 확장의 전체 길이를 제공하는 서비스에 맞는 적당한 양으로 제한하고, 그 양을 넘으면 적절한 4xx(Client Error) 응답을 생성하는 것이 좋다.

#### 7.1.2. 청크 트레일러 섹션

트레일러 섹션을 쓰면 송신자는 청크 메시지 끝에 필드를 더 넣을 수 있다. 메시지 무결성 검사, 디지털 서명, 후처리 상태처럼 콘텐츠를 보내는 동안 동적으로 만들어질 수 있는 메타데이터를 전달하기 위한 것이다. 트레일러 필드의 올바른 사용법과 제한은 [HTTP] 6.5절에 정의되어 있다.

```
  trailer-section   = *( field-line CRLF )
```

메시지에서 청크 코딩을 제거하는 수신자는 받은 트레일러 필드를 선택적으로 유지하거나 버릴 수 있다(MAY). 받은 트레일러 필드를 유지하는 수신자는 그 트레일러 필드를 받은 헤더 필드와 따로 저장·전달하거나, 헤더 섹션에 병합해야 한다(MUST). 수신자는 해당 헤더 필드의 정의가 트레일러 필드 값을 안전하게 병합하는 것을 명시적으로 허용하고 그 방법을 설명하지 않는 한, 받은 트레일러 필드를 헤더 섹션에 병합해서는 안 된다(MUST NOT).

#### 7.1.3. 청크 디코딩

청크 전송 코딩을 디코딩하는 과정은 다음 의사 코드로 나타낼 수 있다.

```
  length := 0
  read chunk-size, chunk-ext (if any), and CRLF
  while (chunk-size > 0) {
     read chunk-data and CRLF
     append chunk-data to content
     length := length + chunk-size
     read chunk-size, chunk-ext (if any), and CRLF
  }
  read trailer field
  while (trailer field is not empty) {
     if (trailer fields are stored/forwarded separately) {
         append trailer field to existing trailer fields
     }
     else if (trailer field is understood and defined as mergeable) {
         merge trailer field with existing header fields
     }
     else {
         discard trailer field
     }
     read trailer field
  }
  Content-Length := length
  Remove "chunked" from Transfer-Encoding
```

### 7.2. 압축용 전송 코딩

다음 압축용 전송 코딩 이름은 대응하는 콘텐츠 코딩과 같은 알고리즘으로 정의된다.

- **compress** (및 x-compress): [HTTP] 8.4.1.1절 참고.
- **deflate**: [HTTP] 8.4.1.2절 참고.
- **gzip** (및 x-gzip): [HTTP] 8.4.1.3절 참고.

압축 코딩은 매개변수를 정의하지 않는다. 이 압축 코딩에 매개변수가 있으면 오류로 다뤄야 한다(SHOULD).

### 7.3. 전송 코딩 레지스트리

"HTTP 전송 코딩 레지스트리"는 전송 코딩 이름의 네임스페이스를 정의하며, <https://www.iana.org/assignments/http-parameters>에서 관리된다.

등록에는 다음 필드가 반드시 포함되어야 한다(MUST).

- 이름
- 설명
- 명세 텍스트 위치

전송 코딩의 이름은 콘텐츠 코딩([HTTP] 8.4.1절)의 이름과 겹쳐서는 안 된다(MUST NOT). 단, 7.2절에 정의된 압축 코딩처럼 인코딩 변환이 동일한 경우는 예외이다.

TE 헤더 필드([HTTP] 10.1.4절)는 여러 전송 코딩을 받아들일 수 있을 때 우선순위 값으로 "q"라는 의사 매개변수를 쓴다. 모호함을 피하기 위해, 앞으로 등록되는 전송 코딩은 (대소문자 구분 없이) "q"라는 이름의 매개변수를 정의하지 않아야 한다(SHOULD NOT).

이 네임스페이스에 값을 추가하려면 IETF 검토([RFC8126] 4.8절 참고)가 필요하며, 이 명세에서 정의한 전송 코딩의 목적에 맞아야 한다(MUST).

인코딩 형식을 식별할 때 프로그램 이름을 쓰는 것은 바람직하지 않으며, 앞으로의 인코딩에서는 권장하지 않는다.

### 7.4. 전송 코딩 협상

HTTP/1.1에서 TE 필드([HTTP] 10.1.4절)는 클라이언트가 응답에서 청크 외에 어떤 전송 코딩을 받아들일지, 그리고 청크 전송 코딩의 트레일러 필드를 보존할 의향이 있는지를 나타낸다.

클라이언트는 TE에 청크 전송 코딩 이름을 보내서는 안 된다(MUST NOT). HTTP/1.1 수신자에게 청크는 항상 받아들일 수 있는 코딩이다.

TE 사용 예시 세 가지는 다음과 같다.

```
TE: deflate
TE:
TE: trailers, deflate;q=0.5
```

여러 전송 코딩을 받아들일 수 있으면, 클라이언트는 대소문자를 구분하지 않는 "q" 매개변수로 선호 순위를 매길 수 있다(MAY). 콘텐츠 협상 필드에서 쓰는 qvalue와 비슷하다([HTTP] 12.4.2절 참고). 순위 값은 0에서 1 사이의 실수로, 0.001이 가장 낮은 선호이고 1이 가장 높은 선호이다. 0은 "받아들일 수 없음"을 뜻한다.

TE 필드 값이 비어 있거나 TE 필드가 없으면, 받아들일 수 있는 전송 코딩은 청크뿐이다. 전송 코딩이 없는 메시지는 항상 받아들일 수 있다.

키워드 "trailers"는 [HTTP] 6.5절에 설명된 대로 송신자가 트레일러 필드를 버리지 않는다는 뜻이다.

TE 헤더 필드는 바로 인접한 연결에만 적용되므로, TE를 보내는 송신자는 그 의미를 지원하지 않는 중개자가 TE 헤더 필드를 전달하지 않도록 Connection 헤더 필드([HTTP] 7.6.1절)에 "TE" 연결 옵션도 함께 보내야 한다(MUST).

## 8. 불완전한 메시지 처리

보통 요청이 취소되거나 타임아웃 예외가 발생해서 불완전한 요청 메시지를 받은 서버는, 연결을 닫기 전에 오류 응답을 보낼 수 있다(MAY).

연결이 일찍 닫히거나 청크 전송 코딩이라고 생각한 것의 디코딩이 실패해서 불완전한 응답 메시지를 받은 클라이언트는, 그 메시지를 불완전하다고 기록해야 한다(MUST). 불완전한 응답에 대한 캐시 요구 사항은 [CACHING] 3.3절에 정의되어 있다.

응답이 헤더 섹션 중간(빈 줄을 받기 전)에서 끝났고 상태 코드가 응답의 완전한 의미를 전달하기 위해 헤더 필드에 의존할 수 있다면, 클라이언트는 그 의미가 전달되었다고 가정할 수 없다. 다음에 무엇을 할지 정하려면 요청을 다시 보내야 할 수도 있다.

청크 전송 코딩을 쓰는 메시지 본문은 인코딩을 끝내는 크기 0인 청크를 받지 못하면 불완전하다. 유효한 Content-Length를 쓰는 메시지는 받은 메시지 본문 크기(옥텟)가 Content-Length 값보다 작으면 불완전하다. 청크 전송 코딩도 Content-Length도 없는 응답은 연결이 닫히면서 끝난다. 이런 응답은 헤더 섹션을 온전히 받았다면, 하위 연결에서 오류를 알리지 않는 한 완전한 것으로 본다(예를 들어 TLS의 "불완전한 종료"는 9.8절에 설명된 대로 응답을 불완전하게 만든다).

## 9. 연결 관리

HTTP 메시징은 하위 전송 계층이나 세션 계층의 연결 프로토콜과 독립적이다. HTTP는 요청이 순서대로 전달되고, 그에 대응하는 응답도 순서대로 전달되는 신뢰할 수 있는 전송만을 가정한다. HTTP 요청·응답 구조를 하위 전송 프로토콜의 데이터 단위에 대응시키는 방법은 이 명세의 범위 밖이다.

[HTTP] 7.3절에 설명된 대로, HTTP 상호작용에 쓸 구체적인 연결 프로토콜은 클라이언트 설정과 대상 URI로 정해진다. 예를 들어 "http" URI 스킴([HTTP] 4.2.1절)은 기본적으로 IP 위의 TCP 연결과 기본 TCP 포트 80을 뜻하지만, 클라이언트는 다른 연결, 포트, 프로토콜로 프록시를 쓰도록 설정되어 있을 수 있다.

HTTP 구현은 연결 관리를 해야 한다. 연결 관리에는 현재 연결의 상태 유지, 새 연결 수립 또는 기존 연결 재사용, 연결에서 받은 메시지 처리, 연결 장애 감지, 각 연결 닫기가 포함된다. 대부분의 클라이언트는 여러 연결을 병렬로 유지하며, 서버 엔드포인트 하나에 둘 이상의 연결을 두기도 한다. 대부분의 서버는 수천 개의 동시 연결을 유지하면서, 공정한 사용을 보장하고 서비스 거부 공격을 감지하기 위해 요청 큐를 제어하도록 설계된다.

### 9.1. 연결 수립

여러 전송 계층이나 세션 계층 프로토콜로 연결을 수립하는 방법을 설명하는 것은 이 명세의 범위 밖이다. 각 HTTP 연결은 하위 전송 연결 하나에 대응한다.

### 9.2. 요청과 응답 연결 짓기

HTTP/1.1에는 요청 메시지와 그에 대응하는 하나 이상의 응답 메시지를 연결 짓는 요청 식별자가 없다. 그래서 같은 연결에서 응답이 도착하는 순서가 요청을 보낸 순서와 정확히 일치한다는 데 의존한다. 요청 하나에 응답 메시지가 둘 이상인 경우는, 같은 요청에 대한 최종 응답 앞에 하나 이상의 정보성 응답(1xx, [HTTP] 15.2절 참고)이 오는 경우뿐이다.

한 연결에 아직 응답을 받지 못한 요청이 둘 이상 있는 클라이언트는, 그 요청들의 목록을 보낸 순서대로 유지해야 하고(MUST), 그 연결에서 받은 각 응답 메시지를 아직 최종(1xx가 아닌) 응답을 받지 못한 첫 번째 요청에 연결 지어야 한다(MUST).

응답을 기다리는 요청이 없는 연결에서 데이터를 받으면, 클라이언트는 그 데이터를 유효한 응답으로 여겨서는 안 된다(MUST NOT). 이제 메시지 경계가 모호해졌으므로 클라이언트는 연결을 닫아야 한다(SHOULD). 단, 데이터가 하나 이상의 CRLF로만 이루어져 있다면 예외이다(2.2절에 따라 버릴 수 있다).

### 9.3. 지속성

HTTP/1.1은 기본적으로 "지속 연결(persistent connection)"을 사용해서, 연결 하나로 여러 요청과 응답을 주고받을 수 있게 한다. HTTP 구현은 지속 연결을 지원해야 한다(SHOULD).

수신자는 가장 최근에 받은 메시지의 프로토콜 버전과 Connection 헤더 필드([HTTP] 7.6.1절)(있다면)를 보고 연결이 지속되는지 판단한다.

- "close" 연결 옵션이 있으면(9.6절), 현재 응답 이후 연결은 유지되지 않는다. 그렇지 않고,
- 받은 프로토콜이 HTTP/1.1 이상이면, 현재 응답 이후에도 연결이 유지된다. 그렇지 않고,
- 받은 프로토콜이 HTTP/1.0이고, "keep-alive" 연결 옵션이 있고, 수신자가 프록시가 아니거나 메시지가 응답이며, 수신자가 HTTP/1.0의 "keep-alive" 방식을 따르려 한다면, 현재 응답 이후에도 연결이 유지된다. 그렇지 않으면,
- 현재 응답 이후 연결이 닫힌다.

지속 연결을 지원하지 않는 클라이언트는 모든 요청 메시지에 "close" 연결 옵션을 보내야 한다(MUST).

지속 연결을 지원하지 않는 서버는 1xx(Informational) 상태 코드가 아닌 모든 응답 메시지에 "close" 연결 옵션을 보내야 한다(MUST).

클라이언트는 "close" 연결 옵션을 보내거나 받을 때까지, 또는 "keep-alive" 연결 옵션이 없는 HTTP/1.0 응답을 받을 때까지, 지속 연결에서 요청을 더 보낼 수 있다(MAY).

연결이 계속 유지되려면, 6장에 설명된 대로 연결의 모든 메시지가 스스로 정의된 메시지 길이(즉, 연결 종료로 정해지지 않는 길이)를 가져야 한다. 서버는 요청 메시지 본문 전체를 읽거나, 응답을 보낸 뒤 연결을 닫아야 한다(MUST). 그렇지 않으면 지속 연결에 남은 데이터가 다음 요청으로 잘못 해석된다. 마찬가지로 클라이언트도 같은 연결을 다음 요청에 재사용하려면 응답 메시지 본문 전체를 읽어야 한다(MUST).

프록시 서버는 HTTP/1.0 클라이언트와 지속 연결을 유지해서는 안 된다(MUST NOT). 많은 HTTP/1.0 클라이언트가 구현한 Keep-Alive 헤더 필드의 문제에 대한 정보와 논의는 부록 C.2.2를 참고하라.

HTTP/1.0 클라이언트와의 하위 호환성에 대한 자세한 내용은 부록 C.2.2를 참고하라.

#### 9.3.1. 요청 재시도

연결은 의도했든 아니든 언제든 닫힐 수 있다. 구현은 비동기적인 연결 종료 이벤트에서 복구해야 할 상황을 예상해야 한다. 클라이언트가 아직 응답을 받지 못한 요청들을 자동으로 재시도할 수 있는 조건은 [HTTP] 9.2.2절에 정의되어 있다.

#### 9.3.2. 파이프라이닝

지속 연결을 지원하는 클라이언트는 요청을 "파이프라이닝"할 수 있다(MAY). 즉, 각 응답을 기다리지 않고 여러 요청을 보낼 수 있다. 서버는 파이프라이닝된 요청들이 모두 안전한 메서드([HTTP] 9.2.1절)라면 병렬로 처리할 수 있지만(MAY), 대응하는 응답은 반드시 요청을 받은 순서대로 보내야 한다(MUST).

요청을 파이프라이닝하는 클라이언트는 대응하는 응답을 모두 받기 전에 연결이 닫히면, 응답받지 못한 요청을 재시도해야 한다(SHOULD). 연결이 실패한 뒤(서버가 마지막 완전한 응답에서 명시적으로 닫지 않은 연결) 파이프라이닝된 요청을 재시도할 때, 클라이언트는 연결을 수립하자마자 파이프라이닝해서는 안 된다(MUST NOT). 이전 파이프라인에 남은 첫 번째 요청이 오류 응답을 일으켰을 수 있는데, 일찍 닫히는 연결에 여러 요청을 보내면 그 오류 응답이 다시 사라질 수 있기 때문이다(9.6절에 설명된 TCP 리셋 문제 참고).

멱등 메서드([HTTP] 9.2.2절)는 연결 실패 후 자동으로 재시도할 수 있으므로 파이프라이닝에서 중요하다. 사용자 에이전트는 파이프라이닝된 요청들과 관련된 부분 실패를 감지하고 복구할 수단이 없다면, 멱등이 아닌 메서드를 보낸 뒤에는 그 메서드의 최종 응답 상태 코드를 받을 때까지 요청을 파이프라이닝하지 않아야 한다(SHOULD NOT).

파이프라이닝된 요청을 받은 중개자는 그 요청을 인바운드로 전달할 때 파이프라이닝할 수 있다(MAY). 어떤 요청을 안전하게 파이프라이닝할 수 있는지는 아웃바운드 사용자 에이전트가 판단한다고 믿을 수 있기 때문이다. 응답을 받기 전에 인바운드 연결이 실패하면, 파이프라이닝하는 중개자는 아직 응답을 받지 못한 요청들이 모두 멱등 메서드일 때 재시도할 수 있다(MAY). 그렇지 않으면 받은 응답을 모두 전달한 뒤 대응하는 아웃바운드 연결을 닫아서, 아웃바운드 사용자 에이전트가 그에 맞게 복구할 수 있게 해야 한다(SHOULD).

### 9.4. 동시성

클라이언트는 특정 서버에 대해 동시에 열어 두는 연결 수를 제한하는 것이 좋다.

이전 HTTP 개정판은 연결 수의 상한을 구체적인 숫자로 정했지만, 많은 애플리케이션에서 비현실적이라는 것이 드러났다. 그래서 이 명세는 특정 최대 연결 수를 강제하지 않고, 대신 클라이언트가 여러 연결을 열 때 보수적으로 행동하도록 권장한다.

여러 연결은 보통 "head-of-line blocking" 문제를 피하기 위해 쓰인다. 이 문제는 서버 처리가 오래 걸리거나 매우 큰 콘텐츠를 전송하는 요청 하나가 같은 연결의 다음 요청들을 막는 것이다. 하지만 연결마다 서버 자원을 소비한다.

게다가 여러 연결을 쓰면 혼잡한 네트워크에서 원치 않는 부작용이 생길 수 있다. 연결 수가 많으면 혼잡하지 않은 네트워크에서도 부작용이 생길 수 있다. 연결들이 모여서 처음에 동시에 전송을 시작하면, 병렬 연결이 적었다면 없었을 혼잡이 생길 수 있기 때문이다.

서버는 한 클라이언트가 지나치게 많은 연결을 여는 것처럼, 남용이나 서비스 거부 공격의 특징으로 보이는 트래픽을 거절할 수 있다.

### 9.5. 장애와 타임아웃

서버는 보통 일정 시간이 지나면 비활성 연결을 더 이상 유지하지 않는 타임아웃 값을 가진다. 클라이언트가 같은 프록시 서버를 통해 연결을 더 맺을 가능성이 높으므로, 프록시 서버는 이 값을 더 크게 둘 수 있다. 지속 연결을 쓴다고 해서 클라이언트나 서버의 이 타임아웃 길이(또는 타임아웃의 존재 여부)에 요구 사항이 생기지는 않는다.

타임아웃하려는 클라이언트나 서버는 연결을 우아하게(graceful) 닫아야 한다(SHOULD). 구현은 열린 연결에서 종료 신호를 받는지 계속 감시하고 적절히 대응해야 한다(SHOULD). 연결 양쪽을 빨리 닫아야 할당된 시스템 자원을 회수할 수 있기 때문이다.

클라이언트, 서버, 프록시는 언제든 전송 연결을 닫을 수 있다(MAY). 예를 들어 서버가 "유휴" 연결을 닫기로 한 바로 그때 클라이언트가 새 요청을 보내기 시작했을 수 있다. 서버 입장에서는 유휴 상태인 연결을 닫는 것이지만, 클라이언트 입장에서는 요청이 진행 중인 것이다.

서버는 가능하면 지속 연결을 유지하고, 클라이언트가 재시도할 것을 기대하며 연결을 끊기보다는 하위 전송의 흐름 제어 메커니즘이 일시적인 과부하를 해결하게 해야 한다(SHOULD). 연결을 끊는 방식은 네트워크 혼잡이나 서버 부하를 악화시킬 수 있다.

메시지 본문을 보내는 클라이언트는 요청을 전송하는 동안 네트워크 연결에서 오류 응답이 오는지 감시해야 한다(SHOULD). 서버가 메시지 본문을 받을 생각이 없고 연결을 닫는다는 응답을 보면, 클라이언트는 즉시 본문 전송을 멈추고 자기 쪽 연결을 닫아야 한다(SHOULD).

### 9.6. 연결 해제

"close" 연결 옵션은 송신자가 응답이 완료된 뒤 이 연결을 닫겠다는 신호로 정의된다. 연결을 닫으려는 송신자는 "close" 연결 옵션을 담은 Connection 헤더 필드([HTTP] 7.6.1절)를 보내야 한다(SHOULD). 예를 들어,

```
Connection: close
```

이 필드가 요청 헤더 필드로 오면 클라이언트가 이 연결에서 보내는 마지막 요청이라는 뜻이고, 응답에 오면 서버가 응답 메시지를 완료한 뒤 이 연결을 닫는다는 뜻이다.

필드 이름 "Close"는 예약되어 있다. 이 이름을 헤더 필드로 쓰면 "close" 연결 옵션과 충돌할 수 있기 때문이다.

"close" 연결 옵션을 보낸 클라이언트는 그 연결에서 ("close"를 담은 요청 이후로) 요청을 더 보내서는 안 되며(MUST NOT), 이 요청에 대응하는 최종 응답 메시지를 읽은 뒤 연결을 닫아야 한다(MUST).

"close" 연결 옵션을 받은 서버는 "close" 연결 옵션을 담은 요청에 최종 응답을 보낸 뒤 연결 종료를 시작해야 한다(MUST)(아래 참고). 서버는 그 연결의 최종 응답에 "close" 연결 옵션을 보내야 한다(SHOULD). 서버는 그 연결에서 받은 요청을 더 처리해서는 안 된다(MUST NOT).

"close" 연결 옵션을 보낸 서버는 "close" 연결 옵션을 담은 응답을 보낸 뒤 연결 종료를 시작해야 한다(MUST)(아래 참고). 서버는 그 연결에서 받은 요청을 더 처리해서는 안 된다(MUST NOT).

"close" 연결 옵션을 받은 클라이언트는 그 연결에서 요청 보내기를 멈추고, "close" 연결 옵션을 담은 응답 메시지를 읽은 뒤 연결을 닫아야 한다(MUST). 그 연결에 파이프라이닝된 요청을 더 보냈다면, 클라이언트는 서버가 그 요청들을 처리할 것이라고 가정하지 않아야 한다(SHOULD NOT).

서버가 TCP 연결을 즉시 닫으면, 클라이언트가 마지막 HTTP 응답을 읽지 못할 위험이 크다. 완전히 닫힌 연결에서 서버가 클라이언트로부터 데이터를 더 받으면(예: 클라이언트가 서버의 응답을 받기 전에 보낸 다른 요청), 서버의 TCP 스택은 클라이언트에 리셋 패킷을 보낸다. 안타깝게도 이 리셋 패킷은 클라이언트의 HTTP 파서가 읽고 해석하기 전에, 클라이언트의 아직 확인 응답(ACK)하지 않은 입력 버퍼를 지워 버릴 수 있다.

TCP 리셋 문제를 피하기 위해 서버는 보통 연결을 단계적으로 닫는다. 먼저 읽기/쓰기 연결 중 쓰기 쪽만 닫는 하프 클로즈(half-close)를 한다. 그다음 클라이언트가 대응하는 종료를 보낼 때까지, 또는 서버 자신의 TCP 스택이 서버의 마지막 응답을 담은 패킷에 대한 클라이언트의 확인 응답을 받았다고 어느 정도 확신할 때까지 연결에서 계속 읽는다. 마지막으로 연결을 완전히 닫는다.

리셋 문제가 TCP에만 있는지, 다른 전송 연결 프로토콜에서도 나타날 수 있는지는 알려져 있지 않다.

클라이언트가 하프 클로즈한 TCP 연결은 요청 메시지의 끝을 표시하지 않으며, 클라이언트가 더 이상 응답에 관심이 없다는 뜻도 아니다. 일반적으로 HTTP/1.1은 전송과 독립적이므로, 전송 신호로 경계 상황을 알린다고 기대할 수 없다.

### 9.7. TLS 연결 시작

개념적으로 HTTP/TLS는 TLS[TLS13]로 보호된 연결 위에서 HTTP 메시지를 보내는 것일 뿐이다.

HTTP 클라이언트는 TLS 클라이언트 역할도 한다. 적절한 포트로 서버에 연결을 시작하고, TLS 핸드셰이크를 시작하기 위해 TLS ClientHello를 보낸다. TLS 핸드셰이크가 끝나면 클라이언트는 첫 HTTP 요청을 시작할 수 있다. 모든 HTTP 데이터는 TLS "애플리케이션 데이터"로 보내야 하지만(MUST), 그 밖에는 HTTP 입장에서 일반 연결과 똑같이 다룬다(지속 연결로 재사용하는 것도 포함).

### 9.8. TLS 연결 종료

TLS는 안전한 연결 종료를 위해 (오류가 아닌) 연결 종료 전에 종료 경고(closure alert)를 주고받는다([TLS13] 6.1절 참고). 유효한 종료 경고를 받으면, 구현은 그 연결에서 더 이상 데이터를 받지 않을 것임을 확신할 수 있다.

보통 HTTP 메시지 경계를 감지해서 필요한 메시지 데이터를 모두 보냈거나 받았다는 것을 알게 된 구현은, 종료 경고를 보낸 다음 상대의 종료 경고를 기다리지 않고 연결을 닫아 "불완전한 종료(incomplete close)"를 만들 수 있다.

불완전한 종료가 이미 받은 데이터의 보안을 의심하게 만들지는 않지만, 그 뒤의 데이터가 잘렸을 수 있음을 나타낼 수 있다. TLS는 HTTP 메시지 프레이밍을 직접 알지 못하므로, 메시지가 완전한지 판단하려면 HTTP 데이터 자체를 살펴봐야 한다. 불완전한 메시지 처리는 8장에 정의되어 있다.

불완전한 종료를 만나면, 클라이언트는 다음 중 하나를 받은 요청을 모두 완료된 것으로 다뤄야 한다(SHOULD).

1. Content-Length 헤더 필드에 지정된 만큼의 데이터
2. (청크 Transfer-Encoding을 쓸 때) 길이 0인 마지막 청크

청크 전송 코딩도 Content-Length도 없는 응답은 유효한 종료 경고를 받은 경우에만 완전하다. 불완전한 메시지를 완전한 것으로 다루면 구현이 공격에 노출될 수 있다.

불완전한 종료를 감지한 클라이언트는 우아하게 복구해야 한다(SHOULD).

클라이언트는 연결을 닫기 전에 종료 경고를 보내야 한다(MUST). 더 받을 데이터가 없다고 판단한 클라이언트는 서버의 종료 경고를 기다리지 않고 그냥 연결을 닫아서, 서버 쪽에 불완전한 종료를 만들 수 있다(MAY).

클라이언트는 서버 데이터의 끝을 알아낼 수 있는 경우가 많으므로, 서버는 클라이언트로부터 불완전한 종료를 받을 준비를 해야 한다(SHOULD).

서버는 연결을 닫기 전에 클라이언트와 종료 경고 교환을 시작하려고 시도해야 한다(MUST). 서버는 종료 경고를 보낸 뒤 연결을 닫아서 클라이언트 쪽에 불완전한 종료를 만들 수 있다(MAY).

## 10. 메시지를 데이터로 감싸기

### 10.1. 미디어 타입 message/http

"message/http" 미디어 타입은 HTTP 요청 또는 응답 메시지 하나를 감싸는 데 쓸 수 있다. 단, 줄 길이와 인코딩에 관해 모든 "message" 타입에 적용되는 MIME 제약을 따라야 한다. 줄 길이 제한 때문에, "message/http" 안의 필드 값은 5.2절에 설명된 줄 접기(obs-fold)를 써서 필드 값을 여러 줄에 걸쳐 전달할 수 있다. "message/http" 데이터를 받은 수신자는 메시지를 사용할 때 폐기된 줄 접기를 모두 하나 이상의 SP 문자로 바꿔야 한다(MUST).

| 항목 | 값 |

| 타입 이름 | message |
| 서브타입 이름 | http |
| 필수 매개변수 | 없음 |
| 선택 매개변수 | version, msgtype |
| 인코딩 고려 사항 | "7bit", "8bit", "binary"만 허용 |

| 프래그먼트 식별자 고려 사항 | 없음 |

- **version**: 감싼 메시지의 HTTP 버전 번호(예: "1.1"). 없으면 본문의 첫 줄에서 버전을 알아낼 수 있다.
- **msgtype**: 메시지 종류. "request" 또는 "response". 없으면 본문의 첫 줄에서 종류를 알아낼 수 있다.

## 11. 보안 고려 사항

이 장은 HTTP 메시지 문법과 파싱에 관련된 알려진 보안 고려 사항을 개발자, 정보 제공자, 사용자에게 알리기 위한 것이다. HTTP 의미론, 콘텐츠, 라우팅에 관한 보안 고려 사항은 [HTTP]에서 다룬다.

### 11.1. 응답 분할

응답 분할(response splitting, CRLF 인젝션이라고도 한다)은 웹 사용에 대한 여러 공격에 쓰이는 흔한 기법으로, HTTP 메시지 프레이밍이 줄 단위라는 점과 지속 연결에서 요청과 응답이 순서대로 짝지어진다는 점을 악용한다[Klein]. 이 기법은 요청이 공유 캐시를 거칠 때 특히 피해가 클 수 있다.

응답 분할은 서버(보통 애플리케이션 서버)의 취약점을 악용한다. 공격자가 요청의 어떤 매개변수에 인코딩된 데이터를 넣어 보내면, 서버가 나중에 이를 디코딩해서 응답의 어떤 헤더 필드에 그대로 되돌려 넣는 경우다. 디코딩된 데이터가 응답이 끝나고 다음 응답이 시작된 것처럼 보이도록 만들어졌다면, 응답이 분할되고 겉보기 두 번째 응답의 내용은 공격자가 통제하게 된다. 그러면 공격자는 같은 지속 연결로 다른 요청을 보내서, 수신자(중개자 포함)가 분할된 뒷부분을 두 번째 요청에 대한 정식 응답이라고 믿게 속일 수 있다.

예를 들어 애플리케이션 서버가 request-target의 매개변수를 읽어서 리다이렉트에 다시 쓰면, 그 매개변수가 응답의 Location 헤더 필드에 그대로 나타난다. 애플리케이션이 매개변수를 디코딩한 뒤 응답 필드에 넣을 때 제대로 인코딩하지 않으면, 공격자는 인코딩된 CRLF 옥텟과 다른 내용을 보내서 애플리케이션의 응답 하나를 둘 이상의 응답처럼 보이게 만들 수 있다.

응답 분할에 대한 흔한 방어는 인코딩된 CR과 LF처럼 보이는 데이터(예: "%0D", "%0A")가 있는 요청을 걸러내는 것이다. 하지만 이 방법은 애플리케이션 서버가 URI 디코딩만 하고, 문자셋 변환, XML 엔티티 변환, base64 디코딩, sprintf 재서식 같은 덜 드러나는 데이터 변환은 하지 않는다고 가정한다. 더 효과적인 완화책은 서버의 핵심 프로토콜 라이브러리 말고는 아무것도 헤더 섹션 안에 CR이나 LF를 보내지 못하게 하는 것이다. 즉, 헤더 필드 출력을 잘못된 옥텟을 걸러내는 API로만 하도록 제한하고, 애플리케이션 서버가 프로토콜 스트림에 직접 쓰지 못하게 하는 것이다.

### 11.2. 요청 스머글링

요청 스머글링([Linhart])은 여러 수신자 사이의 프로토콜 파싱 차이를 악용해서, (그렇지 않았다면 정책상 차단되거나 비활성화되었을) 추가 요청을 겉보기에 무해한 요청 안에 숨기는 기법이다. 응답 분할처럼 요청 스머글링도 HTTP 사용에 대한 다양한 공격으로 이어질 수 있다.

이 명세는 요청 스머글링의 효과를 줄이기 위해 요청 파싱에 새 요구 사항을 도입했으며, 특히 6.3절의 메시지 프레이밍에 관한 것이 그렇다.

### 11.3. 메시지 무결성

HTTP는 메시지 무결성을 보장하는 특정 메커니즘을 정의하지 않는다. 대신 하위 전송 프로토콜의 오류 감지 능력과, 완전성을 감지하기 위한 길이 또는 청크 기반 프레이밍에 의존한다. 역사적으로 단일 무결성 메커니즘이 없는 것은 대부분의 HTTP 통신이 비공식적이라는 이유로 정당화되어 왔다. 하지만 HTTP가 정보 접근 수단으로 널리 쓰이면서, 메시지 무결성 검증이 중요한 환경에서도 점점 더 많이 쓰이고 있다.

"https" 스킴이 제공하는 인증된 암호화 같은 메커니즘은 메시지 변조를 막아 준다. 다만 연결 종료로 메시지를 잘라낼 수 없도록 주의해야 한다(9.8절 참고). 사용자 에이전트는 불완전한 메시지를 받아들이지 않거나 특별하게 다룰 수 있다. 예를 들어 병력이나 약물 상호작용 정보를 보는 데 쓰이는 브라우저는, 프로토콜이 그 정보가 전송 중에 불완전하거나, 만료되었거나, 손상되었다고 감지하면 사용자에게 알려야 한다. 이런 메커니즘은 사용자 에이전트 확장이나 응답의 메시지 무결성 메타데이터 유무에 따라 선택적으로 활성화될 수 있다.

"http" 스킴은 메시지의 우발적이거나 악의적인 변조를 전혀 막아 주지 않는다.

"https" 스킴을 쓸 때에도, 중개자가 메시지를 원치 않게 변조할 위험을 줄이기 위해 프로토콜 확장을 쓸 수 있다. 확장 가능한 메타데이터 필드로 메시지에 선택적으로 추가하는 메시지 인증 코드나 디지털 서명으로 무결성을 보장할 수 있다.

### 11.4. 메시지 기밀성

HTTP는 메시지 기밀성이 필요할 때 하위 전송 프로토콜에 의존한다. HTTP는 전송 프로토콜과 독립적으로 설계되어서 여러 형태의 암호화된 연결 위에서 쓸 수 있으며, 그런 전송의 선택은 URI 스킴이나 사용자 에이전트 설정으로 정해진다.

[HTTP] 4.2.2절에 설명된 대로, "https" 스킴은 기밀 연결이 필요한 리소스를 식별하는 데 쓸 수 있다.

## 부록 B. HTTP와 MIME의 차이

HTTP/1.1은 메시지 본문을 다양한 표현과 확장 가능한 필드로 전송할 수 있도록, 인터넷 메시지 형식[RFC5322]과 MIME(Multipurpose Internet Mail Extensions)[RFC2045]에 정의된 구성 요소를 많이 사용한다. 하지만 일부 구성 요소는 대화형 통신에 더 잘 맞도록 다시 해석되었고, 그래서 HTTP 안에서 MIME 구성 요소를 쓰는 방식에 몇 가지 차이가 생겼다. 이 차이들은 바이너리 연결에서의 성능 최적화, 새 미디어 타입 사용의 자유, 날짜 비교의 단순화, 흔한 구현과의 호환을 위해 신중하게 선택된 것이다.

이 부록은 HTTP가 MIME과 다른 구체적인 부분을 설명한다. 엄격한 MIME 환경과 오가는 프록시와 게이트웨이는 이 차이를 알고, 필요하면 적절히 변환해야 한다.

### B.1. MIME-Version

HTTP는 MIME 준수 프로토콜이 아니다. 하지만 메시지에는 메시지를 만드는 데 쓴 MIME 프로토콜 버전을 나타내는 MIME-Version 헤더 필드를 하나 넣을 수 있다. MIME-Version 헤더 필드를 쓰면 메시지가 ([RFC2045]에 정의된) MIME 프로토콜을 완전히 준수한다는 뜻이다. 엄격한 MIME 환경으로 HTTP 메시지를 내보낼 때 (가능한 한) 완전히 준수하도록 보장하는 것은 송신자의 책임이다.

### B.2. 정규 형식으로 변환

MIME은 [RFC2049] 4절에 설명된 대로 인터넷 메일 본문 부분을 전송하기 전에 정규(canonical) 형식으로 변환할 것을 요구하며, "text" 타입 콘텐츠는 줄바꿈을 CRLF로 표현하고 줄바꿈 시퀀스 밖에서 CR이나 LF를 쓰는 것을 금지한다[RFC2046]. 반면 HTTP는 콘텐츠 안에서 줄바꿈을 CRLF로 나타내든, CR만 쓰든, LF만 쓰든 상관하지 않는다.

HTTP에서 엄격한 MIME 환경으로 가는 프록시나 게이트웨이는 텍스트 미디어 타입 안의 모든 줄바꿈을 RFC 2049의 정규 형식인 CRLF로 변환하는 것이 좋다. 다만 Content-Encoding이 있거나, HTTP가 CR과 LF를 각각 옥텟 13과 10으로 표현하지 않는 일부 문자셋을 허용하기 때문에 이 작업이 복잡해질 수 있다.

원래 콘텐츠가 이미 정규 형식이 아니라면, 변환하면 원래 콘텐츠에 적용된 암호학적 체크섬이 모두 깨진다. 그래서 HTTP에서 이런 체크섬을 쓰는 콘텐츠에는 정규 형식을 권장한다.

### B.3. 날짜 형식 변환

HTTP/1.1은 날짜 비교 과정을 단순하게 하기 위해 제한된 날짜 형식 집합([HTTP] 5.6.7절)을 쓴다. 다른 프로토콜에서 오는 프록시와 게이트웨이는 메시지에 있는 Date 헤더 필드가 HTTP/1.1 형식 중 하나를 따르도록 하고, 필요하면 날짜를 다시 써야 한다.

### B.4. Content-Encoding 변환

MIME에는 HTTP의 Content-Encoding 헤더 필드에 해당하는 개념이 없다. Content-Encoding은 미디어 타입을 수식하는 역할을 하므로, HTTP에서 MIME 준수 프로토콜로 가는 프록시와 게이트웨이는 메시지를 전달하기 전에 Content-Type 헤더 필드 값을 바꾸거나 표현을 디코딩해야 한다. (인터넷 메일의 Content-Type을 실험적으로 쓴 일부 애플리케이션은 Content-Encoding과 같은 기능을 위해 ";conversions=<content-coding>"이라는 미디어 타입 매개변수를 썼다. 하지만 이 매개변수는 MIME 표준의 일부가 아니다.)

### B.5. Content-Transfer-Encoding 변환

HTTP는 MIME의 Content-Transfer-Encoding 필드를 쓰지 않는다. MIME 준수 프로토콜에서 HTTP로 가는 프록시와 게이트웨이는 HTTP 클라이언트에 응답 메시지를 전달하기 전에 Content-Transfer-Encoding을 모두 제거해야 한다.

HTTP에서 MIME 준수 프로토콜로 가는 프록시와 게이트웨이는 그 프로토콜에서 안전하게 전송되도록 메시지가 올바른 형식과 인코딩을 갖추게 할 책임이 있다. 여기서 "안전한 전송"은 사용하는 프로토콜의 제약으로 정의된다. 이런 프록시나 게이트웨이는 그렇게 하면 목적지 프로토콜에서 안전하게 전송될 가능성이 높아질 경우, 데이터를 변환하고 적절한 Content-Transfer-Encoding으로 표시하는 것이 좋다.

### B.6. MHTML과 줄 길이 제한

MHTML[RFC2557] 구현과 코드를 공유하는 HTTP 구현은 MIME의 줄 길이 제한을 알아야 한다. HTTP에는 이 제한이 없으므로 HTTP는 긴 줄을 접지 않는다. HTTP로 전송되는 MHTML 메시지는 줄 길이 제한과 접기, 정규화 등 MHTML의 모든 규칙을 따른다. HTTP는 메시지 본문을 수정 없이 전송하며, "multipart/byteranges" 타입([HTTP] 14.6절)을 제외하면 콘텐츠나 그 안에 들어 있을 수 있는 MIME 헤더 줄을 해석하지 않기 때문이다.

## 부록 C. 이전 RFC로부터의 변경 사항

### C.1. HTTP/0.9로부터의 변경 사항

HTTP/0.9는 요청에 헤더 필드를 지원하지 않았으므로, 이름 기반 가상 호스트(Host 헤더 필드를 보고 리소스를 선택하는 것)를 지원할 방법이 없다. 이름 기반 가상 호스트를 구현하는 서버는 HTTP/0.9 지원을 끄는 것이 좋다. HTTP/0.9처럼 보이는 요청 대부분은 사실 클라이언트가 request-target을 제대로 인코딩하지 못해서 생긴 잘못된 HTTP/1.x 요청이다.

### C.2. HTTP/1.0으로부터의 변경 사항

#### C.2.1. 멀티홈 웹 서버

클라이언트와 서버가 Host 헤더 필드([HTTP] 7.2절)를 지원하고, HTTP/1.1 요청에 Host가 없으면 오류를 보고하고, 절대 URI(3.2절)를 받아들여야 한다는 요구 사항은 HTTP/1.1이 정의한 가장 중요한 변화 중 하나다.

예전 HTTP/1.0 클라이언트는 IP 주소와 서버가 일대일 관계라고 가정했다. 요청이 향한 IP 주소 말고는 요청의 대상 서버를 구분할 확립된 방법이 없었다. Host 헤더 필드는 HTTP/1.1 개발 중에 도입되었고 대부분의 HTTP/1.0 브라우저가 빠르게 구현했지만, 완전한 채택을 보장하기 위해 모든 HTTP/1.1 요청에 추가 요구 사항을 두었다. 이 글을 쓰는 시점에 대부분의 HTTP 기반 서비스는 요청 대상을 정할 때 Host 헤더 필드에 의존한다.

#### C.2.2. Keep-Alive 연결

HTTP/1.0에서는 각 연결을 요청 전에 클라이언트가 수립하고, 응답을 보낸 뒤 서버가 닫는다. 하지만 일부 구현은 [RFC2068] 19.7.1절에 설명된, 명시적으로 협상하는("Keep-Alive") 방식의 지속 연결을 구현한다.

일부 클라이언트와 서버는 "Connection: keep-alive" 요청 헤더 필드로 명시적으로 협상해서 이런 이전 방식의 지속 연결과 호환되고 싶어 할 수 있다. 하지만 HTTP/1.0 지속 연결의 일부 실험적 구현에는 결함이 있다. 예를 들어 HTTP/1.0 프록시 서버가 Connection을 이해하지 못하면 그 헤더 필드를 다음 인바운드 서버로 잘못 전달하고, 그 결과 연결이 멈춰 버린다.

이를 해결하려는 시도로 프록시만을 겨냥한 Proxy-Connection 헤더 필드가 도입되었다. 하지만 프록시는 여러 계층으로 배치되는 경우가 많아서 위와 같은 문제가 그대로 생기므로, 실제로는 이것도 쓸 수 없었다.

그래서 클라이언트는 어떤 요청에도 Proxy-Connection 헤더 필드를 보내지 않는 것이 좋다.

클라이언트는 요청에 "Connection: keep-alive"를 쓰는 것도 신중히 고려하는 것이 좋다. 이것으로 HTTP/1.0 서버와 지속 연결을 쓸 수는 있지만, 이를 쓰는 클라이언트는 연결이 "멈춘" 요청이 있는지 감시해야 하고(멈췄다면 그 헤더 필드를 그만 보내야 한다는 뜻이다), 프록시를 쓸 때는 이 방식을 아예 쓰지 않는 것이 좋다.

#### C.2.3. Transfer-Encoding 도입

HTTP/1.1은 Transfer-Encoding 헤더 필드(6.1절)를 도입했다. MIME 준수 프로토콜로 HTTP 메시지를 전달하기 전에는 전송 코딩을 디코딩해야 한다.

### C.3. RFC 7230으로부터의 변경 사항

HTTP의 설계 목표, 역사, 아키텍처, 준수 기준, 프로토콜 버전 관리, URI, 메시지 라우팅, 헤더 필드를 소개하는 절 대부분은 [HTTP]로 옮겨졌다. 이 문서는 HTTP/1.1에 특화된 메시지 문법과 연결 관리 요구 사항만 다루도록 줄었다.

콘텐츠 밖에서 단독 CR(bare CR)이 금지되었다. (2.2절)

authority-form의 ABNF 정의가 포트를 생략할 수 있는 더 일반적인 URI의 authority 구성 요소에서, CONNECT에 필요한 구체적인 host:port 형식으로 바뀌었다. (3.2.3절)

수신자는 모호한 메시지 프레이밍을 처리할 때 스머글링/분할 공격을 피해야 한다. (6.1절)

청크 확장의 ABNF에서 ";"와 "=" 주변의 (나쁜) 공백이 다시 도입되었다. [RFC7230]에서 이 공백을 제거했지만, 그 변경이 기존 구현을 깨뜨린다는 것이 드러났다. (7.1.1절)

트레일러 필드 의미론이 이제 청크 전송 코딩의 세부 사항을 넘어선다. 청크 디코딩 알고리즘(7.1.3절)은 트레일러 필드를 헤더 섹션과 따로 저장·전달하도록 권장하고, 수신자가 해당 필드 정의가 병합을 허용하고 병합 방법을 정의한다는 것을 알 때만 헤더 섹션에 병합하도록 하며, 그렇지 않으면 병합하지 말고 트레일러 필드를 버리도록 갱신되었다. 트레일러 부분(trailer part)은 이제 헤더 섹션과 더 일관되고 본문 부분(body part)과 더 구별되도록 트레일러 섹션(trailer section)이라고 부른다. (7.1.2절)

TE 헤더 필드에서 순위를 쓰는 것과 충돌하지 않도록, "q"라는 이름의 전송 코딩 매개변수가 금지되었다. (7.3절)
